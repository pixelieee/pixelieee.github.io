**The one-sentence version:** OpenCode has no unified built-in memory store, and its refresh cadence is the exact inverse of Pi's—`AGENTS.md` re-reads from disk every turn, `SKILL.md` bodies stay cached in process memory until restart, SQLite preserves raw tool records, and compaction slices tool outputs to 2,000 UTF-16 code units before summarizing. <Src {...source} p="packages/opencode/src/session/prompt.ts" l="1255-1285" /> <Src {...source} p="packages/opencode/src/session/compaction.ts" l="50-79" />

By the end, four things should be clear:

1. Edit `AGENTS.md` and `SKILL.md` mid-session: why does the next turn carry the **new rule** while `skill` still returns the **old body**?
2. After a full skill call goes through compaction and restart, why does its tail vanish from the request while still sitting intact in SQLite?
3. Why do two directories with the same skill name produce different winners across 8 cold starts—and mix both sources in one resumed request?
4. When a skill exists on disk yet fails to load, which of **three separate gates** (discovery, catalog visibility, runtime permission) stopped it?

This note pins **v1.18.33** (`51ef4be`), exercising the release `opencode run` and `opencode serve` binaries against a local loopback HTTP provider.

## One map: the mirror image of Pi

Before each request, OpenCode's prompt loop combines three sources: fresh instructions and a permission-filtered skill catalog enter `system`, while SQLite history filtered by prune flags and compaction boundaries enters `messages`. <Src {...source} p="packages/opencode/src/session/prompt.ts" l="1089-1099" /> <Src {...source} p="packages/opencode/src/session/prompt.ts" l="1255-1285" />

<FigOpenCodeArch lang="en" />

| Channel | Where it lives | When disk is read | When edits take effect |
|---|---|---|---|
| **Project rules** (`AGENTS.md`) | Global config dir, repo ancestors, `read`-triggered subdirs | **Re-read on every ordinary request** | Next turn right after saving |
| **Skills** (`SKILL.md`) | Process-local registry (including body `content`) | **Parsed once at process startup** | Only after restarting the process/server |
| **Session history** (SQLite) | `session` / `message` / `part` tables | Queried by `session_id` and filtered per turn | Raw text stays in SQLite; model sees summary + kept tail |

Placed next to [Pi](/notes/pi-memory-skills/), the contrast is unmistakable: **Pi caches rules and reads skill bodies fresh; OpenCode reads rules fresh and caches skill bodies.**

## Project rules: live every turn, with `read` attaching nested packages

OpenCode loads global and project rules with two subtle behaviors:

- **First matching filename wins the loop, yet collects every match up the tree.** Global search checks config `AGENTS.md` (fallback `~/.claude/CLAUDE.md`). Project search tries `AGENTS.md`, then `CLAUDE.md`, then deprecated `CONTEXT.md`. Finding any `AGENTS.md` between `cwd` and the worktree root gathers **all `AGENTS.md` files along that path** and breaks out before checking `CLAUDE.md`. <Src {...source} p="packages/opencode/src/session/instruction.ts" l="60-68" /> <Src {...source} p="packages/opencode/src/session/instruction.ts" l="110-150" /> <Src {...source} p="packages/core/src/fs-util.ts" l="154-166" />
- **Opening a nested file with `read` pulls in nearby rules dynamically.** Starting at the repo root does not preload deep package rules; when `read` opens a source file inside a package, it walks upward and attaches any unattached instruction file (skipping those already in `system`, history, or claimed by the current assistant message). Config `instructions` can also add explicit paths, globs or URLs. <Src {...source} p="packages/opencode/src/tool/read.ts" l="294-314" /> <Src {...source} p="packages/opencode/src/session/instruction.ts" l="179-220" /> <Src {...source} p="packages/web/src/content/docs/rules.mdx" l="109-131" />

Because instructions reload per request while skill bodies sit cached in `info.content`, editing both `AGENTS.md` and a unique `revision` skill mid-session yields a clean split:

```text title="Same session calling unique skill revision · system rule / newly returned skill"
Before editing, running service                 V1 / V1
Both files edited to V2, called again           V2 / V1
Restart server, resume same session ID          V2 / V2
```

## SQLite & compaction: raw text stays, yet compaction slices at 2,000 chars

Sessions persist across three SQLite tables (`session`, `message`, `part`); fresh runs in the same directory share zero history unless resumed by `--session` or continuing the latest top-level session. <Src {...source} p="packages/core/src/session/sql.ts" l="22-36" /> <Src {...source} p="packages/core/src/session/sql.ts" l="68-98" /> <Src {...source} p="packages/opencode/src/cli/cmd/run.ts" l="452-528" />

OpenCode shortens long sessions through two distinct mechanisms, **neither of which erases SQLite**:

1. **Tool output pruning (`prune`)—protects `skill`, stamps a timestamp only.** Walking backward from newest to oldest, it protects ~**40,000** estimated tool-output tokens and skips `skill`; when older prunable outputs exceed **20,000** tokens, it writes `state.time.compacted`. The message converter renders `[Old tool result content cleared]` without deleting the original string from SQLite. <Src {...source} p="packages/opencode/src/session/compaction.ts" l="28-33" /> <Src {...source} p="packages/opencode/src/session/compaction.ts" l="271-315" /> <Src {...source} p="packages/opencode/src/session/message-v2.ts" l="290-302" />
2. **Session compaction (`compaction`)—does not exempt `skill`, hard-slices at 2,000 UTF-16 code units.** Triggered automatically on overflow or manually via `POST /session/{id}/summarize`, it serializes older history for a compaction agent and stores `tail_start_id` for kept recent turns. Every completed tool output passes through `truncate()`:

```ts title="packages/opencode/src/session/compaction.ts · 51–52, 76–79"
const truncate = (value: string) =>
  value.length <= TOOL_OUTPUT_MAX_CHARS ? value : `${value.slice(0, TOOL_OUTPUT_MAX_CHARS)}\n[truncated]`

const output = part.state.time.compacted
  ? "[Old tool result content cleared]"
  : truncate([part.state.output, ...attachments].join("\n"))
return [call, `[Tool result]: ${output}`]
```
<Src {...source} p="packages/opencode/src/session/compaction.ts" l="50-85" />

Testing the release binary with a `release` skill carrying `HEAD_CHECKPOINT_PROBE` and `TAIL_CHECKPOINT_PROBE` (2,500 `x` fillers between them), manual compaction (`tail_turns: 1`), and process restart separates all three views cleanly:

<FigOpenCodeCheckpoint lang="en" />

- **Ordinary call**: receives all 2,894 characters with both markers intact;
- **Compaction input**: hard-cut at 2,000 UTF-16 code units from `<skill_content>` onward (`[truncated]`); `TAIL` at offset 2,574 **never reaches the summarizer**;
- **Resumed request**: sends `What did we do so far?` → `STUB_CHECKPOINT` → `TURN_KEEP` (via `tail_start_id`) → `OK` → `TURN_RESTART`; the old tool turn is gone;
- **Raw SQLite query** (`part.data.state.output`): both `HEAD` (pos 50) and `TAIL` (pos 2,575) remain untouched. <Src {...source} p="packages/opencode/src/session/message-v2.ts" l="525-575" />

Two sharp compaction edge cases:
- **When the entire history fits inside `preserve_recent_tokens`, manual compaction keeps zero verbatim tail.** Default `preserve_recent_tokens` is 1/4 of usable input budget (clamped to 2,000–15,000 tokens); when candidate cut index hits 0, the selector summarizes everything with no retained boundary. <Src {...source} p="packages/opencode/src/session/compaction.ts" l="115-161" /> <Src {...source} p="packages/opencode/src/session/compaction.ts" l="223-268" />
- **Failed summaries do not cut history.** Only a completed, error-free summary stops the reverse scan; a stored `summary: true` message that errored on overflow is skipped on reload. <Src {...source} p="packages/opencode/src/session/compaction.ts" l="358-391" /> <Src {...source} p="packages/opencode/src/session/message-v2.ts" l="525-546" />

## Three gates for skills—plus an unbounded concurrency race

When a skill on disk doesn't fire, separate three independent gates:

1. **Discovery (startup scan + body cached)**: scans user/project `.claude/skills`, `.agents/skills`, OpenCode `skill/` or `skills/`, `skills.paths` and `skills.urls` (registering built-in `customize-opencode` first so disk files can override it). Frontmatter **and body `content`** are stored in the instance registry; a missing `description` does *not* reject the file. <Src {...source} p="packages/opencode/src/skill/index.ts" l="105-139" /> <Src {...source} p="packages/opencode/src/skill/index.ts" l="258-285" />
2. **Catalog visibility (`<available_skills>` lives in `system`, not the tool description)**: `Skill.available(agent)` drops `deny` rules and omits entries without a description (`ask` stays listed). The formatted catalog enters the **`system` message**, while the `skill` tool description merely points there. <Src {...source} p="packages/opencode/src/skill/index.ts" l="310-337" /> <Src {...source} p="packages/opencode/src/session/system.ts" l="107-118" /> <Src {...source} p="packages/opencode/src/tool/skill.txt" l="1-5" />
3. **Runtime approval (`ctx.ask`)**: execution resolves the cached record, checks the last matching permission rule, and returns `info.content`, base dir, and **at most 10** auxiliary file paths (listed only—never executed or read). <Src {...source} p="packages/opencode/src/tool/skill.ts" l="21-65" /> <Src {...source} p="packages/opencode/src/permission/index.ts" l="67-101" />

Observed behavior for the same `release` skill under three policies:

| Policy | Listed in `system` catalog? | Result of `skill("release")` |
|---|---|---|
| `allow` (ordinary agent) | Yes | Returns full body and sampled file list |
| `deny` (`reviewer`) | No | `skill` tool stays in schema; named call returns a permission error with no body |
| `ask` (`approver`) | Yes | Emits a pending approval; replying `once` unlocks only that call (next call gets a new ID) |

### Why duplicate skill names win at random

After collecting all matching paths, `loadSkills` parses them with **unbounded concurrency** and assigns directly to `state.skills[md.data.name]`—**last finisher overwrites earlier ones**:

```ts title="packages/opencode/src/skill/index.ts · 240–243"
yield* Effect.forEach(discovered.matches, (match) => add(state, match, events), {
  concurrency: "unbounded",
  discard: true,
})
```

## What actually outlives a session

OpenCode has no post-turn review loop rewriting `SKILL.md`. Cross-session persistence runs through three explicit paths:

1. **Writing to discoverable files**: `/init` guides the agent to create/update root `AGENTS.md`, and authorized editing tools can save verified procedures into `SKILL.md`. <Src {...source} p="packages/opencode/src/command/template/initialize.txt" l="33-66" /> <Src {...source} p="packages/opencode/src/tool/registry.ts" l="211-246" />
2. **Model-specific prompt workflow (not a default memory store)**: certain model names select `PROMPT_BEAST`, telling the model to write `.github/instructions/memory.instruction.md`—but the default instruction loader never lists that filename. <Src {...source} p="packages/opencode/src/session/llm/request.ts" l="53-67" /> <Src {...source} p="packages/opencode/src/session/prompt/beast.txt" l="114-134" />
3. **Plugin hook**: `experimental.session.compacting` lets plugins inject extra context or replace the compaction prompt; long-term persistence and skill evolution belong to the plugin. <Src {...source} p="packages/plugin/src/index.ts" l="291-316" /> <Src {...source} p="packages/web/src/content/docs/plugins.mdx" l="350-389" />

## Gotchas & where docs disagree with code

### Four practical gotchas

<Infer lang="en" /> Engineering judgment based on the code and traces above:

1. **Seeing a new rule does not mean your edited skill reloaded**: `AGENTS.md` reloads every turn while skill bodies stay cached until restart (`V2 / V1`).
2. **Long skills lose their tail before summarization**: `prune` protects `skill`, but compaction hard-cuts tool outputs at 2,000 UTF-16 code units including `<skill_content>` wrappers.
3. **Never rely on directory precedence for duplicate skill names**: unbounded concurrent parsing lets the last finisher win, causing cross-restart mismatches.
4. **Manual compaction on a short session can drop all verbatim tail**: when all history fits in `preserve_recent_tokens`, the cut index hits 0 and sets no `tail_start_id`.

## Answering the four opening questions

1. **After editing both `AGENTS.md` and `SKILL.md` mid-session, why does the next turn see new rules immediately while `skill` still returns the old body?** OpenCode re-reads `AGENTS.md` from disk on every turn, whereas parsed skills (including their full bodies) are cached in process memory on first scan until the process restarts.
2. **Why do the tail steps of a read skill vanish after compaction and restart even though SQLite still holds the full text?** Raw tool outputs remain intact in SQLite's `part` table, but before compaction summarizes history it truncates older tool outputs to their first 2,000 UTF-16 characters—dropping `TAIL_CHECKPOINT_PROBE` before the summary is written.
3. **Why did a duplicate skill name pick different winners across 8 cold starts and mix two sources on resume?** Discovery scans roots concurrently with unbounded `Promise.all`, so whichever file finishes last overwrites the map entry; resuming an older session keeps the old tool result in history while the new process's `system` catalog may list the other root.
4. **When a skill on disk cannot be used, which gate blocked it?** Check three gates in order: discovery (root paths, external-root toggles, or missing `description` hiding it from formatting), catalog rendering in `system` (`<available_skills>`), and `permission.skill` (`allow`, `ask`, or `deny`).
