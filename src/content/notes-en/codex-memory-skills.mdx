**The one-sentence version:** Codex CLI runs cross-session memory as a two-phase async pipeline behind App Server—waiting 6 hours of thread inactivity to extract and a second 6-hour cooldown to consolidate `memory_summary.md`, while writer validation checks only format rather than factual inclusion. <Src {...source} p="codex-rs/app-server/src/request_processors/turn_processor.rs" l="747-783" /> <Src {...source} p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

By the end, four things should be clear:

1. Why can a consolidation job report `done` after extracting a correction in repo A while a new thread in repo B still sees only the old summary?
2. Why does an **empty** extraction delete prior evidence while an error leaves prior evidence standing?
3. After an empty extraction drops SQLite rows to zero, why does the disk file under `rollout_summaries/` survive for another 6 hours?
4. Why does `codex debug prompt-input` never show a valid summary that real App Server threads read cleanly?

This note pins **Codex CLI 0.169.0** (`d32063f`) on the local App Server runtime (IDE extensions share their host's local store; ChatGPT web uses a separate store). [Official memory guide](https://learn.chatgpt.com/docs/customization/memories)

## One map: three persisted layers & two six-hour clocks

In Codex, "saved" spans three separate stores—**`stage1_outputs`** (per-thread SQLite rows), **`rollout_summaries/`** (materialized source files), and **`memory_summary.md`** (what new threads read first). They can disagree briefly or indefinitely, while project skills follow `cwd` on an independent track:

<FigCodexMemory lang="en" />

| Object | Where it lives | How it reaches a future turn |
|---|---|---|
| **Rollout** | Active thread appends events; index tracks source & last activity | Phase 1 claims idle past threads and scans their rollouts backwards |
| **Local memory** | Phase 1 writes SQLite; Phase 2 syncs `rollout_summaries/` & `memory_summary.md` | New thread reads `memory_summary.md` (capped at 2,500 tokens), opening source files lazily |
| **Project skills** | `.agents/skills/<name>/SKILL.md` | Discovered per `cwd` into a catalog; body opened on selection |

Controls split cleanly: `features.memories` defaults to `false`; once enabled, `generate_memories` and `use_memories` both default to `true` and can be toggled independently alongside per-chat `/memories`. <Src {...source} p="codex-rs/features/src/lib.rs" l="1449-1454" /> <Src {...source} p="codex-rs/config/src/types.rs" l="330-338" /> <Src {...source} p="codex-rs/config/src/types.rs" l="382-391" />

## Phase 1: triggered on new turns, tiered sampling, empty means retract

Memory scheduling fires inside App Server's `turn/start` handler—requiring **input that starts a new turn** (steering an in-flight turn skips it) and ignoring ephemeral sessions and non-root agents. <Src {...source} p="codex-rs/app-server/src/request_processors/turn_processor.rs" l="747-783" /> <Src {...source} p="codex-rs/memories/write/src/start.rs" l="24-99" />

The scanner **explicitly excludes the triggering thread** and queries past threads across all directories (no `cwd` or project filter):
- **First 6-hour clock**: idle at least **6 hours**, active within **10 days**, claiming up to **2** threads per pass from interactive sources only (`Cli`, `VSCode`, `atlas`, `chatgpt`—not `codex exec`); when a Codex quota snapshot exists, it also requires ≥ 25% remaining headroom. <Src {...source} p="codex-rs/config/src/types.rs" l="57-62" /> <Src {...source} p="codex-rs/rollout/src/lib.rs" l="86-95" /> <Src {...source} p="codex-rs/memories/write/src/phase1.rs" l="127-143" /> <Src {...source} p="codex-rs/memories/write/src/guard.rs" l="42-80" />
- **8 MiB tiered input**: scans backwards (1 MiB per record, 8 MiB total), replaces media, caps tool outputs, and fills remaining budget in strict tier order before restoring chronology—so user corrections outrank routine tool logs. Each V2 output is redacted and capped at **9,000 bytes**: <Src {...source} p="codex-rs/memories/write/src/rollout_input.rs" l="28-68" /> <Src {...source} p="codex-rs/memories/write/src/rollout_input.rs" l="239-304" /> <Src {...source} p="codex-rs/memories/write/src/phase1_output.rs" l="29-52" />

- **Empty vs. failure do opposite things**: content updates the row and advances consolidation; an **empty string** advances the watermark and **deletes any prior row for that thread** (triggering consolidation only if a row was actually deleted); an error consumes a retry with 1-hour backoff and **leaves prior rows intact**. <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="860-873" /> <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="946-955" /> <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="1003-1029" /> With `disable_on_external_context`, qualifying external tools/MCP can also mark a thread `polluted` to schedule retraction. <Src {...source} p="codex-rs/core/src/mcp_tool_call.rs" l="1052-1068" /> <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="632-667" />

## Phase 2: second 6-hour cooldown, format-only validation, and permissive reads

Phase 2 ranks up to **256** stage-1 rows from the past **30 days** by usage count and recency, materializes `rollout_summaries/`, computes a Git diff, and hands the diff to an ephemeral consolidation agent to update `memory_summary.md`. <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="440-491" /> <Src {...source} p="codex-rs/memories/write/src/phase2.rs" l="64-180" />

Three decisive details:

1. **Second 6-hour clock**: global consolidation cannot claim a new lease until 6 hours after the last successful consolidation—so newly added or deleted SQLite rows wait before `rollout_summaries/` or `memory_summary.md` reflect them. <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="24-29" /> <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="1081-1102" />
2. **`done` checks structure, never factual inclusion**: V2 completion validates only `v1` on line 1, four headings, and `< 10,000` UTF-8 bytes: <Src {...source} p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

```rust title="codex-rs/memories/write/src/workspace.rs · 118–129"
pub fn is_valid_v2_summary(summary: &str) -> bool {
    summary.lines().next() == Some("v1")
        && summary.len() < 10_000
        && [
            "## User Profile",
            "## User preferences",
            "## General Tips",
            "## What's in Memory",
        ]
        .iter()
        .all(|heading| summary.lines().any(|line| line.trim() == *heading))
}
```

3. **Strict writer, permissive reader, and V1 vs. V2 stores**: a clean `CODEX_HOME` selects `memories_v2/` (existing `memories/` stays on V1, whose template may write `skills/` inside its memory workspace—not into project `.agents/skills/`). On read, the extension accepts any non-empty readable `memory_summary.md` capped at **2,500 tokens** without rechecking headings; explicit user "remember/forget" requests append to `extensions/ad_hoc/notes/` for later consolidation. <Src {...source} p="codex-rs/core/src/config/mod.rs" l="3721-3735" /> <Src {...source} p="codex-rs/ext/memories/src/extension.rs" l="45-76" /> <Src {...source} p="codex-rs/ext/memories/src/prompts.rs" l="35-62" /> <Src {...source} p="codex-rs/ext/memories/templates/memories/read_path_v2.md" l="3-20" />

## Live project skills—and the `debug prompt-input` counterexample

Project skills walk `.agents/skills` from `cwd` to repo root (plus `~/.agents/skills`, legacy `$CODEX_HOME/skills`, system/admin/plugin roots), completely independent of memory cooldowns. <Src {...source} p="codex-rs/ext/skills/src/host_roots.rs" l="101-177" /> <Src {...source} p="codex-rs/ext/skills/src/host_roots.rs" l="235-260" />

- **Live reload without restarting App Server**: over one stdio connection with `forceReload: true`, writing `Marker alpha` then `Marker beta` updates the catalog immediately without leaking body text, while a sibling directory sees nothing; a 2-line `v1` + `SUMMARY_7392` file (missing all 4 headings) is still returned by `thread/memory/read` when `use_memories` is on. <Src {...source} p="codex-rs/app-server/src/request_processors/catalog_processor.rs" l="548-617" /> <Src {...source} p="codex-rs/app-server/tests/suite/v2/memory_read.rs" l="99-125" />
- **Debugging trap: `codex debug prompt-input` omits the memory extension**: with `SUMMARY_7392` in place, the debugger prints user input `INPUT_6185` whether memories are off or on, yet **never includes `SUMMARY_7392`**—because it bypasses App Server and builds a custom extension registry that installs Skills without `codex_memories_extension`. <Src {...source} p="codex-rs/cli/src/main.rs" l="2186-2230" /> <Src {...source} p="codex-rs/app-server/src/extensions.rs" l="101-111" />

## Practical gotchas

<Infer lang="en" /> Four takeaways when working with Codex memory and skills:

1. **Put team invariants in `AGENTS.md` or `.agents/skills/`, not background memory**: opening repo B minutes after repo A is far inside the 6-hour idle window, and checked-in files can be reviewed and scoped cleanly.
2. **Debug recall in three layers**: inspect `stage1_outputs` for extraction, global job state + 6h cooldown for stale source files, and `thread/memory/read` for what a thread receives (**never trust `codex debug prompt-input` for memory**).
3. **`done` guarantees format, not content**: a lazy consolidator that leaves a valid stale summary untouched still passes `is_valid_v2_summary`.
4. **Verify `CODEX_HOME`, `CODEX_SQLITE_HOME` and V1/V2 together**: any mismatch points two launches at different stores. <Src {...source} p="codex-rs/config/src/config_toml.rs" l="373-377" /> <Src {...source} p="codex-rs/state/src/runtime.rs" l="355-377" />
