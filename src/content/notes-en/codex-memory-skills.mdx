Suppose you corrected a test command in project A, then opened a conversation in B. I reproduced a case in **Codex CLI 0.169.0** where extraction had saved the command, the source file contained it, and the consolidation job reported `done`. B still received only the old summary.

The word “saved” can refer to three things. `stage1_outputs` holds evidence indexed by source thread. `rollout_summaries/` holds files materialized from the selected evidence. `memory_summary.md` is what a new thread reads first. The three can disagree briefly or carry different content indefinitely. Project skills take a separate path. Their visibility can change immediately with the working directory, independently of memory consolidation.

## Where a conversation enters the runtime

This note follows **Codex CLI 0.169.0**. The interactive command starts the terminal UI. Its local connection path can use a daemon or start an embedded App Server. The implementation of `codex exec` also starts an in-process App Server client. An external client can run `codex app-server` separately and send JSON-RPC requests such as `thread/start`, `turn/start` and `skills/list`. The App Server sits between the client and the thread runtime. Its `turn/start` handler contains the call that schedules background memory work. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/cli/src/main.rs" l="2598-2611" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/tui/src/lib.rs" l="596-637" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/exec/src/lib.rs" l="1097-1106" /> [App Server protocol](https://learn.chatgpt.com/docs/app-server)

That boundary matters when comparing products. OpenAI documents that the IDE extension uses the local memory store of the Codex host it connects to. ChatGPT on the web has its own memory, and the settings available to ChatGPT Work depend on the account and workspace. The paths, defaults and experiments below apply to this release of the public local runtime. [Official memory guide](https://learn.chatgpt.com/docs/customization/memories)

## Three kinds of stored information

| Object | Who writes it | How it is read later |
| --- | --- | --- |
| Conversation record (rollout) | The active thread produces events. Its index records information such as source, path and last activity. | An extractor selects a past thread and opens its rollout. |
| Local memory | The extractor records per-thread results. A consolidation agent updates the summary from selected material. | A new thread starts with `memory_summary.md` and can consult the underlying evidence. |
| Local project skill | A person or a tool with write access creates `.agents/skills/<name>/SKILL.md`. | Discovery exposes a name, description and locator. The instructions can then be opened when the skill is selected. |

Consequently, `skills/list` answers “which skills can this directory see?” Determining which instructions a model actually read takes separate evidence. A message in a rollout likewise needs to survive selection and additional model calls before it can shape a later conversation. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase1.rs" l="257-283" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/ext/memories/src/prompts.rs" l="35-62" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/ext/skills/src/catalog_prompt.rs" l="3-21" />

## Writing starts with a new turn that has input

This release marks `features.memories` as `stable` and defaults it to `false`. Once enabled, two more settings govern different decisions. `memories.generate_memories` determines whether newly created threads are marked as inputs for future generation. `memories.use_memories` controls the read instructions for existing memories. Both settings default to `true`. A new conversation can therefore consult earlier memories while being excluded from future extraction. The interactive `/memories` command also offers per-chat controls. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/features/src/lib.rs" l="1449-1454" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/config/src/types.rs" l="330-338" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/config/src/types.rs" l="382-391" /> [Configuration and chat controls](https://learn.chatgpt.com/docs/customization/memories)

The function has `startup` in its name, but the App Server calls it **after submitting input**. The request must have input, start a new turn and have a primary execution environment configured. Input steering an existing turn takes a different branch. The entry point skips ephemeral sessions, disabled features and non-root agents. The asynchronous worker then checks the state database, prepares its directory and checks quota. ### Which parts of a conversation reach the extractor?

The full transcript may still exist even when its evidence no longer fits the extractor's input. The reader scans recent records backwards, with a 1 MiB limit per record and an 8 MiB budget for the recent input. Oversized or older records can drop out. ### Why an empty extraction can delete an earlier result

A thread has three possible outcomes. On success with content, a transaction records the source timestamp and summary and advances the global consolidation job. An empty result also records a successful pass through that source timestamp, but deletes any existing extraction for the thread. It advances consolidation only if it actually deleted a row. A model or service error records the failure, consumes a retry and schedules backoff, leaving prior output alone. **Empty can retract evidence. Failure leaves the previous judgment standing.** <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="860-873" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="946-955" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="1003-1029" />

What stops every new turn from submitting the same transcript again? The job stores a `last_success_watermark`. An existing output or successful job covering the source timestamp prevents another claim. A worker already holding a valid lease also excludes competitors. When the source advances, it can become eligible again, with explicit handling for previous backoff and exhausted retries. A stage-one lease and its failure backoff both default to one hour, independently of the six-hour idle window for a source thread. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="667-685" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/lib.rs" l="83-89" />

## What survives consolidation

Stage-one outputs compete for space. The query ranks by usage count and then by last use or source update. A never-used entry falls back to its source timestamp. Defaults allow up to 256 entries within a 30-day recency window. Thirty days is a **selection condition for source material**. It does not predict the day a claim will disappear from a summary someone is already reading. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="440-491" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/config/src/types.rs" l="57-62" />

Consolidation uses a global job lease and a lock on the memory workspace. It synchronizes the selected `rollout_summaries/` and computes changes against a Git baseline. If the workspace has no changes and its existing outputs validate, the job can finish there. Otherwise, the agent receives a diff. Its own thread is ephemeral, with memory generation, memory reading and recursive delegation disabled. The V2 instructions tell it to retain provenance, scope and later corrections while updating `memory_summary.md`. The durable change is to text on disk that future requests can use as context. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="64-100" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="137-180" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="215-222" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="318-335" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/templates/memories/consolidation_v2.md" l="12-32" />

### How long does a source survive in the database and on disk?

`selected_for_phase2` identifies the **version of a source selected by the last successful consolidation**. Database pruning only removes old rows outside that selection. The next consolidation prunes files absent from its newly selected set and rewrites the retained ones. Each source file includes a thread ID, source timestamp, rollout path, working directory and, when known, Git branch. These fields let a reader trace where an assertion came from. The presence of a Markdown file alone does not establish that its source row still exists. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="401-425" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="1259-1274" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/storage.rs" l="23-41" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/storage.rs" l="115-136" />

This is where a **second six-hour clock** matters. The first runs from the old thread's last activity and controls extraction. This one runs from the most recent successful global consolidation and controls the next job claim. New input can already be pending while a new turn updates only the database. At consolidation completion the writer confirms it still owns its lease before resetting the Git baseline and recording the selected inputs. If the consolidation agent cannot shut down, the existing lease stays in place to keep another writer out of its directory. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="24-29" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="1081-1102" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="419-435" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="443-485" />

### What does a successful consolidation guarantee?

V2 checks the function below on completion. The first line is a file-format marker, so even a V2 summary begins with `v1`. Rust's `str::len()` counts UTF-8 bytes. This validation requires the four headings and a file smaller than 10,000 bytes. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

```rust
pub fn is_valid_v2_summary(summary: &str) -> bool {
    summary.lines().next() == Some("v1")
        && summary.len() < 10_000
        && [
            "## User Profile",
            "## User preferences",
            "## General Tips",
            "## What's in Memory",
        ]
        .iter()
        .all(|heading| summary.lines().any(|line| line.trim() == *heading))
}
```

The function never checks whether a particular fact in the new source made it into the summary. The consolidation prompt asks the model to ground changes in evidence, remove obsolete claims and apply corrections. The runtime uses the agent's terminal state and the artifact checks to decide whether the job succeeded. Giving the consolidation agent the same prerecorded “finished” reply in two cases makes that division visible. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/templates/memories/consolidation_v2.md" l="39-52" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/phase2.rs" l="407-436" />

### Which summary does a new thread read?

Check the selected store before diagnosing a missing file. A fresh `CODEX_HOME` with memories enabled chooses V2's `memories_v2/` if there is no explicit version, dual writing has not been explicitly disabled, and Codex confirms the old directory does not exist. A profile with an existing `memories/` directory continues on V1 by default. V1 also materializes `raw_memories.md`, and its consolidation instructions allow a `MEMORY.md` and reusable `skills/` **inside its memory workspace**. V2's template centers on the summary and source evidence. **The writer validates the format. The reader accepts readable, nonempty text.** The extension checks the feature and `use_memories`, reads `memory_summary.md` from the selected directory, trims whitespace, then applies a 2,500-token budget. A missing or unreadable file, or text that is empty after truncation, produces no memory prompt fragment. Prompt construction does not recheck the `v1` first line, the four headings or the writer’s 10,000-byte limit. V2 instructs the model to open a particular rollout summary when its wording, chronology or uncertainty could affect the answer. For an explicit request to remember, correct or forget, it directs the model to append a small note under `extensions/ad_hoc/notes/` for later consolidation. ## Experiment: remove a source and watch the next thread

I ran the release `codex app-server` against a Responses fixture bound to loopback. In working directory A, `thread/start` and `turn/start` created two synthetic conversations using the real rollout format. I moved only their last-activity timestamps back eight hours in the temporary state database, leaving their directories, source types, thread IDs and transcripts intact. A new turn in directory B triggered the default scanner. Both stages ran release code. The fixture supplied model responses so that the test could measure state transitions independently of summarization quality.

The extractor's fixture returns the command `check-atlas-47` for the first conversation and an empty summary for the second. The consolidation fixture always replies “finished” and **never requests a file write**. I used two separate Codex homes and varied only the initial global summary. I inspected SQLite, the files on disk, and `thread/memory/read` on a new thread.

| Observation | Empty store at the start | Store starts with a valid old summary |
| --- | --- | --- |
| Stage one | Two completed jobs, one extraction row | Same |
| Source files | One, containing the new command | One, containing the new command |
| Global job | `error / failed_invalid_artifacts` | `done`, row marked selected |
| New thread reads | `null` | Old marker `PRIOR_ONLY_63`, no new command |

The fact was present in the database and in the source file in both cases. The first run failed validation because it lacked a global summary. The second kept a stale summary and passed. Looking up job status and asking whether the next thread can immediately see a specific fact can yield different answers.

In a third run I changed the second extractor reply from valid empty JSON to invalid text. The two jobs in the same batch ended as `done` and `error`, with a future `retry_at` for the failed job. The first thread still produced a source file and global consolidation completed. Diagnosing a partial extraction failure therefore requires looking at individual thread jobs.

**I then made the previously retained source extract to nothing.** I added a synthetic turn to the original thread in A, telling the fixture to return an empty result on re-extraction. I placed its last activity ten minutes after its previous source timestamp while keeping it more than six hours old. A turn in B reduced `stage1_outputs` from one row to zero and left the global job `pending`. The previously successful rollout directory **still held one file**. I moved only the global job's completion timestamp back seven hours in the fixture database. The next ordinary turn then reduced the source-file count to zero and the global job returned to `done`. The old global summary was unchanged throughout this replay.

This suggests a practical order for investigating recall. Look at the source row and its timestamp to diagnose extraction. For a stale source file, check global job state and the last successful consolidation. To learn which summary a new thread received, read it through that thread. Adjusting the two clocks was a shortcut confined to disposable databases.

```shell
python codex-memory-lifecycle.py blank
python codex-memory-lifecycle.py stale
python codex-memory-lifecycle.py malformed
```

## How project skills are discovered

Repository discovery checks `.agents/skills` at each level between the working directory and the project root. A skill at the root can cover nested working directories. A skill under one subdirectory may be invisible to its siblings. User locations include `~/.agents/skills` and the older `$CODEX_HOME/skills`. System, admin and plugin roots have their own sources. The memory root follows Codex home and version, while a project skill follows the working directory and discovery source. Two repositories can share one memory store and still have different runbooks. <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/ext/skills/src/host_roots.rs" l="101-113" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/ext/skills/src/host_roots.rs" l="140-177" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/ext/skills/src/host_roots.rs" l="235-260" />

OpenAI advises skill authors to put the trigger in the `description`. The initial catalog gives the model a way to discover and choose a skill. ## Back to that test command

For a team-owned test command, a checked-in `AGENTS.md` or project skill gives the team a change to review, a revision to revert and a directory scope to verify. For a clue from one investigation, retaining its evidence allows a future agent to check that it still applies. In our example, opening B a few minutes later is too early for the just-finished conversation in A to pass the default idle window. Even after consolidation, sharing a Codex home only creates an opportunity for cross-project recall. As for the project skill in A, the experiment showed that B never listed it.
