**In one line:** Frontier harnesses already look alike on “can I resume a session?”. They split on **where truth lives, who touches the outside world, how agents talk, and how you embed the thing**. DeepSeek Harness derives model-visible history from an append-only log, yet the loop still calls the model and tools—that gap between “log is truth” and “loop only emits commands” is still open.

This note is not a product review and not the memory/skills series. It exists so you can judge Pure Agent’s end-state without being captured by one vendor story.

After reading you should answer:

1. Is “append-only JSONL” the same as “the log is the sole source of truth”?
2. Why can dsh say “everything is a plugin” and still not be a pure core?
3. How do products build “one agent talks to the user; others work in the background”?
4. What problem do in-process libraries, on-demand subprocesses, and always-on app servers each solve?
5. Where is the seat nobody holds firmly for a TypeScript kernel?

Same word—“harness”—different layers. Alma is UI; Hermes is an app with a gateway; Claude Code / Codex are full products with embed shells; pi / dsh sit closer to “something you import or spawn”. Pure Agent should align with that last layer.

## Four axes

## Axis 1 — Where truth lives

**Claim A: the session is an append-only file.** Claude Code writes JSONL and reads it back on resume. Codex has rollout JSONL “so sessions can be replayed or inspected later”. pi stores a JSONL tree with `id` / `parentId`. That only means chat can come back—not that the live loop believes the file.

**Claim B: model-visible history is derived only from the log.** Among the seven, DeepSeek Harness states this in the open:

> The LLM message history is *derived* from the log, never stored separately; replay is re-derivation from the same events.

(`docs/subsystems/session.md` @ `2e39e70`). The loop builds requests via `deriveMessages()`.

| | On disk | What the live loop trusts | “Log is sole truth”? |
|---|---|---|---|
| Claude Code | JSONL transcript | Docs do not specify internals | Not claimed |
| Codex | Memory history + rollout + state DB | `run_turn` reads memory history | No |
| pi | JSONL tree | In-flight: memory; finished: SessionManager | For finished trees |
| OpenCode | SQLite sessions / durable events | Recorded Session history | Commit log, not command fold |
| Hermes | SQLite persistence | Message list to the model | Canonical copy, not fold executor |
| Alma | Product Memory objects | No event-log docs | N/A |
| dsh | Append-only SessionEvent | `deriveMessages()` | **Yes for model-visible history** |

Append-only is common. **Treating the log as the loop’s only input** is not. <Infer lang="en" /> Learning only “write JSONL” buys the entry ticket, not the differentiator. That differentiator continues on axis 2.

## Axis 2 — Who runs side effects

Log truth does not imply a pure loop.

DeepSeek Harness stacks both: history from the log, and a loop that still calls `llm.stream` / `tools.execute`. In memory, `tool/call` is appended before dispatch; on disk, fail-closed flush before requests / tool effects lives in the **removable** plugin `dsh-session-checkpoint-policy`. Architecture docs say the agent loop itself is a plugin. Crash repair returns a physically valid prefix, then `interruptedTurnClosers` appends synthetic results—strong, but the executor remains a replaceable `AgentLoop` service.

“Event-driven” is not “side-effect free” either. Pizza replaces a dialogue `while` with store subscriptions, yet LLM handlers still `await` the model. OpenSuperAgent’s outer loop is a 400ms pump. Those designs answer “what wakes you”, not “can effects enter the core”.

The empty sentence for Pure Agent is:

> The log is sole truth; `reduce` only emits effects; model and tool I/O live in the interpreter; replay checks effects instead of re-performing them.

dsh finished the “model history” half. The second half is still open. The old runtime string `log-reconstruction desync` is gone from `2e39e70` (removed with runtime-invariant plugins in v0.2.0-rc.2). Keeping a desync assert would be Pure Agent’s own test, not current dsh behavior.

## Axis 3 — How agents talk

“One talks to the user; others work” is assembled a few ways:

1. **Subagent-as-tool** — child run returns a tool result (Claude Code subagents, many `background: true` switches).
2. **First-class sessions + mailbox / steer** — Codex mailbox; pi steer/followUp; dsh turns `sendMessage` into a `UserMessage` with `kind: 'agent-message'` then steers the same inbox (unified entry, typed).
3. **Orchestration ledger outside the loop** — OpenSuperAgent inbox + pump; dsh-superagent-prototype effects with `relay` (wake) vs `notice` (inject without wake).
4. **Product teams** — Claude Code experimental agent teams; Hermes `delegate_task`; Alma workflows + human approval.

Most products do **not** unify user text, peer traffic, and external events into one message type. Pizza often wraps peer `_tell` as prefixed `USER_MESSAGE`—one entry, lost types. <Infer lang="en" /> A cleaner shape is one `Input` pipe with `user` / `peer` / `external` kept distinct.

## Axis 4 — How you embed

| | Primary embed | Always-on server? |
|---|---|---|
| Claude Code | Subprocess per `query()` | Managed Agents are hosted; not a local app server |
| Codex | Public TS SDK = `codex exec` | app-server exists; TS SDK does not default to it |
| pi | In-process SDK | Long-lived RPC child, no port by default |
| OpenCode | In-memory router | Optional HTTP on localhost |
| Hermes | In-process Python | Gateway stays up for IMs |
| Alma | No local SDK | Hosted HTTP / MCP |
| dsh | In-process Cordis; SDK spawns `dsh` | `127.0.0.1:3080` is the **web** profile only |

Pattern: **embed defaults to in-process library or on-demand process**. Always-on servers appear after multi-client / IM / remote-desktop product reasons. That is also why Pure Agent should not copy dsh’s “loop is a plugin”: dsh’s immovable pieces are Cordis and event contracts; making `reduce` configurable recreates “no privileged core” and erases the open seat.

## The empty seat

| | Log-derived model history | Loop never runs side effects | In-process `import` | Core guarantees not unpluggable |
|---|---|---|---|---|
| pi | Weak | No | **Yes** | Core loop yes; many features live in extensions |
| dsh | **Strong** | No | Yes (also subprocess SDK) | No—loop replaceable |
| Codex / Claude Code | Weak / undocumented | No | Public SDKs mostly subprocess | Strong products, not a pure TS in-process kernel |
| OpenCode / Hermes | Medium | No | Limited | No |

Nobody firmly holds all four: TypeScript in-process import, append-only log as sole truth for history **and** effects, `reduce` that never performs I/O, and guarantees that are not profile plugins.

## Checklist (fill after reading)

**A. Truth** — resume JSONL only / derive model history (dsh) / also journal effects for replay checks (open seat)

**B. Execution** — loop may call tools (mainstream) / loop emits effects only (open seat) / disk write-ahead as plugin (dsh) / as kernel guarantee (stricter)

**C. Messaging** — subagent-as-tool / sessions+mailbox / outer ledger / unified Input with peer types

**D. Embedding** — in-process only / library + on-demand bridge / default app server

**E. Extension** — everything is a plugin including the loop (dsh) / small immovable core + unloadable modules

**F. Wording** — Primitive / Module / Capability (instead of the casual “lego” metaphor)
