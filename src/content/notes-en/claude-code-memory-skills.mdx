While updating a release script, I tell Claude three things. “This repository publishes with `make release`.” “The on-call engineer confirms when we go live.” “Next time you draft release notes, list the compatibility changes.” It can repeat all three immediately. Which of them will reach the model after I close the terminal and start a fresh conversation in the same repository?

**It depends on who wrote the information to disk and what causes the next session to read it.** I traced four invocations of Claude Code 2.1.327. A plain prompt sent the project instructions and an ordinary skill’s description. An explicit invocation added its body. A read inside a subdirectory brought two more instructions into the next request. Below I distinguish those observations from the product’s documented behavior and my interpretation. The version comes from the installed CLI. I checked the official documentation on November 18, 2026. [Pinned release changelog](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L3)

I also checked a privately held historical snapshot from spring 2026 to identify which reads and writes to trace. It cannot establish how the current release works. Every claim below about the current product rests on publicly checkable material or the reproducible probe at the end.

## Who owns the information?

| What should survive | Where it goes and who writes it | When it appears again |
|---|---|---|
| A team convention, such as getting sign-off from the on-call engineer | The team reviews a root `CLAUDE.md` alongside code | Loaded when starting in the repository. Organizations and users can supply instructions at their own scopes |
| Instructions for code under `module/` | The team writes Markdown with a `paths` selector under `.claude/rules/`, or puts a `CLAUDE.md` inside the directory | When starting above the directory, the matching file access brings these into context |
| A correction that will matter again | Claude can write a topic note in the local project’s auto-memory directory and maintain its `MEMORY.md` index. The user can inspect and edit both | A bounded prefix of the index goes into a new conversation. A separate read retrieves the topic |
| Steps, checks and a template for release notes | The team or user maintains `.claude/skills/release-card/SKILL.md` and any attachments. Claude can draft changes for review | Usually the name and description appear first. Selecting the skill or typing `/release-card` loads its body |
| The command that ran last time and its output | Conversation history | Resuming that session brings its history back. A fresh session does not receive the entire transcript along with the project instructions |

If the `Makefile` already specifies the release command, a second permanent copy can go stale. I would record the sign-off convention, which the code cannot tell me, and put the release-note template in a skill. A one-off failed build belongs in the current session. A later implementation change can then pick up the sign-off requirement without loading the entire publishing procedure. [Project memory](https://code.claude.com/docs/en/memory) · [Where skills load](https://code.claude.com/docs/en/skills#where-skills-live) · [Context and sessions](https://code.claude.com/docs/en/how-claude-code-works)

## Which rules reach the first request?

Suppose the session starts at the repository root. Claude Code concatenates the `CLAUDE.md` files it finds from ancestor directories down to the working directory. At a given level, `CLAUDE.local.md` comes later. Both passages enter context. The documentation describes project instructions as a user message delivered after the system prompt. If one says “always run the full suite” and the other says “run only the relevant tests,” their order cannot guarantee an engineering policy. CI should enforce checks the team cannot skip. [Instruction loading order](https://code.claude.com/docs/en/memory#how-claude-md-files-load)

Reading `module/a.py` from the root can cause two additional loads. The nested `module/CLAUDE.md` applies when the CLI accesses files in that directory. A rule in `.claude/rules/module.md` can narrow its scope to Python files with `paths: ["module/**/*.py"]`. Both markers were absent from the first request in my experiment. After a real CLI `Read` of `module/a.py`, the file, the nested instructions and the path rule all appeared in the next request. For diagnosis in a real repository, the `InstructionsLoaded` hook can distinguish `session_start`, `nested_traversal` and `path_glob_match`. [Path-specific rules](https://code.claude.com/docs/en/memory#path-specific-rules) · [InstructionsLoaded hook](https://code.claude.com/docs/en/hooks#instructionsloaded)

There is also a selection rule for `AGENTS.md`. With this version’s defaults, a project-side `CLAUDE.md` or `CLAUDE.local.md` in or above the working directory prevents the fallback to direct `AGENTS.md` loading. With both root files present, only the `CLAUDE.md` marker reached my first request. A team maintaining both can explicitly configure their joint use or import the shared instructions with `@AGENTS.md` from `CLAUDE.md`. Direct `AGENTS.md` support starts with v2.1.277 and depends on the execution environment. [AGENTS.md selection rules](https://code.claude.com/docs/en/memory#agents-md)

## Auto memory has to be discoverable after a write

Auto memory is enabled by default for local terminal sessions. Claude judges whether a correction, preference, project decision or external reference is worth keeping. A session can end without writing anything. The standard directory is `~/.claude/projects/<project>/memory/`. **By default, worktrees from the same repository on one machine share auto memory.** Switching to another machine does not transfer it. The user can inspect, edit or disable it through `/memory`. Expiration of session history leaves the memory files intact. [Write scope and storage](https://code.claude.com/docs/en/memory#auto-memory)

The index can point to separate topic files. An entry such as “Production sign-off → release-owner.md” gives the next session a clue. Claude can use its ordinary file tools to read the current contact and conditions. When it writes a memory file that starts with YAML frontmatter, the CLI records the write time in a `modified` field. The validity of an older decision still requires checking. A topic file with no index entry is harder to discover. Putting the entire handoff procedure in the index consumes space that could have pointed to other topics.

On startup the index contributes **its first 200 lines or 25 KB, whichever comes first**. A write and a later load have different boundaries. The documentation says an oversized write still reaches disk, and the tool tells Claude to shorten the index. The next startup loads only the bounded prefix. That particular limit applies to the auto-memory index. A `CLAUDE.md` read at startup has a separate whole-file limit. Up to 4 MiB loads in full. A larger file is skipped entirely. [Startup limits and oversized writes](https://code.claude.com/docs/en/memory#how-it-works)

Sharing across branches has a cost. If Claude writes “the billing module is being migrated” as a repository-wide fact, a worktree maintaining the previous release can see it too. For facts that depend on a code version, I would inspect the actual branch. A note about a human decision can name the affected branches, the date and when the decision expires. This consequence follows from the documented scope. My experiment did not ask a model to reason across branches.

### In-session writes, extraction and dreams

A correction can reach a topic file before the conversation ends. Release notes give two useful boundaries for a separate memory-extraction path. Version 2.1.77 fixed a race between extraction writes and the main transcript that could drop recent messages on resume. In v2.1.273, a fix extended `permissions.blockReadsOutsideWorkingDirectories` to extraction when repository settings supplied the memory directory. Extraction has its own read and write timing. A change to `MEMORY.md` alone cannot identify which invocation wrote it. [Transcript race fix](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L8904) · [Memory extraction and directory permissions](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L4404)

Local auto memory can be disabled with `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. In a background session, or one started by another Claude Code session, `/memory` can turn it off but cannot re-enable it. The official Help Center also lists `/dream` in its CLI reference table. The public command reference gives no fixed schedule for local consolidation. Check what the interactive session actually offers with `/help`. The four runs below started with prewritten memory files and did not trigger or verify background extraction or consolidation. [Auto-memory settings](https://code.claude.com/docs/en/memory#enable-or-disable-auto-memory) · [CLI Help Center](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) · [Command reference](https://code.claude.com/docs/en/commands)

Anthropic documents a specific protocol for the **Managed Agents Dreams API**. An asynchronous job takes an existing memory store and one to one hundred sessions. It writes a separate output store that the application can review before adopting. The input remains available. Anthropic’s CL-Bench database experiment illustrates what can go wrong. One model recorded untested guesses, while others used grader feedback to correct and accumulate rules. A completed job shows that some material was processed. Whether it improved our release procedure is a question for the next set of release notes. These are results from the managed service. They do not establish a scheduling interval, a trigger threshold or an overwrite policy for the local terminal. [Dreams API](https://platform.claude.com/docs/en/managed-agents/dreams) · [Anthropic’s memory research](https://www.anthropic.com/research/components-of-agent-memory)

## A skill’s description, body and permissions have different lifetimes

A skill description tells the model when to open it. “Draft release notes, comparing compatibility changes and migration steps” communicates more than “release tool.” The body supplies the procedure. References and scripts can stay on disk until needed. Anthropic’s engineering article describes these three levels of disclosure. Simon Willison tried the official Slack GIF skill. Its validator could inspect the finished dimensions directly, giving the model a check it could actually run. The two accounts explain the design. The current product behavior below comes from the documentation and the CLI trace. [Anthropic engineering article](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [Willison’s GIF experiment](https://simonwillison.net/2025/Oct/16/claude-skills/)

| Skill configuration | At the start of an ordinary conversation | Who can invoke it directly |
|---|---|---|
| Default | Ordinarily advertises the description, loads the body on demand | User and model |
| `disable-model-invocation: true` | Withholds even the description from the model | The user can explicitly type `/name` |
| `user-invocable: false` | Can advertise the description | The model can choose it. The user cannot invoke it through `/name` |

With many skills, discovery also depends on the catalog budget. The current documentation assigns it 1% of the model’s context window. Names remain visible, but descriptions can be omitted, starting with less frequently used entries. An explicit invocation that loads the right procedure tells us little about whether the model can discover it from an ordinary request. [Invocation controls](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill) · [Catalog budget](https://code.claude.com/docs/en/skills#skill-descriptions-are-cut-short)

Invocation adds the rendered body to the conversation as a message. Later turns can still see it. Edits on disk can refresh the catalog during the session, but an older message retains its original text. Invoking again produces a short reminder if the rendered result matches, or appends the new body if it changed. Tool pre-approval from `allowed-tools` expires when the next user message starts a new turn. **A procedure can therefore remain in the conversation after its tool approval has expired.** [Editing during a session](https://code.claude.com/docs/en/skills#live-change-detection) · [Skill content lifecycle](https://code.claude.com/docs/en/skills#skill-content-lifecycle) · [Tool pre-approval](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill)

## Compaction, delegation and improvement

A long release can cross a context compaction. The root `CLAUDE.md` is re-read from disk. Nested instructions load again when accessed. Invoked skills follow another rule. After the summary, Claude Code tries to reattach the most recent invocation of each skill, keeping the first 5,000 tokens per skill and 25,000 overall, with recent invocations first. A critical check at the end of a long skill can be available on first use and absent after compaction. These budgets are documented as of the date above. The model-free experiment below did not trigger compaction. [Project instructions after compaction](https://code.claude.com/docs/en/memory#instructions-seem-lost-after-/compact) · [Skill reattachment budget](https://code.claude.com/docs/en/skills#skill-content-lifecycle)

Delegation changes who reads the information. An ordinary subagent does not automatically load the main conversation’s auto memory. A fork can inherit the parent’s conversation and system prompt. A dedicated reviewer with `memory: project` can keep its own notes in `.claude/agent-memory/<name>/` in the repository. With `local` the corresponding directory is `.claude/agent-memory-local/<name>/`, for machine-local records. Explicitly preloading a skill into a subagent also supplies its full body at startup. A trace of a normal main conversation is a poor guide to that case. [Subagent persistent memory](https://code.claude.com/docs/en/sub-agents#enable-persistent-memory) · [Preloading skills](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)

“Learned” can mean two observable changes. First, there is a new piece of information that a later request can retrieve. A request trace can show that. Second, future tasks of this type produce better results. That takes a comparison. The public `skill-creator` workflow tests the description with neighboring prompts that should and should not trigger the skill, then evaluates output against task assertions. The trigger evaluator inspects actual tool events. It accepts a call to the target skill or a read of the matching file. Merely mentioning the skill in a response does not count. A new skill gets a no-skill baseline. A revision is compared with its previous version. “Draft notes for this release” should trigger our skill. “Explain why this release was rolled back” might not. Neither verdict tells us whether generated notes actually list the breaking changes. This is a human-initiated improvement workflow. A successful file write alone establishes neither a skill revision nor an update to model weights. [Pinned evaluation workflow](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/SKILL.md#L145-L201) · [Trigger-evaluation implementation](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/scripts/run_eval.py#L132-L168)

## Experiment: inspect the CLI’s actual requests

I created an isolated config directory and a temporary Git repository, put unique markers in each input file and let the real 2.1.327 CLI assemble requests. A loopback server prints only the known markers and a fragment of the truncation warning. It returns a fixed `OK` for the first three invocations. For the fourth, it first asks for a specific `Read`, then returns `OK`. This observes what the client discovers, reads and sends. With no real model behind the endpoint, the experiment cannot measure spontaneous skill selection, memory writing or instruction following.

| Input to the real CLI | First request | Subsequent observation |
|---|---|---|
| `ordinary prompt` | Root `CLAUDE.md`, index and ordinary skill description present. Topic body, both skill bodies and manual-only description absent | Ends after the fixed reply |
| `/release-card` | Ordinary skill body appears | Its description remains in the catalog |
| `/release-manual` | Manual-only skill body appears | Its description is still absent from the catalog |
| `READ_PROBE` | Nested instructions, path rule and test file contents all absent | The second request contains all three after the CLI executes `Read module/a.py` |

I expected a full-text search to settle the index boundary. A 202-line index, well under 25 KB, showed why that can mislead. Searching for the marker on line 201 would give the wrong answer because a warning quotes the first omitted line. To test what loaded, inspect where the match occurred. This run did not exercise an oversized write.

```python title="probe.py"
"""Python 3.9+, Git and Claude Code 2.1.327. No accounts or third-party packages."""
import json
import os
import shutil
import subprocess
import tempfile
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from pathlib import Path
from threading import Thread

base = Path(tempfile.mkdtemp(prefix="cc-context-"))
repo = base / "repo"
config = base / "config"
memory = base / "memory"

def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8")

def skill(name, manual=False):
    front = "disable-model-invocation: true\n" if manual else ""
    write(repo / ".claude/skills" / name / "SKILL.md",
          f"---\nname: {name}\ndescription: DESC_{name}_TAG\n{front}---\nBODY_{name}_TAG\n")

write(repo / "CLAUDE.md", "ROOT_TAG")
write(repo / "AGENTS.md", "SECOND_GUIDE_TAG")
write(repo / "module/CLAUDE.md", "NESTED_TAG")
write(repo / "module/a.py", "FILE_TAG = 1")
write(repo / ".claude/rules/module.md", '---\npaths: ["module/**/*.py"]\n---\nRULE_TAG')
write(config / "settings.json", json.dumps({"autoMemoryDirectory": str(memory), "autoMemoryEnabled": True}))
write(memory / "MEMORY.md", "\n".join(["INDEX_TAG"] + [f"entry {i}" for i in range(2, 200)]
                                     + ["LINE200_TAG", "LINE201_TAG", "LINE202_TAG"]))
write(memory / "topic.md", "TOPIC_TAG")
skill("release-card")
skill("release-manual", manual=True)
subprocess.run(["git", "init", "-q", str(repo)], check=True)

markers = ("ROOT", "SECOND_GUIDE", "NESTED", "RULE", "FILE", "INDEX", "LINE200",
           "LINE201", "LINE202", "TOPIC", "DESC_release-card", "BODY_release-card",
           "DESC_release-manual", "BODY_release-manual")

class Receiver(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def do_POST(self):
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        if self.path.split("?")[0] != "/v1/messages":
            self.send_error(404)
            return
        text = json.dumps(req, ensure_ascii=False)
        print(" ", " ".join(k for k in markers if k + "_TAG" in text), flush=True)
        if "LINE201_TAG" in text:
            offset = text.index("LINE201_TAG")
            print("  ...", text[offset-64:offset+17], "...")
        read = "READ_PROBE" in text and "tool_result" not in json.dumps(req["messages"])
        block = {"type": "text", "text": ""}
        delta = {"type": "text_delta", "text": "OK"}
        if read:
            block = {"type": "tool_use", "name": "Read", "id": "toolu_probe", "input": {}}
            delta = {"type": "input_json_delta", "partial_json": json.dumps({"file_path": str(repo / "module/a.py")})}
        msg = {"id": "msg_probe", "role": "assistant", "type": "message", "model": req["model"],
               "content": [], "stop_reason": None, "stop_sequence": None,
               "usage": {"input_tokens": 1, "output_tokens": 0}}
        events = [("message_start", {"message": msg}), ("content_block_start", {"index": 0, "content_block": block}),
                  ("content_block_delta", {"index": 0, "delta": delta}), ("content_block_stop", {"index": 0}),
                  ("message_delta", {"delta": {"stop_reason": "tool_use" if read else "end_turn", "stop_sequence": None},
                                     "usage": {"output_tokens": 1}}), ("message_stop", {})]
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.end_headers()
        for name, fields in events:
            payload = json.dumps({"type": name, **fields})
            self.wfile.write(f"event: {name}\ndata: {payload}\n\n".encode())

server = ThreadingHTTPServer(("127.0.0.1", 0), Receiver)
Thread(target=server.serve_forever, daemon=True).start()
# Keep OS prerequisites, omit any existing provider credentials and custom settings.
keep = {"PATH", "PATHEXT", "SYSTEMROOT", "WINDIR", "COMSPEC", "TEMP", "TMP", "LANG",
        "PROGRAMDATA", "PROGRAMFILES", "PROGRAMFILES(X86)", "PROCESSOR_ARCHITECTURE"}
env = {k: v for k, v in os.environ.items() if k.upper() in keep}
home = base / "home"
home.mkdir()
env.update(HOME=str(home), USERPROFILE=str(home), LOCALAPPDATA=str(home / "Local"),
           APPDATA=str(home / "Roaming"), CLAUDE_CONFIG_DIR=str(config),
           ANTHROPIC_BASE_URL=f"http://127.0.0.1:{server.server_port}", ANTHROPIC_API_KEY="local-fixture",
           CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC="1", DISABLE_AUTOUPDATER="1", NO_PROXY="127.0.0.1")
cli = shutil.which("claude.exe") or shutil.which("claude")
try:
    for prompt in ["ordinary prompt", "/release-card", "/release-manual", "READ_PROBE"]:
        print(prompt, flush=True)
        subprocess.run([cli, "-p", "--no-session-persistence", "--model", "sonnet", "--strict-mcp-config",
                        "--tools", "Read,Skill", "--allowedTools", "Read", "--", prompt],
                       cwd=repo, env=env, stdin=subprocess.DEVNULL, check=True)
finally:
    server.shutdown()
print("Fixture directory:", base)
```
