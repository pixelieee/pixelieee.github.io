**The short version:** Claude Code splits durable knowledge into three tracks—team-reviewed project rules, repo-shared local auto memory, and on-demand skills—loading bounded prefixes at startup without rewriting the active turn's snapshot, while a single empty directory is enough to cut off a linked worktree's skill fallback.

By the end you will be able to answer four questions:

1. Right after `Write` and `Edit` succeed on auto memory, why does the next outgoing request still carry the **old index** in its startup attachment?
2. When `MEMORY.md` reaches 202 lines, how can the disk write succeed, `tool_result` report no error, and the next request still include an "Error" warning?
3. Why does a Git linked worktree inherit the repo's auto-memory index automatically yet suddenly lose main-checkout skills the moment an **empty directory** exists?
4. Why can an invoked skill's instructions stay visible in later turns after its `allowed-tools` pre-approval has already expired?

This note traces the installed **Claude Code 2.1.327** against a local loopback endpoint (scripted tool calls executed by the real CLI—no API key or model predictions), with official docs verified on November 18, 2026. [Pinned release changelog](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L3)

## The big picture: three tracks and the first request

Deciding where a piece of knowledge belongs in Claude Code starts with **who owns it**—team conventions live in Git, local corrections go to auto memory, and multi-step procedures live in skills:

<FigClaudeArch lang="en" />

| What should survive | Where it lives & who maintains it | When it enters context next time |
|---|---|---|
| Repo-wide conventions (e.g., on-call sign-off) | Root `CLAUDE.md` / `CLAUDE.local.md`, reviewed in Git | Concatenated from ancestors down to `cwd` at startup as a user message after the system prompt |
| Rules scoped to part of the tree (`module/`) | `.claude/rules/` (with `paths`) or nested `CLAUDE.md` | Absent on request 1; injected only after a real file access matches |
| Local corrections and preferences | `~/.claude/projects/<project>/memory/MEMORY.md` + topic files | First **200 lines or 25 KB** of index at startup; topic bodies wait for `Read` |
| Reusable steps, checklists, templates | `.claude/skills/<name>/SKILL.md` + attachments | Name & description in a 1% catalog budget; body loads on invocation or `/name` |
| Last command run and its logs | Conversation transcript | Available when resuming that session; omitted from fresh sessions |

Two loading rules frequently surprise teams:
- **Scoped rules wait for file access**: with `.claude/rules/module.md` (`paths: ["module/**/*.py"]`) and `module/CLAUDE.md` present, both markers were absent from request 1. After a real CLI `Read` of `module/a.py`, the file, nested instructions, and path rule all arrived together in the next request. Use the `InstructionsLoaded` hook (`session_start`, `nested_traversal`, `path_glob_match`) to diagnose which path fired. [Instruction loading order](https://code.claude.com/docs/en/memory#how-claude-md-files-load) · [Path-specific rules](https://code.claude.com/docs/en/memory#path-specific-rules) · [InstructionsLoaded hook](https://code.claude.com/docs/en/hooks#instructionsloaded)
- **`CLAUDE.md` suppresses `AGENTS.md` fallback**: by default (direct `AGENTS.md` support arrived in v2.1.277), any project-side `CLAUDE.md` or `CLAUDE.local.md` in or above `cwd` prevents fallback to `AGENTS.md`. With both files at root, only `CLAUDE.md` reached request 1; teams maintaining both must configure joint loading or import via `@AGENTS.md`. [AGENTS.md selection rules](https://code.claude.com/docs/en/memory#agents-md)

Avoid duplicating commands that already live in a `Makefile`—record non-obvious conventions in rules, keep procedures in skills. [Project memory](https://code.claude.com/docs/en/memory) · [Where skills live](https://code.claude.com/docs/en/skills#where-skills-live)

## One edit, three requests: why startup snapshots stay put

In an isolated config directory, I initialized a Git repo whose `MEMORY.md` started with `INDEX_BEFORE`. The loopback endpoint had the real CLI read the index, write `release-owner.md` containing `DETAIL_QUARTZ`, and `Edit` the index to `INDEX_AFTER`; then I launched a fresh process (`--no-session-persistence`) in the same repo and issued a `Read`.

<FigClaudeTrace lang="en" />

Searching the raw text of request 4 finds both `INDEX_BEFORE` and `INDEX_AFTER`, which easily misleads you into thinking the index reloaded. Splitting by message slot shows the truth: the startup `user` attachment **still holds the old index**, while the assistant's own `Edit` call carries `new_string`. Within the turn, tool history bridges the gap without mutating the startup prefix. Restarting discards tool history and loads `INDEX_AFTER` from disk—yet `DETAIL_QUARTZ` remains absent until `Read` returns it as a `tool_result`:

```json title="Fresh process · request 2 · adjacent message blocks (abridged)"
[
  {
    "role": "assistant",
    "content": [{
      "type": "tool_use", "id": "toolu_1", "name": "Read",
      "input": {"file_path": "…/release-owner.md"}
    }]
  },
  {
    "role": "user",
    "content": [{
      "type": "tool_result", "tool_use_id": "toolu_1",
      "content": "…The on-call handoff code is DETAIL_QUARTZ. …"
    }]
  }
]
```

Inspecting `release-owner.md` on disk also revealed an added `modified` timestamp beyond the YAML fields passed to `Write`—useful for knowing when a note was written, though not whether it is still accurate today. [How auto memory is read and written](https://code.claude.com/docs/en/memory#how-it-works)

## Oversized writes and background paths: success plus an Error

Auto memory is on by default for local terminal sessions under `~/.claude/projects/<project>/memory/`. **Worktrees of the same repository on one machine share auto memory**, and memory files survive session-history expiration; inspect, edit, or toggle via `/memory`. [Write scope and storage](https://code.claude.com/docs/en/memory#auto-memory)

### The 202-line test: three checks, three outcomes

After reading `MEMORY.md`, the real CLI wrote 202 lines ending in `EDGE_200`, `EDGE_201`, and `EDGE_202` (small enough to trip the 200-line limit before 25 KB):

| Where I checked | Actual 2.1.327 outcome |
|---|---|
| `MEMORY.md` on disk | All 202 lines persisted, including `EDGE_202` |
| `user.tool_result` to assistant | Reported update success; **no** `is_error` flag |
| Separate `system` message in next request | Tagged `PostToolUse:Write`, warned that the read limit was exceeded and asked to move details into topic files |

All three hold at once: `Write` finished saving the file, while `PostToolUse` enforces **how much the next startup can load** (first 200 lines or 25 KB, whichever hits first, separate from `CLAUDE.md` caps). Checking only `is_error` misses the cleanup prompt; retrying the same write on seeing "Error" just rewrites the oversized index. [Index write and load limits](https://code.claude.com/docs/en/memory#how-it-works)

Restarting exposes a subtler search trap:

<FigClaudeMemory lang="en" />

Because the startup truncation warning quotes the first omitted line, a full-payload grep for `EDGE_201` still hits—even though `EDGE_200` is the last line in the actual index body, `EDGE_201` appears **only inside the warning quote**, and `EDGE_202` is completely gone.

### Foreground writes, background extraction, and dreams

Beyond direct foreground tool calls, Claude Code also runs a separate extraction path: public release notes document a v2.1.77 fix for a race between extraction writes and the main transcript, and a v2.1.273 fix enforcing `permissions.blockReadsOutsideWorkingDirectories` on repo-configured memory paths during extraction—meaning a change on disk alone cannot identify which path wrote it. [Transcript race fix](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L8904) · [Extraction & directory permissions](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L4404)

Disable auto memory locally via `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (in background or nested sessions, `/memory` can turn it off but not back on). While the Help Center lists `/dream`, the public command reference promises no fixed local schedule—check `/help` in your active CLI. Separately, Anthropic's **Managed Agents Dreams API** defines an explicit async two-store protocol (1–100 sessions distilled into a new reviewable store), though managed-service guarantees cannot be extrapolated to local CLI cadence or overwrite policies. [Auto-memory settings](https://code.claude.com/docs/en/memory#enable-or-disable-auto-memory) · [CLI Help Center](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) · [Dreams API](https://platform.claude.com/docs/en/managed-agents/dreams)

## Why one empty directory cuts off linked-worktree skills

With an uncommitted `release-card` skill added to the main checkout *after* `git worktree add`, I launched three fresh processes in the linked worktree using the exact same prompt and CLI config—changing only `.claude/skills/` in the worktree root:

<FigClaudeScope lang="en" />

An unrelated Git repo run under the exact same CLI config contained neither `INDEX_AFTER` nor either skill description, ruling out config-directory leakage.

The split is sharp: auto memory resolves to the same repo-scoped machine directory across worktrees, whereas project skills (since v2.1.277) fall back to the main checkout **only when `.claude/skills/` is absent—an empty directory switches fallback off immediately**. Adding a branch's first local skill can silently hide main-checkout procedures while shared memory entries remain visible. [What worktrees share](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout) · [Project skill discovery](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)

## Skill descriptions, bodies, and permissions expire separately

Skills follow three-level progressive disclosure: catalog descriptions first, full body on invocation, supporting scripts on demand. With many skills, the catalog budget is **1% of the context window**—names remain visible, but descriptions drop starting from less-used entries. [Anthropic engineering article](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [Catalog budget](https://code.claude.com/docs/en/skills#skill-descriptions-are-cut-short)

| Skill config | Startup catalog | Who can invoke directly |
|---|---|---|
| Default | Advertises description; body on demand | User and model |
| `disable-model-invocation: true` | **Withholds even the description** | User only via `/name` |
| `user-invocable: false` | Advertises description | Model only; user cannot run `/name` |

Three independent lifetimes govern what happens once invoked: [Invocation controls](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill) · [Skill content lifecycle](https://code.claude.com/docs/en/skills#skill-content-lifecycle) · [Tool pre-approval](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill)

1. **Duplicate invocations deduplicate; manual-only skills block tool calls**: invoking `Skill({"skill":"release-card"})` twice produced two "launching" tool results, yet the body appeared only **once**—followed on the second call by a short "already loaded and unchanged" note. Calling `Skill({"skill":"release-manual"})` returned `is_error: true` with no body, while typing `/release-manual` injected it immediately—knowing a skill's name does not grant the model permission to run it.
2. **`allowed-tools` expires on the next user message**: the injected procedure remains in conversation history, but its tool pre-approval ends when the next user turn starts—**the text stays longer than the permission**.
3. **Compaction and subagents change who sees what**: after `/compact`, root `CLAUDE.md` reloads from disk and nested rules return to on-demand, while invoked skills reattach most-recent-first up to **5,000 tokens each and 25,000 total**—critical checks at the tail of a long skill can vanish mid-session. Ordinary subagents do not inherit main auto memory (forks do); dedicated subagents can opt into `memory: project` (`.claude/agent-memory/<name>/`) or `local`, and preloaded skills inject their full body at startup. [Instructions after compaction](https://code.claude.com/docs/en/memory#instructions-seem-lost-after-/compact) · [Subagent persistent memory](https://code.claude.com/docs/en/sub-agents#enable-persistent-memory) · [Preloading skills](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)

## What skill-creator measures, and four pitfalls to watch

A skill can score 100% on trigger evals and still miss breaking changes in real release notes. Anthropic's public `skill-creator` evaluator explains why: it writes **the description under test plus a placeholder body** to a temporary command file and checks whether `claude -p` calls `Skill` or `Read` with that generated name. [Pinned source · L51–75](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/scripts/run_eval.py#L51-L75) · [Trigger detection](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/scripts/run_eval.py#L132-L168)

```python title="run_eval.py · L51–54"
unique_id = uuid.uuid4().hex[:8]
clean_name = f"{skill_name}-skill-{unique_id}"
project_commands_dir = Path(project_root) / ".claude" / "commands"
command_file = project_commands_dir / f"{clean_name}.md"
```

That measures **discoverability and false-positive rate**, not whether the real procedure produces better outputs—which requires separate output assertions against a no-skill or prior-version baseline. [Output evaluation and baselines](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/SKILL.md#L145-L201)

### Four practical takeaways

1. **Inspect payload slots, never whole-request greps**: mid-turn `Edit` arguments put old and new index markers in the same request, and 200-line truncation warnings quote line 201 even when it was dropped from the body.
2. **Enforce team policies in `CLAUDE.md` + CI, not auto memory**: auto memory is machine-local and capped at 200 lines / 25 KB, and prompt ordering in `CLAUDE.md` is no substitute for CI gates.
3. **Front-load critical checks in long skills**: post-compaction reattachment caps each skill at its first 5,000 tokens.
4. **Treat `.claude/skills/` in linked worktrees as all-or-nothing**: even an empty directory disables fallback to the main checkout.

## Answering the four opening questions

1. **Right after `Write` and `Edit` succeed on auto memory, why does the next request still carry the old index in its startup attachment?** The startup `MEMORY.md` block is loaded once at session start; mid-turn edits update disk and appear in tool history without mutating the startup prefix, reloading into the startup slot only in a fresh process (while topic bodies still wait for `Read`).
2. **When `MEMORY.md` hits 202 lines, how can disk write succeed, `tool_result` report no error, and the next request still warn with an Error?** `Write` reports file-system success, whereas a separate `PostToolUse:Write` `system` message checks the next startup's 200-line / 25 KB load cap; on restart, the truncation warning also quotes line 201 even though it was dropped from the index body.
3. **Why does a linked worktree inherit auto memory automatically yet lose main-checkout skills as soon as an empty directory exists?** Worktrees of one repo share the same machine-local auto-memory folder, but project skill discovery (since v2.1.277) falls back to the main checkout only when `.claude/skills/` is absent—even an empty local directory switches fallback off.
4. **Why do a skill's instructions remain in later turns after `allowed-tools` has expired?** Invoking a skill injects its body into conversation messages (and reattaches up to 5,000 tokens after compaction), whereas `allowed-tools` pre-approval is strictly turn-scoped and expires on the next user message.
