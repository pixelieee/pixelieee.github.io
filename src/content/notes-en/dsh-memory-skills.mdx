“Check the artifact before shipping” can live in a DSH conversation, a project's `AGENTS.md` or a callable skill. All three preserve text. Different sessions can carry it forward. DeepSeek Harness composes plugins through Cordis. To establish what a deployment remembers, identify its plugins, then follow the **write, the durable record and the next request**. This note pins the official repository at `2e39e70` and identifies optional components where they matter.

## How can a second repository find the first release record?

I started the reference memory server specified by DSH in a temporary project A. I gave `release` the observation `refresh atlas` and a `requires` edge to another entity, `manifest`. Then I stopped the process, changed to project B, and started a new server against the same graph file. A search for `ATLAS` returned `release`. With the directory and query program held constant, restarting against a fresh graph produced an empty result.

The experimental DSH session-query tool answers a different scope question. To read another session, it filters by **both the target ID and the caller's working directory** and checks the observed session header. Two directories in the same Git repository do not gain a shared lookup scope from that relationship. What explained the cross-project result above was two server processes opening the same graph. For a demonstration of cross-project recall, the first piece of evidence I would ask for is the **name of the tool that returned the record**. <Src {...source} p="packages/experimental/tool-session-query/src/workspace-access.ts" l="74-112" /> <Src {...source} p="apps/cli/config/examples/mcp-memory/mcp-reference-memory.cordis.yml" l="1-13" />

Three changes trace the different readers below: a session acquires a checkpoint, a skill file changes, and a memory service restarts. The first two follow the pinned DSH source. The third uses the independently versioned service in its sample configuration. The graph writes were explicit protocol calls.

## Four destinations for the same lesson

| Destination | Owner and scope | How it reaches a later request |
|---|---|---|
| Session events and checkpoints | Session appends events. The persistence provider stores the log. | Continuing or resuming the session reconstructs its effective message sequence. |
| User and project instructions | `agent-instructions` reads files from the user roots and project hierarchy. | The first request gets a baseline. Relevant file activity or a working-directory change can produce updates. |
| Skills | `ctx.skills` merges providers. Filesystem-backed procedures live in directories and files. | The model gets a callable catalog, then loads the body. Explicit user invocation takes a separate route. |
| External long-term memory | The selected MCP service owns storage, search and write semantics. | The service must be installed, enabled and exposed through tools that a caller actually uses. |

Two kinds of lookup are easy to confuse. `ctx.sessionQuery` serves an application's session history. A third-party memory MCP configuration connects a separately maintained dataset. Finding a fact in the former tells us nothing about whether it was written into the latter. <Src {...source} p="packages/session-query/session-query/README.md" l="28-49" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="5-21" />

## Compaction replaces part of the model's view

DSH offers distinct reads of the log and the current sequence of model-visible messages, called the *surface*. The JSONL backend appends logical events per session and can store them as checksummed Zstandard frames by default. An optional SQLite persistence backend also exists. `readSession` returns replay-validated raw events. `readSurface` returns the current sequence. History queries prefer a live session and can read a persisted copy without reviving it. <Src {...source} p="docs/subsystems/persistence.md" l="341-346" /> <Src {...source} p="packages/session-query/session-query/README.md" l="9-13" /> <Src {...source} p="packages/session-query/session-query/README.md" l="36-49" />

The basic compaction backend checks pressure at step boundaries and has a recovery path for a provider-confirmed overflow. Selection retains an appropriate recent tail and avoids splitting a tool call from its result. A `compaction/summary` event records the summary and the events it shadows. A subsequent message applies the replacement and links back to the summary and its source events. <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="155-182" /> <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="228-251" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="115-156" />

```ts title="compaction-basic/src/region.ts · 507–510"
  session.append('user/message', checkpointMessage, {
    surfaceOp: { op: 'replace', startSeq: start, endSeq: end },
    sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
  })
```

`startSeq` and `endSeq` are event IDs. The backend locates each ID on the current surface and slices the inclusive interval **between those positions**. After an earlier replacement, selecting all log rows whose numbers fall between the endpoints can collect the wrong material. The transaction writes a start marker, records the summary and replacement, then closes. A framed summary that fails to shrink the selected content is an error. Recovery can distinguish an attempted compaction from a committed replacement. <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="200-250" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="411-426" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="492-510" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="337-358" />

**Can a new session look up an old one?** The experimental `tool-session-query` consumer is opt-in. Its five read-only tools can find events, read source records and trace relationships. Cross-session access requires an exact match between the target and caller's `cwd`. A caller with no `cwd` can inspect only itself. The SQLite query backend can search current, shadowed and log-only material by default. ### A new message arrives while the summary is being written

The normal follow-up path has a queue. An upstream case pauses manual compaction while it awaits a summary and submits a second question via `agent.followup`. The next turn starts after the compaction end and flush. Its model request contains the checkpoint followed by the new question. The stability check below addresses the separate case where the runtime surface actually changes during summarization. <Src {...source} p="packages/compaction/compaction-basic/tests/manual-compaction.spec.ts" l="266-308" />

Summarization waits on a model call. Suppose a user message arrives at the end of the surface during that wait. Can the summary still commit? The caller selects a **stability check**. Automatic compaction requires the whole measured surface to match before committing in the current turn. A manual selection requires the chosen span to remain contiguous and valid, with the same events and measurements. An append outside that span can survive alongside the replacement. Both modes use the same commit function. <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="398-415" /> <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="428-454" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="431-469" />

The **stage of failure** matters too. If the framed summary costs at least as much as the selected region, it fails before replacement. After validation, the code appends the summary, the replacement message and the closing event. Only then does it call the optional persistence flush. A flush failure surfaces as a `persistence` error even though an in-memory reader can already see the new checkpoint. The evidence that distinguishes these cases is the current surface, the closing event and the result of a cold read after restart. <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="228-270" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="411-425" />

## Workspace rules still have to fit

The base composition enables `agent-instructions`. For the first request it reads user roots (`$DSH_HOME` and the shared agents root), then the project chain from its root down to the working directory. `AGENTS.md`, `CLAUDE.md` and their `.local.md` variants can contribute. Files with identical trimmed content in one candidate group are presented once. The base budget is 65,536 **bytes per chain**. A file's presence does not guarantee that every byte of it reaches the request. <Src {...source} p="packages/context/agent-instructions/README.md" l="27-44" /> <Src {...source} p="packages/context/agent-instructions/src/files.ts" l="430-450" />

Successful relevant file operations can introduce a deeper directory's rule, replace an earlier rule or generate a removal notice for the next request. Resuming reconciles the baseline. A save in an external editor is not an immediate message in a running chat. The plugin considers whether a tool operation succeeded, waits for pending projections and composes the instructions at a step that actually proceeds. <Src {...source} p="packages/context/agent-instructions/README.md" l="9-13" /> <Src {...source} p="packages/context/agent-instructions/src/index.ts" l="330-369" />

## A skill passes three selection points

The registry first picks a winner for each name **within each scope layer**, then merges layers. A layer closer to the agent can override a more distant one. Numeric rank settles competition within a layer. The filesystem provider ranks project `.dsh/skills` at 100, project `.agents/skills` at 200, custom directories at 300, user DSH at 400, user agents at 500 and bundled skills at 600. Treating these as a process-wide ordering would give the wrong answer for a same-name provider mounted by an agent preset in its own layer. <Src {...source} p="packages/skill/skill/src/index.ts" l="553-586" /> <Src {...source} p="packages/skill/skill/src/index.ts" l="810-815" /> <Src {...source} p="packages/skill/skill-filesystem/README.md" l="44-58" />

Before a step, the tool plugin requests a snapshot for the current agent scope and working directory. It filters model-invocable entries and publishes **names and descriptions** in a message carrying source metadata. A `skill` call checks model invocation policy both before and after loading the definition. The filesystem provider rereads the body. An explicit `/<name>` in an actual user message takes a different route: it checks `userInvocable` and appends the instructions to the step. These independent policy bits let an author require an explicit user gesture for a skill. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="133-159" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="166-207" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="packages/skill/skill-filesystem/src/index.ts" l="212-234" />

Why can editing the body leave the catalog quiet? Its digest includes the names, descriptions and completeness of discovery. Changing only a procedure can affect the next load without changing what the catalog advertises. Editing a description, deleting an entry or recovering from partial discovery can instead produce a replacement catalog. Even an **empty catalog** has two meanings: a successful discovery found none, or discovery could not confirm any this time. An incomplete observation is not cached as authoritative and old catalog entries are no longer a license to call those names. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="290-329" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="344-356" /> <Src {...source} p="docs/subsystems/skills.md" l="11-17" /> <Src {...source} p="docs/subsystems/skills.md" l="77-83" />

### The files did not change. Why did the catalog get published again?

Publication compares two states. One comes from current discovery: names and rendered descriptions contribute to a digest, with an extra bit for an incomplete observation. The other is the last structured catalog **still visible to the model**. The plugin walks backward through session events for readable catalog data, then checks whether the event sequence number occurs in `surface.nodes`. File timestamps alone cannot explain what happens after compaction. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="344-355" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="380-399" />

### A provider goes away or changes during discovery

If a preferred source becomes unavailable, a lower-priority definition of the same name may win. Guidance limits the model to confirmed entries and records incomplete discovery. Even if the same names are present next time, recovering completeness changes the digest and clears the warning. This measures confidence in the current catalog. Identifying who authored a change takes separate evidence. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="290-329" /> <Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="363-402" />

A narrower race occurs when a provider invalidates the registry during a scan. The cache key includes the working directory, scope chain and revision. A revision change during discovery triggers one more collection. If that races too, the registry returns the observed entries as uncacheable. Loading a body also checks identity: if the loaded name differs from the candidate chosen earlier, the call returns no definition and invalidates the relevant registration's cache. A file being renamed cannot deliver instructions with a new identity under the old name. <Src {...source} p="packages/skill/skill/src/index.ts" l="24-28" /> <Src {...source} p="packages/skill/skill/src/index.ts" l="502-550" /> <Src {...source} p="packages/skill/skill/tests/skill.spec.ts" l="796-864" />

## Who owns an external memory write?

The official guide has three default-off reference configurations: Memorix, MCP Reference Memory and Engram. DSH launches an installed stdio process or connects to a running HTTP service, discovers its tools and makes them callable. The selected server owns indexing, project identity, migrations, conflict handling and forgetting policies. Enabling its tools does not establish that an ordinary chat message calls a writer. <Src {...source} p="docs/user/guide/mcp-memory.md" l="5-33" />

For Reference Memory, the example sets `MEMORY_FILE_PATH` to a local JSONL knowledge graph of entities, relations and observations. Search performs case-insensitive substring matching over entity names, types and observations. If a semantic paraphrase fails to retrieve a record, check whether a write tool ran, whether both processes target the same file and whether the literal search term occurs in an indexed field. <Src {...source} p="apps/cli/config/examples/mcp-memory/mcp-reference-memory.cordis.yml" l="1-13" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="48-59" />

### Does finding an edge also retrieve the neighbor's properties?

The opening experiment used `create_entities`, `create_relations`, `search_nodes` and `open_nodes`. Calling `create_entities` again for an existing `release` with a new observation, `SECOND_NOTE`, successfully returned an empty list of additions. Searching for that marker also returned nothing. Creation deduplicates by name; the operation for adding a fact to an existing entity is `add_observations`. Counting successful write calls would overstate how many facts the graph acquired. [Pinned server implementation](https://unpkg.com/@modelcontextprotocol/server-memory@2026.7.4/dist/index.js)

| Query in a fresh process | Entities returned | What the result establishes |
|---|---|---|
| Same graph, search `ATLAS` | `release` | The observation matches. An edge naming `manifest` is also returned. |
| Same graph, search `map` | None | A related word has no literal match in this fixture. |
| Same graph, open `manifest` | `manifest` | The neighbor's own observation, `owner: ci`, becomes available. |
| Same directory, read a different, empty graph | None | Starting a server and choosing which data file to open are separate decisions. |

The first search revealed the neighbor's name and the relationship. Its observations arrived only on the second tool call. That extra hop is what the model would need to answer who maintains the dependency. The probe speaks MCP over stdio directly to the server pinned by DSH's example. It covers writes, process exit, restart and reads. It does not measure DSH's tool selection or the likelihood of a model taking the second hop. ## Experiment: why can a 600-byte budget yield 879 bytes?

[Download the budget probe](/experiments/dsh-instruction-budget.mjs) into the pinned DSH checkout and run `node dsh-instruction-budget.mjs` with Node 22.23.1. One workspace dependency is resolved to source in the same checkout. The real renderer receives a 240-byte user rule, an 800-byte project-root rule and a 240-byte nested rule. The measurement includes the headings and omission notices delivered to the caller.

| Input and per-chain budget | Output bytes | Fully omitted | Truncated |
|---|---:|---|---|
| Project root and nested file, 600 | 600 | `AGENTS.md` | 186 body bytes retained from `app/AGENTS.md` |
| Add the user rule, 600 | 879 | `AGENTS.md` | The same 186 bytes of the nested file |
| All three, 2,000 | 1,659 | None | None |

The totals include headings and explanatory text. Adding the user file raised the total above 600 because the user and project chains each have a budget. It did not displace more of the nested rule. Within a single project chain the broader root file was omitted first, then the more specific file was truncated. When an instruction is missing, inspect the rendered omission and truncation records as well as the filesystem. <Src {...source} p="packages/context/agent-instructions/src/render.ts" l="363-420" /> <Src {...source} p="packages/context/agent-instructions/src/render.ts" l="427-480" />

## Where evolution actually happens

The pinned version shows three distinct changes: a session can acquire a checkpoint, a provider can expose an updated skill, and maintainers can revise and release a skill in response to a failure. The last has a documented example. The shipped Cordis plugin-development skill grew large enough for the standard preset's tool-result pruner to remove its middle. Maintainers moved recipes into `references/` and templates into `templates/`, and added tests for entry length and reference integrity. The failure, edit and acceptance condition are all identifiable. A maintainer owned the write. <Src {...source} p=".agents/notes/archived/architecture/2026-09-21-creator-skills-progressive-disclosure.md" l="8-26" />

The experimental `ralph` tool illustrates a different kind of iteration. When the user explicitly asks for fresh-agent rounds, each child starts with a fixed objective, a shared workspace and the previous child's bounded report. Parent chat and older child sessions are not seeded. A worker-reported completion ends the loop without independent verification. The files and the one-round handoff carry progress across attempts. They establish neither a revised Skill nor a measured improvement in the next task. <Src {...source} p="packages/experimental/tool-ralph/README.md" l="28-38" />

In the base composition, registry and consumer inspected here, I found no end-of-session worker that automatically distills ordinary conversations into skills, revises them and archives older versions by usage. A user-directed edit, a deployment-specific plugin or the selected external memory service can change that answer. <Infer lang="en" /> DSH makes it possible to identify which call, scope and material produced a change. The trade-off is that text seen once in a client reveals little about its visibility elsewhere. To establish cross-session reuse, inspect the **message actually delivered or tool result actually returned** in the new session. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="65-72" />

Hermes connects historical material to background review and file writes. DSH hot reload establishes that a reader can observe an edit. A claim about learning from history also needs the origin of that write. [Compare the Hermes implementation](/notes/hermes-memory-skills/#background-review-what-ties-the-three-together)
