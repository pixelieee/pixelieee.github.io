**The one-sentence version:** DeepSeek Harness composes session logging, instruction budgets, skills and external MCP memory as Cordis plugins; models see only a derived `surface` over an append-only log, compaction shadows spans without deleting history, and even skill catalog republication tracks what remains visible on `surface`. <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="492-510" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="344-355" />

By the end, four things should be clear:

1. Why can a second repository find a prior release record through MCP memory while DSH's own session-query tool refuses to cross directories?
2. How does compaction replace history without deleting log rows—and why do automatic and manual compaction disagree when a new message arrives mid-summary?
3. Why does a 600-byte per-chain budget produce 879 bytes once user rules are added?
4. Why does DSH republish the exact same skill catalog after compaction even though no skill file changed?

This note pins official commit `2e39e70` and flags optional default-off plugins explicitly.

## One map: four destinations for one lesson

Built on Cordis plugins, DSH has no monolithic built-in memory store. Answering "did it remember?" starts with knowing which plugins are enabled across four channels:

<FigDshArch lang="en" />

| Channel | Owner | How it reaches a future request |
|---|---|---|
| **Session events & checkpoints** | Session appends events; JSONL (Zstd) or SQLite persists them | Continuing or resuming derives the active message sequence from `surface` |
| **User & project instructions** | `agent-instructions` reads `$DSH_HOME` and project hierarchy | Baseline on turn 1; reconciled on relevant file operations or cwd changes |
| **Skills** | `ctx.skills` merges providers; files keep bodies on disk | Model sees a tagged catalog message, then reads bodies fresh on `skill` or `/<name>` |
| **External long-term memory** | Default-off MCP servers (e.g., Reference Memory) | Enabled server owns storage, retrieval and write semantics via MCP tools |

Two lookups sound similar and point to different datasets: `ctx.sessionQuery` reads **DSH's own session history**, whereas third-party memory MCP servers query **their own external database**. <Src {...source} p="packages/session-query/session-query/README.md" l="28-49" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="5-21" />

## Event log vs. surface: compaction shadows views, never deletes rows

DSH cleanly separates raw log events from the model-facing message sequence (`surface`): `readSession` returns replay-validated raw events while `readSurface` returns the visible view, preferring an active in-memory session and falling back to cold reads of checksummed Zstd JSONL or SQLite. <Src {...source} p="docs/subsystems/persistence.md" l="341-346" /> <Src {...source} p="packages/session-query/session-query/README.md" l="9-13" />

Compaction writes a `compaction/summary` event and then appends a checkpoint message carrying `surfaceOp: replace` to shadow the summarized span:

```ts title="packages/compaction/compaction-basic/src/region.ts · 507–510"
  session.append('user/message', checkpointMessage, {
    surfaceOp: { op: 'replace', startSeq: start, endSeq: end },
    sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
  })
```
<Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="492-510" />

Although `startSeq` and `endSeq` are event IDs, slicing locates them by **position on the current `surface`**—after an earlier replacement, a higher-numbered event can sit ahead of an older one:

<FigDshSurface lang="en" />

Two crisp engineering boundaries:
- **A new message arrives while summarizing**: normal follow-ups queue behind compaction, but if `surface` changes mid-call, **automatic compaction** demands the entire surface match its measurement, whereas **manual compaction** only checks that the selected span remains contiguous and unchanged—so appends outside that span survive alongside the checkpoint. <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="398-454" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="431-469" />
- **Failure stages matter**: a framed summary that fails to shrink the span errors before replacement; after validation, events append in memory before optional persistence flush—so a flush error surfaces as `persistence` even while an in-memory reader already sees the checkpoint. <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="228-270" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="337-358" />

Can a new session query an old one? The opt-in `tool-session-query` plugin provides five read-only tools that can search active, shadowed, and log-only events—but cross-session reads require an **exact `cwd` match**, so even two directories inside the same Git repo do not share access. <Src {...source} p="packages/experimental/tool-session-query/README.md" l="9-14" /> <Src {...source} p="packages/experimental/tool-session-query/src/workspace-access.ts" l="74-112" /> <Src {...source} p="packages/session-query/session-query-sqlite/README.md" l="59-69" />

## Workspace rules: two separate 64 KB budget chains

`agent-instructions` loads a user chain (`$DSH_HOME` and shared agents root) plus a project chain (repo root down to `cwd`), reading `AGENTS.md`, `CLAUDE.md` and `.local.md` (deduplicating identical trimmed content per group). <Src {...source} p="packages/context/agent-instructions/README.md" l="27-44" /> <Src {...source} p="packages/context/agent-instructions/src/files.ts" l="430-450" />

The budget is **65,536 bytes per chain**, not shared across both—and within a chain, the broader root file drops first before the more specific nested file truncates. Driving the real renderer with a 600-byte per-chain cap across a 240 B user rule, 800 B root rule and 240 B nested rule proves it:

| Input & per-chain budget | Output bytes | Fully omitted | Truncated |
|---|---:|---|---|
| Project root + nested, 600 each | 600 | root `AGENTS.md` | `app/AGENTS.md` keeps 186 body bytes |
| Add user rule, 600 each | **879** | root `AGENTS.md` | Nested still keeps 186 bytes |
| All three, 2,000 each | 1,659 | None | None |
<Src {...source} p="packages/context/agent-instructions/src/render.ts" l="363-480" />

External editor saves do not inject messages mid-chat, whereas successful in-session file tool calls reconcile deeper rules, replacements, or removal notices on the next step. <Src {...source} p="packages/context/agent-instructions/README.md" l="9-13" /> <Src {...source} p="packages/context/agent-instructions/src/index.ts" l="330-369" />

## Skills: layer beats rank, and catalog republication watches `surface`

DSH separates skill resolution into three crisp rules:

1. **Scope layer beats numeric rank**: closer scope layers override outer ones; numeric rank resolves ties only **within a layer** (project `.dsh/skills` 100 > project `.agents/skills` 200 > custom 300 > user DSH 400 > user agents 500 > bundled 600). <Src {...source} p="packages/skill/skill/src/index.ts" l="553-586" /> <Src {...source} p="packages/skill/skill-filesystem/README.md" l="44-58" />
2. **Independent model vs. user flags**: `tool-skill` publishes model-invocable names and descriptions as a tagged message and rereads disk bodies on `skill` calls; explicit `/<name>` user messages check `userInvocable` separately. <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="133-255" /> <Src {...source} p="packages/skill/skill-filesystem/src/index.ts" l="212-234" />
3. **Why an unchanged skill catalog republishes after compaction**: `tool-skill` compares the current discovery digest (names, descriptions, completeness—not bodies) against the **last catalog event still present in `surface.nodes`**. Editing only a body leaves the catalog silent; once a compaction checkpoint shadows that catalog event off `surface`, the very next step republishes the identical entries: <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="290-356" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="380-399" /> <Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="585-614" /> <Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="689-744" />

## External memory: shared graph files, substring search, and two traps

DSH ships three default-off reference MCP configs (Memorix, MCP Reference Memory, Engram): DSH starts or connects to the server and exposes its tools, while storage, deduplication and scope belong entirely to the server. <Src {...source} p="docs/user/guide/mcp-memory.md" l="5-33" /> <Src {...source} p="apps/cli/config/examples/mcp-memory/mcp-reference-memory.cordis.yml" l="1-13" />

Probing `@modelcontextprotocol/server-memory@2026.7.4` across two directories (write `release` with `refresh atlas` and a `requires` edge to `manifest` in project A → exit → restart in project B against the same graph file) exposes three crisp facts:

| Query in project B (new process) | Entities returned | What it reveals |
|---|---|---|
| Same graph, search `ATLAS` | `release` | Cross-repo recall comes from sharing `MEMORY_FILE_PATH`, yet **omits neighbor `manifest`'s observations** |
| Same graph, search `map` | None | Case-insensitive **literal substring match** only—no semantic search |
| Same graph, `open_nodes("manifest")` | `manifest` | A second tool hop is required to read the neighbor's `owner: ci` |
| Same dir, empty graph | None | Scope follows the graph file path, not the workspace directory |

One easy write trap: calling `create_entities` again for an existing `release` with `SECOND_NOTE` **succeeds with an empty list**—adding facts to an existing entity requires `add_observations`. [Pinned server source](https://unpkg.com/@modelcontextprotocol/server-memory@2026.7.4/dist/index.js)

## Gotchas & evolution boundaries

<Infer lang="en" /> Four practical takeaways from the code and probes above:

1. **No built-in post-turn curator**: hot reload proves a reader can see an edit, not that DSH automatically distills conversations into new skills.
2. **Check the tool name on any "cross-project memory" demo**: MCP servers sharing one graph file cross repos freely, whereas built-in `tool-session-query` enforces an exact `cwd` match.
3. **Finding a graph edge does not fetch neighbor properties**: `search_nodes` returns only the neighbor's name and relation; reading its observations takes an explicit `open_nodes` hop.
4. **Missing rules can be a budget cut, not a path bug**: hitting the 64 KB per-chain limit silently omits root `AGENTS.md` or truncates nested files.

## Answering the four opening questions

**1. Why can a release note show up in another repo while DSH's built-in session search finds nothing?**
They query completely different stores. Cross-repo recall comes from an external MCP memory server pointed at one shared graph file, whereas DSH's built-in session search only looks inside sessions whose working directory matches yours **character for character**—even a subdirectory is isolated.

**2. How does compaction swap out history without deleting log entries, and why do auto vs. manual compaction handle concurrent messages differently?**
DSH's log is strictly append-only; compaction just appends a replacement marker that hides the older span from the model's current view and swaps in a summary. If a new message arrives while summarizing, auto compaction throws away the stale summary to retry next turn, while manual compaction keeps your requested summary and places the new message right after it.

**3. Why did a 600-byte instruction budget still emit 879 bytes once user rules were present?**
Because the budget isn't a single shared pool: project instructions and user instructions each get their **own independent 600-byte allowance** before being concatenated—giving up to 1,200 bytes combined.

**4. Why does DSH resend an unchanged skill catalog right after compaction?**
Before skipping a resend, DSH checks not only whether the files changed, but also whether the previously sent catalog is **still visible to the model**. Once compaction hides that earlier span, the next turn automatically sends the catalog again.
