Try approach A in Pi, go back to the question, then take approach B. The JSONL file still contains every word of A, even when the model never sees A again. Conversely, a rule that has never appeared in a chat can be present on the first turn of a new session. Three inputs explain the difference: **the recorded events, the selected branch and the resources loaded for the current project**.

This note follows `@earendil-works/pi-coding-agent`. The package at the pinned commit declares version 1.5.2. The experiment calls its TypeScript implementation directly, with no model service, desktop client or third-party extension. <Src {...source} p="packages/coding-agent/package.json" l="1-16" />

## One invocation can carry old rules and new instructions

I put two recognizable markers in a `release` skill: `DESC_A` in the description and `BODY_A` in the procedure. The project's `AGENTS.md` contained `RULE_A`. After the first invocation, I changed all three markers from A to B and created a second skill named `late`. Without leaving the session, I sent the same `/skill:release` command again.

In the request Pi actually handed its test provider, the effective system rule was still **A**, the newly expanded procedure was already **B**, and an earlier user message still contained the first **A**. The rule and catalog came from resource loading. The command read the body from its registered path at invocation. The previous invocation survived as a message on the active branch. The figure shows which of these changed at each step.

One observation overturned my first interpretation. I expected that finding `RULE_A` anywhere in the transcript after `/reload` would indicate a failed refresh. The marker did survive, yet Pi's own replay produced **only B as the effective rule**. The session computes changes to named prompt sections and appends a system message carrying the patch. The test provider sees that sequence. An adapter that accepts a single leading system message can collapse the sequence before sending. Searching the transcript and inspecting the effective system prompt answer different questions. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1826-1848" /> <Src {...source} p="packages/ai/src/types.ts" l="562-581" /> <Src {...source} p="packages/ai/src/utils/transcript.ts" l="68-110" />

## Three ways to carry a lesson forward

Suppose a failed release taught you to regenerate an index before publishing. Where you put that lesson determines who will see it.

| Destination | Writer and reader | When it becomes visible |
|---|---|---|
| Session message, compaction or branch summary | The runtime appends entries. SessionManager reconstructs the selected path. | On that path, including after resume. A fresh, independent session has no such path. |
| User or project instruction file | A person or a tool with write access edits Markdown. The resource loader reads it. | When a session opens in an applicable directory, or its resources are reloaded. |
| `skills/release/SKILL.md` | An author maintains the procedure. The loader indexes its metadata. | The prompt can carry a name, description and location. The model reads the body on demand, or the user explicitly invokes it. |

Version control can distribute project files. Several projects can also share an agent directory. Grouping session files by working directory helps locate an earlier conversation. Starting with `--continue`, choosing `/resume` and starting with `/new` have different effects on the next request. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="7-27" /> <Src {...source} p="packages/coding-agent/docs/sessions.md" l="61-72" />

## Two paths on disk, one in the request

Persistent sessions default to `~/.pi/agent/sessions/`. An entry has an `id` and a `parentId`. An append creates a child of the current leaf. `/tree` changes position within one session file, `/fork` creates a separate session from an earlier user message, and `/clone` copies the active branch. A text editor shows the order entries were appended. Reconstructing a model request requires the parent links. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="983-995" /> <Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-49" />

<FigPiBranch lang="en" />

The checkpoint belongs to B. Pi walks the ancestry of the target leaf and finds the latest compaction **on that path**. It places the summary before retained messages, then includes eligible entries from `firstKeptEntryId` and entries appended after compaction. Switch back to A and B's checkpoint drops out as well. System messages have special handling, another reason an array slice cannot reproduce the projection. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="390-423" /> <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="468-513" />

Once the branch and compaction boundary are selected, Pi applies the latest `context_edit` on that branch for each target. An edit can replace message content or omit it from the model context with `replacement: null`. The raw entry stays in the log. Default overflow recovery uses this mechanism. It records omissions for the failed attempt before it tries to compact. If compaction fails or is cancelled, the omissions persist. Rebuilding the context hides the attempt even though the branch has no new checkpoint. <Src {...source} p="packages/coding-agent/docs/session-format.md" l="229-245" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="87-98" />

Default compaction keeps recent material verbatim and asks a model to summarize older material. `reserveTokens` helps determine **when** to compact. `keepRecentTokens` sets the target for **how much recent history** to preserve. Their defaults here are 16,384 and 20,000, with per-model overrides. A separate summarizer can run when navigating with `/tree`. It finds the common ancestor, collects entries on the path being left and records a `branch_summary` at the destination. That is one way B can inherit a lesson from A without inheriting the whole exchange. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="25-50" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="172-185" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="421-437" />

## Where does compaction get its list of modified files?

Back in the release task, I had the test provider call Pi's built-in `edit` tool with a piece of old text that did not exist in `release.md`. The tool returned an error. The file still contained `unchanged`. After another turn I passed the real session branch into compaction preparation with a one-token recent budget, putting the attempted edit in the material to summarize. Its list of modified files included `release.md`.

```json title="Three observations of the same failed edit"
{
  "toolError": true,
  "onDisk": "unchanged",
  "readFiles": [],
  "modifiedFiles": ["release.md"]
}
```

The list has three identifiable sources of structure. First, Pi looks through **model-visible messages** for assistant calls to `read`, `write` and `edit`. For codemode it also inspects nested calls recorded on tool results. Next it classifies and deduplicates the `path` argument. A file both read and edited appears only under modifications. Finally it appends the list to the summary and returns it in structured `details`. This path neither inspects a Git diff nor requires a successful result for each direct edit. <Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="29-74" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="899-919" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="1037-1056" />

This affects the next compaction as well. The default implementation carries file sets forward from a previous non-extension checkpoint and supplies the previous summary to the update prompt. A later `modifiedFiles` list is good evidence of **where to look**. To establish whether a release manifest actually changed, inspect the tool result or the artifact. The experiment measured the preparation stage. Generating summary text and merging an earlier list are source-traced steps. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="51-83" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="713-733" />

### Where can Pi cut a long tool-using turn?

When the recent budget falls inside a long investigation, Pi chooses a legal cut in the active projection. A tool result cannot simply become the first retained message. There are now three regions: history before this user turn, the first part of the turn itself and the tail retained verbatim. With input for both older regions, Pi summarizes the history and the turn prefix separately, then joins them under `Turn Context (split turn)`. If there is an earlier summary and no new pre-turn history, that summary can supply the first part. The retained exchange can thus keep an account of the problem it was answering. Repeated compaction also depends on previous summaries: a rationale already omitted there may never reappear. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="87-98" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="863-919" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="980-1020" />

## How project instructions reach the next turn

The resource loader checks the agent directory, then collects ancestor files from the working directory and orders them from broadest to most specific. It takes **one readable candidate per directory**. The order is `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md` and `CLAUDE.MD`. An override in `repo/sub` determines what that directory contributes. The parent repository still contributes its own instructions. Nested linked Git worktrees have an extra check to avoid counting the same repository scope twice. <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="214-260" /> <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="262-304" />

The contents enter the project-context section of the system prompt. The configuration reference explicitly separates discovery of these files, which does not require project trust, from loading project `.pi` configuration. To reproduce a surprising instruction, record the working directory and agent directory alongside the repository revision. Two sessions in the same checkout can inherit different ancestors. <Src {...source} p="packages/coding-agent/docs/configuration.md" l="39-47" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="79-91" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="170-181" />

## Skill descriptions and bodies have different freshness

At discovery, the loader parses frontmatter and retains the name, description, file location, base directory and invocation policy. A missing usable description skips the skill. Some naming violations only produce diagnostics. The automatic catalog advertises name, description and location. It filters out `disable-model-invocation: true` entries, and the prompt builder checks that a reading route exists in the selected tools. Reading a file locally to parse its frontmatter and transmitting that file to the model are distinct operations. <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="277-344" /> <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="352-390" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="171-181" />

An explicit `/skill:release v2` takes another path. Pi looks up the name in its current registry and **reads the file from disk at invocation**. It removes frontmatter and wraps the body with its resource location, followed by the user's `v2` argument. Changing the body at an indexed path can therefore affect the next explicit invocation. A newly added or renamed skill needs discovery first. `/reload` reloads resources and rebuilds the runtime. An older body already in the conversation still belongs to its earlier message. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="2310-2338" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3849-3877" />

Project skill discovery also depends on trust. Pi automatically scans the project's `.pi/skills` and applicable ancestor `.agents/skills` directories only for a trusted project. A project `AGENTS.md` can therefore reach the prompt in an untrusted checkout while skills stored in those project directories stay out of the automatic catalog. <Src {...source} p="packages/coding-agent/src/core/package-manager.ts" l="2700-2704" /> <Src {...source} p="packages/coding-agent/src/core/package-manager.ts" l="2720-2753" />

Precedence depends on the entry point. The low-level merge keeps the first discovered item and reports a name collision. At application level, the upstream regression test resolves a project auto-discovered skill ahead of a same-name user or package skill. That test does not establish a blanket directory-depth rule for SDK callers who provide their own list of paths. <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="423-455" /> <Src {...source} p="packages/coding-agent/test/suite/regressions/2781-skill-collision-precedence.test.ts" l="76-109" />

## Experiment: does B's checkpoint follow us back to A?

In the pinned repository root, run `npm ci --ignore-scripts`. Save the following as `probe.mjs` and run `node --import ./packages/coding-agent/src/experimental/source-resolver.ts probe.mjs`. The real SessionManager runs in memory. Supplying the summary directly isolates the projection logic from the model that would ordinarily write it.

```js title="probe.mjs"
import {SessionManager} from './packages/coding-agent/src/core/session-manager.ts';
const log = SessionManager.inMemory();
const say = text => log.appendMessage({role:'user', content:text, timestamp:0});
const root=say('base'); const left=say('attempt A');
log.branch(root); const right=say('attempt B');
console.log('raw messages',log.getEntries().filter(e=>e.type==='message').map(e=>e.message.content));
console.log('active leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendCompaction('checkpoint', right, 1200);
console.log('compacted',log.buildSessionContext().messages.map(m=>m.summary ?? m.content));
log.branch(left);
console.log('other leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendContextEdit(left, null);
console.log('edited A', log.buildSessionContext().messages.map(m=>m.content));
```

| Observation | Measured output, in order |
|---|---|
| Enumerate raw messages | `base`, `attempt A`, `attempt B` |
| B is the active leaf | `base`, `attempt B` |
| Append the checkpoint to B | `checkpoint`, `attempt B` |
| Switch back to A | `base`, `attempt A` |
| Append an omission on A | `base` |

The first four observations vary the branch or compaction boundary. The fifth keeps A in the raw log and removes it from the request with a single edit. I also ran the upstream skill parsing, collision-precedence and context-building tests. These results establish how history is selected. They do not measure how often a model loses a fact when writing its own summary. <Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="126-147" /> <Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="211-246" />

## What can accumulate across sessions?

The default coding-agent paths examined here persist session entries, explicit edits to user or project files, and writes implemented by extensions. Compaction and branch summaries can change a later request. I found no built-in maintainer in these paths that promotes successful sessions to skills, rewrites them by usage, then archives superseded versions. To carry the release lesson into a **new project session**, update the appropriate instruction file or skill and inspect it from a fresh session. Sharing it across repositories also requires the appropriate installation scope or distribution mechanism. <Src {...source} p="packages/coding-agent/docs/skills.md" l="58-67" /> <Src {...source} p="packages/coding-agent/docs/skills.md" l="87-93" />

Pi exposes separate extension mechanisms. `pi.appendEntry()` persists extension state in a session without adding it to model context. A custom message can enter context. `session_before_compact` can supply a different summarization policy, and `before_agent_start` can change the upcoming turn's inputs. An application can use these hooks to implement review. For a particular deployment the remaining questions are concrete: which extension is installed, what triggers its writer, where does the result land, and which new session reads it? <Infer lang="en" /> Editable resources make durable changes easy to review. A lesson left only in a conversation can remain invisible outside that conversation. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="122-134" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="532-552" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-635" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1625-1633" />

### Two official extensions identify exactly who carries a change forward

The `todo` example returns a full task snapshot and the next ID in its structured tool-result `details`. On `session_start` or `session_tree` the extension clears its in-memory variables and replays results belonging to `todo` on the current branch. Return to an earlier leaf and it reconstructs that branch's task state. Both persistence and restoration have a concrete boundary here: the chosen path in this session. <Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="106-138" /> <Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="147-177" />

To carry a debugging result into **another session**, the official `/handoff` example collects branch material, combines it with the user's next goal and generates a draft. The user can revise or cancel it. A new session records the parent reference and puts the draft in the editor for the user to send. The artifact is a prompt tailored to the next task. Installing the extension, invoking its command and submitting that prompt are identifiable decisions. Neither example publishes the experience as a searchable `SKILL.md` for every project. <Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="85-116" /> <Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="161-190" />

What I value for debugging is the ability to trace a surprising answer to **a particular branch, resource load or explicit invocation**. The cost is equally tangible: corrected instructions can coexist with older copies in the conversation, and a file list can record an attempted change. For evidence that a lesson became a reusable procedure, start a genuinely fresh session and inspect the procedure that its skill invocation actually expands.

Pi reconstructs messages from the selected leaf. Hermes also offers a tool for searching history. An active branch and a history-tool call leave different evidence for how an old fact reached an answer.
