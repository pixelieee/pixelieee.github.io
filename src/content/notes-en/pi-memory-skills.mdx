**The short version:** Hermes, Claude Code and Codex all ship built-in cross-session memory—dedicated memory files backed by a write tool or a background extraction job. Pi takes the opposite minimalist line: **it implements Skills in full, yet deliberately ships no built-in memory store**—no `MEMORY.md`, no `memory` tool, and no post-turn review job, for the same reason it skips built-in sub-agents and plan mode. <Src {...source} p="packages/coding-agent/README.md" l="15-19" /> Out of the box, only two things survive past a single request: **Markdown files maintained explicitly on disk** (`AGENTS.md` and `SKILL.md`), and **the session itself—an append-only, branchable JSONL tree much like a Git commit graph**. Even system-prompt updates, context compactions and message retractions never edit an existing record; each is **appended as a new line** at the end of the file, and before every request Pi walks parent links from the current `leaf` back to the root to assemble the single branch the model sees. Nearly every counter-intuitive behavior in Pi comes down to those three words: **append, never rewrite.**

By the end you should be able to answer five questions:

1. Without a built-in memory store, **where** do standing conventions, reusable workflows and mid-task scratch notes each belong in Pi?
2. With a session still open, you edit both `AGENTS.md` and `SKILL.md` on disk: why does invoking the skill without running `/reload` send **the old `AGENTS.md` alongside the new `SKILL.md` body** in the very same model request?
3. Why might a message sitting plainly in the JSONL file **never** reach the model, and what happens to a branch's compaction summary when you switch back to an earlier branch?
4. What does compaction **keep and drop**, and why does its "modified files" list record edits that **failed cleanly**?
5. If you want to build automatic memory or post-turn review on top of Pi, **which extension hooks** carry it?

## The big picture: where knowledge goes when there is no memory store

Start with the whole map. Everything that can enter a Pi model request arrives through three channels:

<FigPiArch lang="en" />

| | Session tree (conversation & state log) | Context files (standing rules) | Skills (on-demand workflows) |
|---|---|---|---|
| Location | `~/.pi/agent/sessions/--<cwd>--/<time>_<id>.jsonl` | personal global dir `~/.pi/agent/`, plus `cwd` and every parent up to the filesystem root | `~/.pi/agent/skills`, `~/.agents/skills`, project `.pi/skills`, ancestor `.agents/skills` up to the Git root, Pi packages |
| Holds | chat turns, base system prompt and section diffs, compaction checkpoints, message edits/omissions, branch summaries | project conventions or personal rules that apply to every task | step-by-step procedures, reference docs and helper scripts for a specific kind of task |
| How it reaches the model | assembled fresh before every request by walking from the active `leaf` back to the root | injected into the `<project_context>` section of the system prompt on every turn | only name, description and file path sit in `<skills>`; the body is opened with `read` or expanded via `/skill:name` |
| When disk is read | once when opening the session; later entries append in memory and write through | at resource load only: startup and manual `/reload` | the catalog scans at startup or `/reload`; the body is read from disk on every `/skill:name` or `read` call |
| Written by | the runtime, automatically | humans, or `write` / `edit` when asked | humans, installed packages, or `write` / `edit` when asked |

Two rows do all the explanatory work:

- **"How it reaches the model" decides what belongs where.** `AGENTS.md` is sent in full on every turn and occupies context continuously, so keep it to short invariants that apply no matter the task (build commands, architectural boundaries, style rules). A skill costs one catalog line until needed, so put multi-hundred-line runbooks, release checklists and scripts there. Dead-end debugging belongs in the session tree—use `/tree` to step back to an earlier turn and branch cleanly without polluting future requests.
- **"When disk is read" decides when an edit takes effect.** The session tree is re-walked on every request, so branching and compaction apply at once. `AGENTS.md` and the skill catalog are loaded into memory only at startup or `/reload`, so editing them in another window leaves a running session untouched. Skill **bodies** are the lone exception: nothing caches them in memory, so every call reads the file straight from disk. Edit both `AGENTS.md` and `SKILL.md` mid-session and invoke the skill without `/reload`, and one outgoing request ends up carrying the old `AGENTS.md`, the old `SKILL.md` body from an earlier turn, and the newly edited `SKILL.md` body all at once.

## One underlying rule: append, never rewrite

A naive chat client stores a conversation as a mutable array: compaction splices out old messages for a summary, and reloading rules overwrites element zero. Once you mutate in place, time only runs forward—you cannot jump back to turn 4 to try a different approach without losing what came after, and you cannot reconstruct from the log what system prompt the model actually had when turn 5 went sideways.

Pi stores the entire session as an **append-only tree**. Every line in the JSONL file carries an `id` and a `parentId`, and a single pointer called `leaf` marks where you are standing:

- On an ordinary turn, the new entry is appended as a child of `leaf`, and `leaf` advances to it.
- When `/tree` jumps back to an earlier turn, Pi **deletes nothing**; it moves `leaf` back to that older entry, and whatever happens next grows a sibling branch from there. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1591-1602" />

```ts title="packages/coding-agent/src/core/session-manager.ts · 984–994"
/**
 * Manages conversation sessions as append-only trees stored in JSONL files.
 *
 * Each session entry has an id and parentId forming a tree structure. The "leaf"
 * pointer tracks the current position. Appending creates a child of the current leaf.
 * Branching moves the leaf to an earlier entry, allowing new branches without
 * modifying history.
 *
 * Use buildSessionContext() to get the resolved message list for the LLM, which
 * handles compaction summaries and follows the path from root to current leaf.
 */
```
<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="984-995" />

What makes this cohesive is that **Pi models non-chat state transitions as appended tree nodes too**—including the system prompt and active tool declarations. The leading `system` message records the initial prompt (organized into named XML sections such as `<tools>`, `<rules>`, `<project_context>`, `<skills>`) and tool list. If you edit `AGENTS.md` and run `/reload` mid-session, Pi does not rewrite that leading message; it **diffs the named sections** and appends a new `system` message carrying only the sections that changed. <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="187-192" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="216-228" />

```ts title="packages/ai/src/types.ts · 559–568"
/**
 * System instructions and tool declarations at one point in the transcript.
 *
 * The leading system message is the system prompt. Later system messages change it:
 * `content` adds instructions from that point on, `sections` replace or remove named
 * prompt sections, and `toolsAdded`/`toolsRemoved` change the tool set. Replaying
 * every system message in order yields the current prompt and tools. Providers that
 * accept system messages mid-conversation send each one in place; other providers
 * rebuild the leading system message from the replayed state.
 */
```
<Src {...source} p="packages/ai/src/types.ts" l="559-585" />

Count across the codebase and six distinct operations obey the same append-only discipline:

1. **Chat turns (`message`)**: appended under `leaf`; if writing to disk throws, both the in-memory entry and `leaf` roll back immediately so later entries never reference a parent missing from the file. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1199-1232" />
2. **Prompt and tool updates (`system` patches)**: Pi diffs the branch's replayed sections against the newly built ones and appends only changed sections as a new `system` message. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1826-1848" />
3. **Hiding or replacing an earlier message (`context_edit`)**: an appended entry points at `targetId`; `replacement: null` omits it from model context while leaving the original line intact in JSONL. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="174-180" />
4. **Compaction (`compaction`)**: an appended entry stores the summary, `firstKeptEntryId` (where verbatim recent history resumes), and a merged snapshot of the `system` state at that boundary. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1278-1305" />
5. **Carrying lessons across branches (`branch_summary`)**: if you summarize when leaving a branch in `/tree`, the summary is appended at the **target** position while the abandoned branch stays untouched. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="4280-4292" />
6. **Overflow self-recovery**: when a response fails on context overflow, Pi first appends `context_edit` omissions for the failed attempt, then appends a `compaction` and retries. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3211-3216" />

Beyond zero-copy branching, this buys a concrete cost win: **preserving the provider's prefix cache**. Some model APIs accept `role: "system"` messages mid-conversation; others accept only a single system prompt at the head of the request. For the first group, Pi sends the patch in place at the end of the transcript, leaving tens of thousands of earlier tokens byte-identical in the cached prefix; for the second, Pi folds all `system` messages into a new leading prompt right before sending, paying a single cache miss per rule change. <Src {...source} p="packages/ai/src/utils/transcript.ts" l="104-120" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="657" /> Even the one-off summarization call sets `cacheRetention: "none"` so it doesn't pay to write a cache entry nothing will ever reuse. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="626-632" />

Placed next to Hermes, the symmetry is striking. Both are engineered around prefix-cache reuse: Hermes **freezes its memory snapshot** inside the system prompt for the rest of the session, whereas Pi **lets the system prompt evolve by appending section diffs at the tail**. ## The session tree: how one file yields multiple contexts

### Persistence rules

By default, sessions live under `~/.pi/agent/sessions/--<cwd with path separators replaced by ->--/` as `<timestamp>_<sessionId>.jsonl`. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="586-595" /> `--session-dir`, `PI_CODING_AGENT_SESSION_DIR` or `sessionDir` relocate them, and `--no-session` keeps everything in memory. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="64-68" />

Two small details prevent common failure modes:

- **Opening and quitting without chatting leaves no empty file.** Startup entries (model, thinking level, initial `system` prompt) sit in memory until the first `user` or `assistant` message arrives, at which point header and entries flush together. Flushing on the `user` message—rather than waiting for the assistant reply—ensures a long prompt isn't lost if the first turn crashes mid-flight. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1168-1197" />
- **Corrupt lines are skipped.** Unparseable JSON lines are ignored on load rather than bricking the whole transcript. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="617-625" />

### Three-step context assembly before every request

Because `/tree` moves within one file (unlike `/fork`, which branches from an earlier user turn into a new file, or `/clone`, which copies the active branch), **line order on disk is not what the model sees**. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-48" />

Before every request, `SessionManager` computes the active view (`buildSessionProjection`) in three steps:

1. **Trace the ancestry chain.** Walk `parentId` from `leaf` back to the root and reverse into a single chronological path. Sibling branches off this path are ignored no matter how recently they were written. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="390-416" />
2. **Cut at the latest compaction on that path.** Find the **last** `compaction` entry along the path. If one exists, entries older than `firstKeptEntryId` drop out, replaced by `[compaction, ...kept non-system entries from firstKeptEntryId, ...entries after compaction]`:

```ts title="packages/coding-agent/src/core/session-manager.ts · 499–511"
const contextEntries: SessionEntry[] = [compaction];
let foundFirstKept = false;
for (let i = 0; i < compactionIdx; i++) {
	const entry = path[i];
	if (entry.id === compaction.firstKeptEntryId) {
		foundFirstKept = true;
	}
	if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
		contextEntries.push(entry);
	}
}
contextEntries.push(...path.slice(compactionIdx + 1));
return contextEntries;
```
<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="468-512" />

Notice why line 8 filters out `system` messages inside the kept pre-compaction range: when `appendCompaction` created that checkpoint, it already replayed every `system` message up to that moment and saved the merged result in `compaction.systemMessage`. When projected, the compaction entry emits that complete `system` snapshot followed by the summary; keeping pre-compaction `system` patches in the retained tail would apply them twice. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="461-464" /> <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1286-1302" />

3. **Apply `context_edit` entries.** For each surviving entry, apply the **last** `context_edit` on the path targeting its ID: `null` omits it completely; a content payload replaces the body while keeping role and metadata. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="519-574" />

Put those three steps in one picture and the multi-context behavior becomes obvious:

<FigPiBranch lang="en" />

**Compactions and message edits belong strictly to their branch.** Compacting on branch B hangs the `checkpoint` node off B; step back to branch A with `/tree` and that node is no longer on the path to root, so A's uncompacted turns reappear verbatim. Likewise, a `context_edit` appended on A never hides anything on B. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1377-1416" />

### Why overflow recovery writes `context_edit` before compacting

`context_edit` earns its keep during context-overflow and truncated-length recovery.

When a provider rejects a request for exceeding the context window (or cuts off early), the failed `assistant` message is already persisted in the session tree so token accounting and diagnostics stay accurate. Running compaction straight on top of it would either summarize a broken half-answer or overflow the compaction call itself.

Pi therefore appends `context_edit(targetId, null)` entries to omit the failed assistant turn and its tool results first, runs auto-compaction second, and retries as a fresh run—**at most once** per failure so a genuinely oversized prompt cannot loop forever. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3180-3216" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1334-1340" /> One subtle payoff: if that recovery compaction itself fails or is cancelled by the user, the omission edits **remain on the branch**—there is no new checkpoint yet, but the broken attempt is already out of the next request's context. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="85-98" />

## Compaction: sliding windows and the false-"modified" trap

### Triggers and the two token budgets

Automatic compaction comes down to one comparison:

```ts title="packages/coding-agent/src/core/compaction/compaction.ts · 267–270"
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;
}
```
<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="267-270" />

Two settings sound similar and do completely different jobs: <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="126-130" />

- `reserveTokens` (default **16,384**) decides **when** auto-compaction fires—how much headroom to keep free for the next reply. On a 200K-window model, crossing `200,000 - 16,384 = 183,616` tokens triggers compaction.
- `keepRecentTokens` (default **20,000**) decides **how much recent history stays verbatim** once compaction runs—walking backwards from the newest message, roughly 20K tokens stay untouched and everything older is summarized. Both numbers accept per-`provider/modelId` overrides. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="417-457" />

Alongside between-turn threshold checks and overflow recovery, `/compact [focus]` runs the same pipeline on demand. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="27-41" />

### Iterative summaries and split turns

Make repeated compaction concrete with numbers. Suppose pass 1 summarizes the first 160K tokens into summary S1 and keeps the latest 20K tokens verbatim (starting at `firstKeptEntryId`). When the window fills again, pass 2 starts its summarization span at that earlier `firstKeptEntryId`—handing **"the 20K tokens that survived pass 1 + new early turns" together with S1 inside `<previous-summary>`** to an update prompt that produces S2. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="714-727" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="872-894" /> Repeated compaction is therefore **lossy chaining**: anything omitted from S1 is gone for good in S2.

Two cut-point rules keep the resulting message list valid:

- **Never split a tool call from its `toolResult`.** Cuts may land on `user`, `assistant`, bash-execution or custom messages, never on `toolResult`, which providers reject if orphaned from its call. <Src {...source} p="packages/coding-agent/docs/compaction.md" l="128-136" />
- **Split an oversized single turn into two summaries.** If one prompt ("fix the test suite") kicks off 30 tool iterations that alone exceed 20K tokens, the cut lands mid-turn on an `assistant` message. Pi summarizes prior turns into a history summary, summarizes the **completed first half of the current turn** into a separate turn-prefix checkpoint, and joins them so the kept tail still knows what the user originally asked: <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="976-1040" />

```ts title="packages/coding-agent/src/core/compaction/compaction.ts · 1018"
summary = `${historyText}\n\n---\n\n**Turn Context (split turn):**\n\n${turnPrefixResult.text}`;
```

### Why `modifiedFiles` records failed edits

To help the model remember what it touched before compaction, the default compactor appends `<read-files>` and `<modified-files>` blocks to the summary and stores them in `details`. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="1042-1056" /> Look at the collector, however, and a sharp edge jumps out—**it reads only tool-call arguments, never outcomes**:

```ts title="packages/coding-agent/src/core/compaction/utils.ts · 48–62"
function addFileOp(toolName: string, args: Record<string, unknown> | undefined, fileOps: FileOperations): void {
	const path = typeof args?.path === "string" ? args.path : undefined;
	if (!path) return;
	switch (toolName) {
		case "read":
			fileOps.read.add(path);
			break;
		case "write":
			fileOps.written.add(path);
			break;
		case "edit":
			fileOps.edited.add(path);
			break;
	}
}
```
<Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="27-73" />

It walks `read`, `write` and `edit` calls on `assistant` messages in the summarized span, plus nested calls recorded on tool results by codemode scripts (where the model writes a script to batch tool calls): every path passed to `edit` or `write` lands in `modifiedFiles` (and is simultaneously filtered out of `readFiles`, which lists only files read without modification). **Even if `edit` failed with `isError: true` and left the file untouched on disk, the path still enters `modifiedFiles`**—and subsequent compactions union the previous checkpoint's file sets straight into the new one. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="57-88" /> <Infer lang="en" />The code doesn't comment on why outcomes are ignored; structurally, `extractFileOpsFromMessage` inspects one message at a time without pairing an `assistant` tool call against the following `toolResult.isError` (even `nestedCalls`, which carry their own `status` field, pass straight through `addFileOp`). <Src {...source} p="packages/ai/src/types.ts" l="627-639" /> Treat `<modified-files>` as "paths the model tried to touch", never as proof a change landed. Experiment 2 below verifies this directly.

## Context files: stacked across directories, one winner per directory

Now look at the first class of disk resource: standing rule files such as `AGENTS.md`.

Discovery runs in two stages: first the personal global directory (`~/.pi/agent/` by default), then `cwd` and every parent directory **all the way up to the filesystem root** (it does *not* stop at the Git repo root), ordered from farthest ancestor down to `cwd` inside `<project_context>`. <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="262-304" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="79-86" />

Two practical consequences follow:

- **Directories stack; filenames within a directory override.** Dropping `AGENTS.override.md` into `repo/packages/web/` replaces only `web/`'s own file while keeping `repo/AGENTS.md` active. One smart exception handles a Git linked worktree nested inside its main checkout (such as `repo/.worktrees/feat`): if the worktree root has its own context file, Pi skips the main repo root's copy so repo-level instructions aren't injected twice. <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="235-260" />
- **No trust prompt, and no file watcher.** Context-file discovery requires no project trust approval. <Src {...source} p="packages/coding-agent/docs/configuration.md" l="41-47" /> At the same time, nothing watches these files while a session is open—edit `AGENTS.md` in another window and you must run `/reload` (or open a new session) for Pi to diff and append the updated section. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1798-1824" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3831-3873" />

## Skills: no dedicated tool—just a cached catalog and direct file reads

Everything about Pi's skills clicks into place once you notice what is missing: **Pi has no `skill` tool.**

Hermes defines `skill_view`; OpenCode and Claude Code register a dedicated `Skill` tool. Pi simply renders an XML `<available_skills>` catalog inside the system prompt's `<skills>` section—listing each skill's name, description and **absolute file path**—and tells the model: **"Use the `read` tool to load a skill's file when the task matches its description."** <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="347-388" /> If neither `read` nor `bash` is active, Pi omits the entire `<skills>` section from the prompt, since the model would have no way to open any file it listed. <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="173-181" />

Put that alongside the explicit `/skill:name` command handler:

```ts title="packages/coding-agent/src/core/agent-session.ts · 2321–2328"
const skill = this.resourceLoader.getSkills().skills.find((s) => s.name === skillName);
if (!skill) return text; // Unknown skill, pass through

try {
	const content = readFileSync(skill.filePath, "utf-8");
	const body = stripFrontmatter(content).trim();
	const skillBlock = `<skill name="${skill.name}" location="${skill.filePath}">\nReferences are relative to ${skill.baseDir}.\n\n${body}\n</skill>`;
	return args ? `${skillBlock}\n\n${args}` : skillBlock;
```
<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="2309-2338" />

**Pi caches only the routing table (`name → description + filePath`) in memory; it never caches skill bodies.** Three everyday behaviors follow immediately:

1. **Editing an existing skill's body takes effect right away, with no `/reload`.** Its path in the registry hasn't changed, so both model `read` calls and user `/skill:name` commands hit `readFileSync` and get the new instructions at once—though any body expanded on an earlier turn remains in branch history as an ordinary `user` message.
2. **Editing `description` or `disable-model-invocation` requires `/reload`.** Those fields build the `<skills>` catalog (`disable-model-invocation: true` hides the skill from automatic routing while keeping `/skill:name` available). <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="352-360" />
3. **Creating or renaming a skill requires `/reload`.** Until the registry rescans disk, the model doesn't see the new entry, and typing `/skill:new-name` hits `if (!skill) return text` on line 2 and goes to the model as literal chat text.

### Discovery roots, precedence, and the trust asymmetry

Four boundaries complete the picture:

- **Layout and lenient validation**: the portable layout is `skills/<name>/SKILL.md` (stopping recursion there so `scripts/` and `references/` can sit beside it), while standalone `.md` files directly inside a skills root also load (Pi's own `.pi/skills/` uses standalone files). - **Where discovery stops**: user roots are `~/.pi/agent/skills` and `~/.agents/skills`; project roots are `.pi/skills` plus `.agents/skills` walked upward from `cwd` **stopping at the Git repository root** (unlike `AGENTS.md`, which walks to `/`), supplemented by Pi packages and extension hooks. <Src {...source} p="packages/coding-agent/src/core/package-manager.ts" l="538-557" /> <Src {...source} p="packages/coding-agent/src/core/package-manager.ts" l="2700-2754" />

## Scope and extensions: where to plug in long-term memory

First, the isolation boundaries:

- **Session folders group files for lookup only.** `--continue` reopens the latest session for `cwd`, whereas starting fresh (or running `/new`) shares zero conversation state with earlier runs in the same directory. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="5-22" />
- **Global vs. project scope.** Files under `~/.pi/agent/` and skills in `~/.pi/agent/skills` or `~/.agents/skills` apply across every project for that user; project files apply to their directory tree.

If you want Hermes-style background review or persistent structured memory on top of Pi, the extension API provides four distinct extension points with non-overlapping roles:

1. **`pi.appendEntry(customType, data)`**: persists arbitrary state on the active branch so extensions can reconstruct it on reload or branch switch, **without ever sending it to the LLM**. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="118-132" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1683-1690" />
2. **`custom_message` (`sendMessage`)**: also stored on the branch, **and projected into model context** (with optional TUI visibility). <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="147-165" />
3. **`before_agent_start`**: mutates `systemPromptOptions.sections` per run—for example retrieving relevant notes from an external store into a named section, which Pi automatically diffs and appends. <Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-657" />
4. **`session_before_compact` and `agent_end`**: replace the compaction summarizer or run a post-turn extractor that writes back to disk. <Src {...source} p="packages/coding-agent/docs/extensions.md" l="534-552" />

Two official examples demonstrate branch-aware state without an external DB: `todo.ts` stores the full todo snapshot on each tool result's `details` and replays the **active branch** on `session_start` and `session_tree`, so jumping back in `/tree` rewinds the todo list to match that branch. <Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="106-133" /> `handoff.ts` implements `/handoff`, distilling the current branch into an editable draft prompt inside a new session linked via `parentSession`—explicit human-reviewed handoff in place of silent auto-memory. <Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="160-190" />

## Experiments

All three experiments execute the pinned TypeScript source directly against Pi's in-process `fauxProvider`, capturing the exact normalized transcript handed to a provider without network or model variance.

### Experiment 1: editing files mid-session puts old and new versions in one request

From the source paths above, `system` sections freeze until reload, `/skill:name` hits disk on every call, and prior expansions stay on the branch. Combining them in one session should put both generations into a single request.

The script writes `RULE_A` to `AGENTS.md` and `DESC_A` / `BODY_A` to a `release` skill, runs `/skill:release`, rewrites all three markers on disk to `B` while adding a brand-new `late` skill, and then captures turns before reload, after `/reload`, and in a fresh session:

```js title="pi-skill-lifecycle.mjs (excerpt)"
await turn("initial", session, "/skill:release");
await putSkill("release", "DESC_B", "BODY_B");
await putSkill("late", "NEW_SKILL", "New instructions.");
await writeFile(join(project, "AGENTS.md"), "RULE_B");
await turn("edit on disk", session, "/skill:release");
await turn("unknown name", session, "/skill:late");
await session.reload();
await turn("reload", session, "/skill:release");
```

<FigPiSkillRequests lang="en" />

**Right after the disk edits, the effective `system` prompt is still `RULE_A · DESC_A`, user message #1 still holds `BODY_A`, and user message #2 already expands to `BODY_B`; on the next turn, `/skill:late` arrives at the provider as literal text.**

The `/reload` turn also exposes an easy diagnostic trap: grepping the raw provider payload for `RULE_A` **still matches**, because the initial `system` message is never mutated; the script verifies both the two raw `system` messages (`A` followed by the `B` patch) and the replayed `getCurrentSystemMessage()` state (`RULE_B · DESC_B · NEW_SKILL` only).

### Experiment 2: a failed `edit` still lands in `modifiedFiles`

To test argument-only file tracking, the script writes `unchanged` to `release.md`, has `fauxProvider` invoke the real `edit` tool with a non-existent `oldText`, confirms `isError: true` and an unchanged file on disk, and passes the branch to `prepareCompaction` with `keepRecentTokens: 1`:

```json title="Three observations of the same failed edit"

  "toolError": true,
  "onDisk": "unchanged",
  "readFiles": [],
  "modifiedFiles": ["release.md"]
}
```

**The tool errored out and the file never changed, yet `release.md` appears in `modifiedFiles`.** Any downstream step reading `<modified-files>` after compaction sees an attempted edit reported alongside successful ones.

### Experiment 3: switching back to branch A drops branch B's checkpoint

A minimal in-memory `SessionManager` script isolates tree traversal, compaction boundaries and `context_edit`:

```js title="probe.mjs"
import {SessionManager} from './packages/coding-agent/src/core/session-manager.ts';
const log = SessionManager.inMemory();
const say = text => log.appendMessage({role:'user', content:text, timestamp:0});
const root=say('base'); const left=say('attempt A');
log.branch(root); const right=say('attempt B');
console.log('raw messages',log.getEntries().filter(e=>e.type==='message').map(e=>e.message.content));
console.log('active leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendCompaction('checkpoint', right, 1200);
console.log('compacted',log.buildSessionContext().messages.map(m=>m.summary ?? m.content));
log.branch(left);
console.log('other leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendContextEdit(left, null);
console.log('edited A', log.buildSessionContext().messages.map(m=>m.content));
```

|---|---|
| All raw message entries in JSONL | `base`, `attempt A`, `attempt B` |
| Active leaf at B | `base`, `attempt B` |
| Append `checkpoint` after B (retaining from `attempt B`) | `checkpoint`, `attempt B` |
| Move leaf back to A | `base`, `attempt A` |
| Append `null` omission edit targeting `attempt A` | `base` |

## Assessment

### What it gets right

1. **One append-only tree solves branching, auditability and prefix caching together.** Turns, prompt patches, compactions and retractions are all tree nodes: branching is zero-copy, mid-conversation `system` patches preserve cached prefixes where supported, and any historical request can be replayed from parent links.
2. **Skipping a dedicated `skill` tool removes a whole layer of state sync.** Putting file paths in `<available_skills>` and reading bodies straight from disk means body edits work immediately with zero cache-invalidation code.
3. **Failure paths keep tree invariants intact.** No empty session files before chat starts, immediate memory/leaf rollback on disk-write failure, and omission-first overflow recovery capped at one retry.
4. **Restrained core, clearly separated extension points.** Separating non-LLM state (`appendEntry`), LLM-visible messages (`custom_message`) and section-diffed prompt updates (`before_agent_start`) lets extensions add long-term memory without fighting each other.

### What to watch out for

The following is my judgment, not source fact.

1. **Silent staleness when disk rules change.** Editing `AGENTS.md` or a skill description mid-session produces no "reload needed" notice in the UI.
2. **Multiple versions of a skill can coexist in one prompt.** Because `/skill:name` appends the full body as a durable `user` message, revising and re-invoking a skill leaves older procedures sitting in history alongside the new one.
3. **`modifiedFiles` conflates intent with outcome.** Failed edits enter the list and accumulate across compactions, which can mislead a post-compaction model into assuming a change already landed.
4. **Chained compactions are lossy.** Updating S1 into S2 never re-reads raw entries from before S1, so nuance lost in pass 1 stays lost.
5. **Cross-session learning is 100% manual by default.** Without a background extractor, hard-won debugging lessons vanish when you close the session unless someone asks to write them into `AGENTS.md` or `SKILL.md`.
6. **`AGENTS.md` is untrusted and walks to `/`.** Cloning an unfamiliar repo injects its `AGENTS.md` immediately, and a stray `~/AGENTS.md` silently leaks into every project or temp folder under your home directory.

## Open questions

1. **First-turn `system` patch after `/tree`.** Source inspection shows Pi diffs the target branch's replayed sections against loaded resources on the next turn; I haven't verified that patch in a separate interactive trace.
2. **Provider matrix for mid-conversation `system` messages.** Whether `/reload` preserves or invalidates the prefix cache depends on each provider adapter's `supportsMidConvoSystemMessages` flag, which I didn't audit provider by provider.
3. **Real-model retention across chained compactions.** Using fixed summary strings isolates what enters the compactor, not how much detail real models retain over multiple passes.
