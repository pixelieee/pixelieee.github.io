## One map: where knowledge lives without a memory store

Hermes, Claude Code and Codex all ship cross-session memory files and background extraction jobs. Pi takes the opposite minimalist line—no `MEMORY.md`, no `memory` tool, and no post-turn review job.

Everything that can enter a model request flows through three channels:

<FigPiArch lang="en" />

| Channel | How it enters the model | When disk is read | Best used for |
|---|---|---|---|
| **Session tree** (`*.jsonl`) | Walked from `leaf` back to root before every request | Once on open; later entries append and flush | Active task turns and dead-end debugging (`/tree` branches cleanly) |
| **Context files** (`AGENTS.md`) | Injected in full into the system prompt on every turn | Startup and `/reload` only | Short invariants that apply to every task (commands, boundaries, style) |
| **Skills** (`SKILL.md`) | Only name, description and path sit in `<skills>`; body loads on demand | Catalog scans at startup/`/reload`; **body reads disk on every call** | Multi-hundred-line runbooks, release checklists and scripts |

Hold onto those last two columns and the architecture clicks: **rules stay resident, skills load on demand, and scratch work lives on disposable branches.**

## One underlying rule: append, never rewrite

A naive client stores chat as a mutable array: compaction splices out old turns, and rule reloads overwrite element zero. Once you mutate in place, you lose branching and can no longer reconstruct what prompt produced an earlier mistake.

Pi stores the whole session as an **append-only JSONL tree**. Every line carries `id` and `parentId`, and `leaf` marks your active node—`/tree` deletes nothing; it simply moves `leaf` back to an older node and grows a sibling branch from there. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="984-995" /> <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1591-1602" />

What ties everything together is that **non-chat state changes are appended tree nodes too**:

- **Prompt & tool updates (new `system` message)**: the initial system prompt is organized into named XML sections (`<tools>`, `<rules>`, `<project_context>`, `<skills>`); `/reload` never edits message zero—it diffs the sections and appends only the changed ones as a new `system` message at the tail. <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="187-192" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1826-1848" />
- **Compaction (`compaction`)**: appends a summary entry storing `firstKeptEntryId` (where verbatim recent turns resume) plus a merged snapshot of the active `system` state. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1278-1305" />
- **Hiding or replacing an old turn (`context_edit`)**: appends a pointer to `targetId`; `replacement: null` hides it from future requests while leaving the raw JSONL line untouched. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="174-180" />
- **Carrying lessons across branches (`branch_summary`)**: summarizing an abandoned branch in `/tree` appends the summary onto the **target** branch, leaving the old branch intact. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="4280-4292" />

```ts title="packages/ai/src/types.ts · 559–568"
/**
 * System instructions and tool declarations at one point in the transcript.
 *
 * The leading system message is the system prompt. Later system messages change it:
 * `content` adds instructions from that point on, `sections` replace or remove named
 * prompt sections, and `toolsAdded`/`toolsRemoved` change the tool set. Replaying
 * every system message in order yields the current prompt and tools. Providers that
 * accept system messages mid-conversation send each one in place; other providers
 * rebuild the leading system message from the replayed state.
 */
```
<Src {...source} p="packages/ai/src/types.ts" l="559-585" />

Beyond zero-copy branching, this **preserves the provider's prefix cache**: providers that accept mid-conversation `system` messages receive the update at the tail while tens of thousands of earlier tokens stay byte-identical; others fold all `system` messages into a single leading prompt before sending. <Src {...source} p="packages/ai/src/utils/transcript.ts" l="104-120" /> Even the one-off summarization call passes `cacheRetention: "none"` so it doesn't pay to write a cache entry nothing will reuse. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="626-632" /> Compare [Hermes's frozen snapshot](/notes/hermes-memory-skills/): Hermes protects the cache by freezing memory mid-session, while Pi lets the prompt evolve by appending diffs at the tail.

## Session tree & compaction: how one file yields multiple contexts

Within one session, `/tree` switches branches inside the same file, `/fork` splits an earlier turn into a new file, and `/clone` copies the active branch. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-48" /> Because one JSONL file can hold several branches, **file order is not model order**. Before every request, `SessionManager` builds context in three steps:

1. **Trace ancestry**: walk `parentId` from `leaf` back to root and reverse into a single chronological path; sibling branches are ignored no matter how recent. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="390-416" />
2. **Cut at the latest compaction**: find the **last** `compaction` on that path and replace earlier entries with `[compaction (its merged system snapshot + summary), kept recent turns from firstKeptEntryId, entries after compaction]`. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="468-512" />
3. **Apply `context_edit`**: for each surviving entry, apply the last `context_edit` targeting it on the path (`null` hides it; otherwise replaces body text). <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="519-574" />

The same JSONL file yields two completely different contexts on branches A and B:

<FigPiBranch lang="en" />

Because assembly walks only the active ancestry, **compactions and `context_edit` records belong strictly to their branch**. Moving `leaf` back to A drops B's `checkpoint` immediately and restores A's original history verbatim.

```ts title="packages/coding-agent/src/core/session-manager.ts · 499–511 (why kept system messages are skipped)"
const contextEntries: SessionEntry[] = [compaction];
let foundFirstKept = false;
for (let i = 0; i < compactionIdx; i++) {
	const entry = path[i];
	if (entry.id === compaction.firstKeptEntryId) {
		foundFirstKept = true;
	}
	if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
		contextEntries.push(entry);
	}
}
contextEntries.push(...path.slice(compactionIdx + 1));
return contextEntries;
```
<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="461-512" />

Line 8 skips `system` entries inside the kept range because `compaction.systemMessage` already folded every prior prompt update into one snapshot; keeping them would replay them twice. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1286-1302" />

### Overflow recovery, the two budgets, and the false-`modifiedFiles` trap

- **Why overflow recovery writes `context_edit` before compacting**: a failed overflow reply is already persisted for billing and diagnostics. Pi appends `context_edit(targetId, null)` to hide that broken turn and its tool results first, compacts second, and retries **at most once**; even if compaction itself fails or is cancelled, the omission edits stay on the branch. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3180-3216" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="85-98" />
- **Two budgets people mix up**: `reserveTokens` (default **16,384**) decides **when** auto-compaction fires (`contextTokens > contextWindow - reserveTokens`, alongside on-demand `/compact [focus]`); `keepRecentTokens` (default **20,000**) decides **how much recent history stays verbatim**. Repeated compaction chains lossily on `<previous-summary>`; cuts never split a tool call from its `toolResult`, and an oversized single turn splits into a history summary plus a turn-prefix summary. <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="267-270" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="27-41" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="872-894" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="976-1040" />
- **The `modifiedFiles` trap**: the default compactor appends `<read-files>` and `<modified-files>`, yet `addFileOp` **reads only tool-call arguments, never outcomes** (including nested calls recorded by codemode batch scripts)—every path passed to `edit` or `write` lands in `modifiedFiles` (and is stripped from `readFiles`), and later compactions union old sets forward. <Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="27-73" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="57-88" /> <Src {...source} p="packages/ai/src/types.ts" l="627-639" />

Running the pinned source with Pi's in-process `fauxProvider` against a deliberately failing `edit` on `release.md` confirms it directly:

## AGENTS.md & Skills: why one request mixes old and new

The session tree handles branching and compaction within one session; what survives across sessions are the other two channels on disk—`AGENTS.md` and `SKILL.md`. Put their disk-read schedules side by side and the mid-session paradox clicks immediately.

**Context files (`AGENTS.md`) stack across directories, override within a directory, and have no file watcher.** Pi loads `~/.pi/agent/`, then walks from `cwd` all the way up to `/` (never stopping at the Git root), taking only the first hit per directory: `AGENTS.override.md > AGENTS.md > AGENTS.MD > CLAUDE.md > CLAUDE.MD`. <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="214-233" /> <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="262-304" /> Once loaded into memory, disk edits are invisible until you run `/reload`, which appends a `system` diff. <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1798-1824" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3831-3873" />

**Skills do the opposite: Pi has no `skill` tool—it caches only the index and reads bodies straight from disk.** The system prompt's `<skills>` section lists an XML `<available_skills>` catalog (name, description, absolute file path) and tells the model to call `read` (omitting `<skills>` altogether if both `read` and `bash` are disabled). <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="347-388" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="173-181" /> Explicit `/skill:name` commands also look up the path in memory and run `readFileSync` on the spot:

```ts title="packages/coding-agent/src/core/agent-session.ts · 2321–2328"
const skill = this.resourceLoader.getSkills().skills.find((s) => s.name === skillName);
if (!skill) return text; // Unknown skill, pass through

try {
	const content = readFileSync(skill.filePath, "utf-8");
	const body = stripFrontmatter(content).trim();
	const skillBlock = `<skill name="${skill.name}" location="${skill.filePath}">\nReferences are relative to ${skill.baseDir}.\n\n${body}\n</skill>`;
	return args ? `${skillBlock}\n\n${args}` : skillBlock;
```
<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="2309-2338" />

Three rules follow immediately:

1. **Edit an existing skill's body** → works right away without `/reload`; earlier expansions stay on the branch as ordinary `user` messages.
2. **Edit `description` or `disable-model-invocation`** → needs `/reload`, since the `<skills>` catalog is cached in memory. <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="352-360" />
3. **Create or rename a skill** → needs `/reload`, or `/skill:new-name` misses the index and goes to the model as literal chat text.

Four-row cheat sheet:

| Moment | Edit `AGENTS.md` | Edit existing skill body | Add/rename skill or description |
|---|---|---|---|
| **Next turn in same session** | Not seen (old rules stay) | New body read right away; older turn still keeps old body | Catalog unchanged; `/skill:new-name` sent as literal text |
| **After `/reload`** | Appends new `system` update; active | Same as above | `<skills>` catalog updates; command expands |

| **`/tree` to older branch** | Next turn diffs and appends a `system` patch to sync latest rules[^tree-en] | Each branch keeps only its own prior expansions | Same |

## Where to plug in long-term memory

Separate sessions share zero chat history unless reopened with `--continue` or `/resume`. <Src {...source} p="packages/coding-agent/docs/sessions.md" l="5-22" /> To build Hermes-style background review or persistent memory on Pi, four extension hooks split cleanly without fighting each other:

1. **`pi.appendEntry(customType, data)`**: persists branch-aware state across restarts and `/tree` switches **without sending it to the LLM**. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="118-132" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1683-1690" />
2. **`custom_message` (`sendMessage`)**: also stored on the branch, **and projected into model context**. <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="147-165" />
3. **`before_agent_start`**: mutates `systemPromptOptions.sections` before a run (e.g. retrieving external memory into a named section; Pi diffs and appends automatically). <Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-657" />
4. **`session_before_compact` & `agent_end`**: replace the compaction summarizer or run a post-turn extractor back to disk. <Src {...source} p="packages/coding-agent/docs/extensions.md" l="534-552" />

Two built-in examples show the pattern cleanly: `todo.ts` stores snapshots on tool-result `details` and replays the active branch on `session_tree` (so stepping back in `/tree` rewinds the todo list too); `handoff.ts` distills the current branch into an editable draft prompt inside a new session—human-reviewed handoff instead of silent auto-memory. <Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="106-133" /> <Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="160-190" />

## Gotchas & where docs disagree with code

### Four practical gotchas

My engineering judgment based on the mechanisms above:

1. **Silent staleness after disk edits**: editing `AGENTS.md` or a skill description mid-session shows no "reload needed" notice in the UI.
2. **Multiple skill versions in one transcript**: every `/skill:name` appends a durable `user` message, so iterating on a skill in one session leaves old and new bodies sitting side by side.
3. **`modifiedFiles` conflates intent with outcome**: failed edits enter the list and accumulate across compactions, risking false assumptions after long runs.
4. **`AGENTS.md` is untrusted and walks to `/`**: cloning an unfamiliar repo injects its `AGENTS.md` immediately, and a stray `~/AGENTS.md` leaks into every directory under `$HOME`.

## Answering the four opening questions

**1. Without a built-in memory store, where do standing rules, procedures, and trial-and-error live?**
Standing rules go straight into `AGENTS.md` or `CLAUDE.md` and load into the system prompt at startup. Reusable procedures live in `SKILL.md`, showing only a name and short summary until the model reads the file on demand. Temporary trial-and-error stays in the JSONL session tree and gets folded into summaries when you compact.

**2. Why can messages saved in JSONL never reach the model, and where does another branch's compaction go when switching back?**
Pi never sends the whole log file—it walks backward from your current node to the root and stops at the most recent compaction checkpoint along that path, skipping older entries. When you switch back to an earlier branch, any summary created on the other branch stays in the file but no longer lies on your active path, so the model never sees it.

**3. After editing both `AGENTS.md` and `SKILL.md` mid-session without `/reload`, why do old rules, old body, and new body all appear in one request?**
They refresh differently: `AGENTS.md` and the skill list are cached at startup and stay stale until `/reload`, while `/skill:name` and `read` always pull straight from disk. So the old skill body stays in earlier chat messages, the fresh call brings in the new body from disk, and the cached `AGENTS.md` remains old—putting all three in the same request.

**4. Which extension hooks let you add long-term memory to Pi?**
Four hooks cover the full request lifecycle: `before_agent_start` to inject prompts or memory messages before a turn, `context` to trim or rewrite messages before sending, `session_before_compact` and `session_before_tree` to customize summaries, and `appendEntry` to store private plugin state inside the JSONL log.
