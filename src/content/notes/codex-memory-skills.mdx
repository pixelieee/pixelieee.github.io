在仓库 A 纠正了一条测试命令，后来在仓库 B 开新对话。一条记忆已经被提取、落盘，整理任务甚至显示 `done`，B 仍然能只读到旧摘要。我在 **Codex CLI 0.169.0** 的本地 App Server 上复现了这个状态。

关键是查清“写入”指哪一层。`stage1_outputs` 是按旧线程记账的材料，`rollout_summaries/` 是本次选中材料的文件副本，`memory_summary.md` 才是新线程首先读取的摘要。三个地方会短暂不一致，也可能长期保留不同内容。项目 Skill 又是另一条路，它能随工作目录立刻改变，与记忆整理的完成时间无关。

### 一次空结果，为什么会删除旧材料

同一个线程有三种结局。成功且带内容时，事务更新来源时间、保存摘要、推进全局整理任务。返回空结果时，事务也记录本次成功处理到哪个时间点，但会删除这个线程原有的提取行；之前确实有行被删，才再次通知全局整理。模型或服务报错则进入错误状态，扣减重试额度并安排退避，旧产物继续留存。**空和失败的含义相反**：前者可以撤回旧证据，后者表示这次没有形成新判断。<Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="860-873" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="946-955" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="1003-1029" />

如何避免每个新回合反复提交同一份历史？任务记录带有 `last_success_watermark`。已有输出或成功记录已经覆盖来源更新时间时，就跳过本次领取。正在运行且租约有效的任务也会跳过；来源更新后，可重新获得一次提取机会，原有退避和耗尽的额度有专门的处理。默认每件提取任务的租约和失败退避均为一小时。这些时间都独立于旧会话的六小时空闲窗口。<Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/state/src/runtime/memories.rs" l="667-685" /> <Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/lib.rs" l="83-89" />

### 一份来源在数据库和磁盘上各活多久

### `done` 对摘要保证了什么

V2 在收尾时检查下面这个函数。首行是格式标记，所以 V2 目录中的文件也以 `v1` 开头。Rust 的 `str::len()` 计 UTF-8 字节。四个标题全部存在且总长小于 10,000 字节，才通过这部分格式校验。<Src repo="openai/codex" rev="d32063f96c2dff1dc96af839b3952abb6acfeda4" p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

```rust
pub fn is_valid_v2_summary(summary: &str) -> bool {
    summary.lines().next() == Some("v1")
        && summary.len() < 10_000
        && [
            "## User Profile",
            "## User preferences",
            "## General Tips",
            "## What's in Memory",
        ]
        .iter()
        .all(|heading| summary.lines().any(|line| line.trim() == *heading))
}
```

## 实验：来源已删，下一次新线程会读到什么

我启动正式 `codex app-server`，模型端接到仅监听本机的 Responses 测试服务。在工作目录 A 通过 `thread/start` 和 `turn/start` 生成两段真实格式的合成历史。随后只把临时状态库中它们的最后活动时间拨早八小时，保留真实目录、来源、线程 ID 和 rollout 文件。切到工作目录 B 开新回合，触发默认筛选。两阶段都走发行版的代码；测试服务控制模型的回答，不评估真实模型总结的好坏。

回放规则只有两条：提取器读到第一段时返回命令 `check-atlas-47`，读到第二段时返回空摘要；整理器总是回复完成，**不发写文件工具调用**。我在两份独立的 `CODEX_HOME` 各跑一次，仅改变初始总摘要。观察点同时放在 SQLite、文件目录和新线程的 `thread/memory/read` 上。

| 观察点 | 空目录起步 | 已有一份格式正确的旧摘要 |
| --- | --- | --- |
| 阶段一 | 两个任务完成，一条提取行 | 相同 |
| 来源文件 | 一份，正文含新命令 | 一份，正文含新命令 |
| 全局任务 | `error / failed_invalid_artifacts` | `done`，该行的选中位为 1 |
| 新线程读到 | `null` | 旧标记 `PRIOR_ONLY_63`，没有新命令 |

同一段有用事实已经在数据库和两组的来源文件里。第一组缺总摘要，验收失败。第二组沿用旧摘要，也通过了验收。此时检查任务状态和检查用户下次能否直接看到某个事实，会得到不同答案。

我另跑了第三组，把第二段的空 JSON 改成无法解析的文本。结果是同一批领取的两个任务分别为 `done` 和 `error`，失败任务的 `retry_at` 在未来；第一段的来源文件照常写出，全局整理仍能完成。定位一次局部提取故障时，应按线程检查任务行。

**再把已保留的来源变成空结果。** 我在原线程 A 追加一条合成消息，让下一次提取固定返回空，并把它的最后活动时间放在上一轮来源时间之后十分钟，仍满足六小时空闲。B 再开回合时，`stage1_outputs` 从 1 行降到 0，全局任务为 `pending`；刚成功整理过的 `rollout_summaries/` 里仍有 **1 个文件**。只把该临时库里全局任务的成功时间拨早七小时，另开一个正式回合，来源文件才从 1 个降到 0，任务回到 `done`。原有总摘要在这次回放里仍没有变。
