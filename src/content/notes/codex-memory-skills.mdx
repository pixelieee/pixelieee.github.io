**一句话结论：** Codex CLI 把跨会话记忆做成挂在 App Server 后的两阶段异步流水线——旧会话先熬过 6 小时空闲被提取，再过 6 小时冷却整理进 `memory_summary.md`，而写端验收只查格式，不核对新事实是否真写进了摘要。<Src {...source} p="codex-rs/app-server/src/request_processors/turn_processor.rs" l="747-783" /> <Src {...source} p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

读完这篇，你能搞清四件事：

1. 在仓库 A 纠正了测试命令、整理任务甚至报了 `done`，为什么在仓库 B 开新对话时仍只读到旧摘要？
2. 为什么提取器返回**空结果**会删掉旧证据，而报错失败反而保留旧证据？
3. 为什么一条记录被撤回后，数据库里已经变 0 行，磁盘上的 `rollout_summaries/` 却还要等 6 小时才消失？

本文固定 **Codex CLI 0.169.0**（提交 `d32063f`），覆盖本地 App Server 运行时（IDE 扩展共用所连主机本地记忆，ChatGPT 网页版则独立）。[官方记忆说明](https://learn.chatgpt.com/docs/customization/memories)

## 一张图看懂：三层存储与两个六小时窗口

在 Codex 里，「记住」一词背后其实有三层独立状态——**`stage1_outputs`**（SQLite 单线程证据行）、**`rollout_summaries/`**（同步到磁盘的来源副本）、**`memory_summary.md`**（新线程首读的总摘要），三者可以短暂不一致，甚至长期内容不同。项目 Skill 则完全独立，按当前工作目录即时发现：

| 对象 | 写在哪里 | 下一次怎么被读到 |
|---|---|---|
| **会话记录（rollout）** | 活动线程追加事件，索引记录来源与最后活动时间 | 阶段一挑中空闲旧线程后，反向扫描其 rollout |
| **本地跨会话记忆** | 阶段一写 SQLite，阶段二写 `rollout_summaries/` 与 `memory_summary.md` | 新线程先读 `memory_summary.md`（裁至 2,500 token），需要证据再开来源文件 |

## 阶段一：新回合触发扫描，按优先级取样，空结果即撤回

记忆写入的触发点藏在 App Server 的 `turn/start` 之后——必须**带输入、开启新回合**（往进行中回合插话走 `Steered` 不触发），且跳过临时会话与子 Agent。<Src {...source} p="codex-rs/app-server/src/request_processors/turn_processor.rs" l="747-783" /> <Src {...source} p="codex-rs/memories/write/src/start.rs" l="24-99" />

后台扫描**显式排除当前正在发言的线程**，按以下条件领取其他旧线程（不按 `cwd` 或项目过滤，因此跨仓库共用）：
- **第一道 6 小时窗口**：空闲至少 **6 小时**、最近活动在 **10 天**内，每次最多领 **2** 个；仅限交互来源（`Cli`、`VSCode`、`atlas`、`chatgpt`），`codex exec` 批处理不算；若有额度快照，默认还要求剩余额度 ≥ 25%。<Src {...source} p="codex-rs/config/src/types.rs" l="57-62" /> <Src {...source} p="codex-rs/rollout/src/lib.rs" l="86-95" /> <Src {...source} p="codex-rs/memories/write/src/phase1.rs" l="127-143" /> <Src {...source} p="codex-rs/memories/write/src/guard.rs" l="42-80" />

## 阶段二：第二道六小时冷却、格式验收与读写宽严反差

阶段二从最近 **30 天**里按使用次数和更新时间挑出最多 **256 条**提取行，同步到 `rollout_summaries/`，用 Git 基线算差异交给临时整理 Agent 更新 `memory_summary.md`。<Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="440-491" /> <Src {...source} p="codex-rs/memories/write/src/phase2.rs" l="64-180" />

这里藏着三个最关键的设计真相：

1. **第二道 6 小时冷却**：距上次成功全局整理未满 6 小时，全局任务拿不到租约——即便数据库里刚删掉或新增了提取行，`rollout_summaries/` 和总摘要也要等冷却过完才同步。<Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="24-29" /> <Src {...source} p="codex-rs/state/src/runtime/memories.rs" l="1081-1102" />
2. **写端 `done` 只查结构格式，不查内容是否更新**：V2 收尾验收只跑下面这个函数——首行 `v1`、四个标题齐全、小于 10,000 字节即算成功，**完全不检查新证据有没有写进正文**：<Src {...source} p="codex-rs/memories/write/src/workspace.rs" l="103-130" />

```rust title="codex-rs/memories/write/src/workspace.rs · 118–129"
pub fn is_valid_v2_summary(summary: &str) -> bool {
    summary.lines().next() == Some("v1")
        && summary.len() < 10_000
        && [
            "## User Profile",
            "## User preferences",
            "## General Tips",
            "## What's in Memory",
        ]
        .iter()
        .all(|heading| summary.lines().any(|line| line.trim() == *heading))
}
```

3. **写端严、读端宽，且 V1 / V2 目录不同**：干净 `CODEX_HOME` 默认进 `memories_v2/`（已有旧 `memories/` 则继续走 V1；V1 允许在记忆目录内部生成 `skills/`，但不会自动装进项目的 `.agents/skills/`）。读端扩展只要求 `memory_summary.md` 是非空可读文本并裁到 **2,500 token**，根本不复查 `v1` 首行和四个标题；若用户当场要求「记住/忘记」，V2 模板会先写 `extensions/ad_hoc/notes/` 等后续整理。<Src {...source} p="codex-rs/core/src/config/mod.rs" l="3721-3735" /> <Src {...source} p="codex-rs/ext/memories/src/extension.rs" l="45-76" /> <Src {...source} p="codex-rs/ext/memories/src/prompts.rs" l="35-62" /> <Src {...source} p="codex-rs/ext/memories/templates/memories/read_path_v2.md" l="3-20" />

### 实测：整理报 `done`，新线程为什么仍读到旧摘要

在正式 `codex app-server` 上接本地回环服务：在目录 A 造两条合成历史并把临时库里活动时间拨早 8 小时，切到目录 B 触发扫描。让提取器对第一条返回命令 `check-atlas-47`、对第二条返回空；让整理器**只回复「已完成」、不改任何文件**，对比两种初始状态：

| 观察点 | 空目录起步 | 已有一份格式合法的旧摘要 |
|---|---|---|
| 阶段一与来源文件 | 1 条提取行 + 1 份含 `check-atlas-47` 的文件 | 相同 |
| 全局整理任务状态 | `error / failed_invalid_artifacts` | **`done`**（选中位 `selected_for_phase2 = 1`） |
| 新线程 `thread/memory/read` | `null` | **旧标记 `PRIOR_ONLY_63`，没有新命令** |

紧接着给原线程 A 追加一条消息让它重提取为空：数据库 `stage1_outputs` 立刻从 1 变 0、全局任务变 `pending`，但磁盘 `rollout_summaries/` 里**仍留着 1 个文件**；直到把临时库里上次整理完成时间拨早 7 小时、再开一轮新回合，磁盘文件才清成 0：

## 踩坑清单与落地建议

<Infer /> 回到开头「仓库 A 纠正了测试命令、切到仓库 B」的问题，四条实战判断：

1. **团队硬规范写进 `AGENTS.md` 或 `.agents/skills/`，别指望记忆流水线**：几分钟后切到 B，A 根本没过 6 小时空闲门槛；哪怕之后整理完成，也只共享同一 `CODEX_HOME` 的线索，没法像仓库文件那样审阅和回滚。
2. **排查记忆没生效，按三层逐级查**：查提取看 `stage1_outputs` 与 `last_success_watermark`；查旧文件为何还在看全局任务状态与 6 小时冷却；查新线程实际拿到什么，直接看 `thread/memory/read`（**千万别用 `codex debug prompt-input` 下结论**）。
3. **`done` 不等于「新事实一定进了总摘要」**：写端只验格式不验内容，整理模型如果偷懒未改文件，只要旧摘要合法一样报 `done`。
4. **注意 `CODEX_HOME`、`CODEX_SQLITE_HOME` 与 V1/V2 版本**：三者任何一个没对齐，两次启动看到的就不是同一份记忆库。<Src {...source} p="codex-rs/config/src/config_toml.rs" l="373-377" /> <Src {...source} p="codex-rs/state/src/runtime.rs" l="355-377" />

## 回看开篇的四个问题

**1. 在仓库 A 纠正了测试命令、整理任务甚至报了 `done`，为什么在仓库 B 开新对话时仍只读到旧摘要？**
第一道坎是时间：仓库 A 刚聊完没多久就切去 B，它还没空闲满 6 小时，压根轮不到后台去提取。就算熬过了两道 6 小时窗口、整理任务也跑完了，验收程序也**只检查摘要的排版格式**（开头是不是 `v1`、四个标题齐不齐、有没有超字数），完全不核对新事实写没写进去——所以整理模型偷懒没改文件，只要旧摘要格式合法，照样会报 `done`。

**2. 为什么提取器返回空结果会删掉旧证据，而报错失败反而保留旧证据？**
在 Codex 眼里，这两件事的意思完全相反：返回空结果是明确表态「这段旧对话里已经没什么值得记住的了」，所以会顺手撤掉它以前提炼出来的旧记录；而调用报错只是临时出故障，系统会等 1 小时再重试，不会因为一次网络或模型抽风就把好好的旧证据删掉。

**3. 为什么一条记录被撤回后，数据库里已经变 0 行，磁盘上的 `rollout_summaries/` 却还要等 6 小时才消失？**
因为「撤回记录」和「清理磁盘文件」分属前后两个阶段。第一阶段发现该撤回时，会立刻把数据库里的提取行删成 0 并排个整理任务；但真正负责把变动同步到磁盘目录和总摘要的是第二阶段，它有自己的一道 6 小时全局冷却时间，冷却没过完，旧文件就得先留在磁盘上。

**4. 为什么 `codex debug prompt-input` 查不到写好的摘要，正式 App Server 对话却能读到？**
因为这个调试命令走了捷径、绕开了正式的 App Server，自己拼扩展列表时装了 Skill，偏偏**漏装了记忆扩展**。所以拿它去验证记忆有没有生效，永远查不到，会误以为记忆坏了。
