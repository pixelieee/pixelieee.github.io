**一句话结论：** Claude Code 把长期知识拆成「团队审阅的项目规则、本机按仓共享的自动记忆、按需加载的 Skill」三条线——启动只载受限前缀，写入不改当轮启动快照，而一个空目录就足以切断 worktree 的 Skill 继承。

读完这篇，你能搞清四件事：

1. 刚用 `Write` 和 `Edit` 改完记忆索引且全部报成功，为什么紧接着发出的请求里启动说明还是**旧索引**？
2. `MEMORY.md` 写到 202 行时，为什么磁盘落盘、`tool_result` 报成功、请求里却同时冒出一条 `Error` 告警？
3. 为什么新建一个 Git linked worktree 能自动继承仓库的记忆索引，却可能因为多了一个**空目录**突然看不到主仓的 Skill？
4. 为什么 Skill 的正文在后续轮次还在对话里，它附带的 `allowed-tools` 免审批授权却已经过期了？

本文基于本机 **Claude Code 2.1.327** 配合本地环回接收端实测（脚本只指定工具调用，读写全部由真实 CLI 执行，不依赖模型预测），官方资料核对日期为 2026-11-18。[固定版本发布记录](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L3)

## 一张图看懂：三条知识线与首次请求

在 Claude Code 里，「让下次还记得」先要分清**谁拥有这条知识**——团队规范进仓库审阅，本机纠偏进自动记忆，跨步流程进 Skill，三条线落盘位置和送达时机各不相同：

<FigClaudeArch />

| 希望留下什么 | 落点与维护者 | 下一次何时进入上下文 |
|---|---|---|
| 仓库级约定（如发布前需值班人确认） | 根 `CLAUDE.md` / `CLAUDE.local.md`，随代码评审 | 启动时从上级拼接到当前目录，作为用户消息附在系统提示之后 |
| 只约束局部代码的规则（如 `module/`） | `.claude/rules/`（带 `paths`）或子目录 `CLAUDE.md` | 首次请求缺席；真实读到匹配文件时才随下一次请求进入 |
| 对话中纠正的本机事实与偏好 | `~/.claude/projects/<project>/memory/MEMORY.md` 及主题文件 | 新对话带入前 **200 行或 25 KB** 索引；正文等 `Read` 才读 |
| 可复用步骤、检查项与模板 | `.claude/skills/<name>/SKILL.md` 及附件脚本 | 起步只在 1% 预算清单里列简介；调用或 `/name` 才注正文 |
| 上次命令执行日志 | 当前会话记录 | 恢复该会话可见；另起新会话不随项目说明自动带入 |

有两条规则特别容易踩坑：
- **局部规则按访问延迟加载**：实验中根目录放了 `.claude/rules/module.md`（限定 `paths: ["module/**/*.py"]`）和 `module/CLAUDE.md`，首份请求里两者都缺席；让 CLI 真实 `Read` 一次 `module/a.py` 后，文件内容、子目录说明和路径规则同时出现在下一次请求里。排查触发来源可用 `InstructionsLoaded` hook（区分 `session_start`、`nested_traversal`、`path_glob_match`）。[说明文件加载顺序](https://code.claude.com/docs/en/memory#how-claude-md-files-load) · [路径规则](https://code.claude.com/docs/en/memory#path-specific-rules) · [InstructionsLoaded 事件](https://code.claude.com/docs/en/hooks#instructionsloaded)
- **有 `CLAUDE.md` 时默认不回退 `AGENTS.md`**：只要工作目录或上级存在项目侧的 `CLAUDE.md` 或 `CLAUDE.local.md`，直接读 `AGENTS.md` 的回退（v2.1.277 起支持）就会关闭。实验根同时放了两份文件，首份请求只出现了 `CLAUDE.md` 的标记；两份都要用时须显式配置或在 `CLAUDE.md` 里 `@AGENTS.md` 导入。[AGENTS.md 选择条件](https://code.claude.com/docs/en/memory#agents-md)

如果 `Makefile` 已经写清了发布命令，就别在长期笔记里再抄一份——只记代码推不出来的约束，把长流程放进 Skill。[项目记忆](https://code.claude.com/docs/en/memory) · [Skill 存放位置](https://code.claude.com/docs/en/skills#where-skills-live)

## 一次改写，三份请求：写入为何不改启动快照

为看清一条新知识如何跨越进程，我在隔离配置目录里初始化了仓库，索引原有一行 `INDEX_BEFORE`。接收端依次让真实 CLI 读旧索引、写入含 `DETAIL_QUARTZ` 的 `release-owner.md`、用 `Edit` 把索引改为 `INDEX_AFTER`；随后关闭进程（`--no-session-persistence`），在同仓另起新进程并执行一次 `Read`。

<FigClaudeTrace />

如果只对第四份请求全文搜字符串，会同时搜到 `INDEX_BEFORE` 和 `INDEX_AFTER`，误以为 CLI 已经重载了索引。按消息槽位拆开才看清真相：启动时作为 `user` 文本附上的**仍是旧索引**，新索引只出现在助手自己的 `Edit` 工具入参里——同一回合靠工具历史知道发生了什么，但启动附件不动（保住前缀稳定）。另起进程后工具历史清空，首份请求才从磁盘读入 `INDEX_AFTER`；而真正的口令 `DETAIL_QUARTZ` 依然不在请求里，直到第二次请求前执行 `Read`：

```json title="重启后第 2 次请求 · messages 中相邻的两个内容块（节选）"
[
  {
    "role": "assistant",
    "content": [{
      "type": "tool_use", "id": "toolu_1", "name": "Read",
      "input": {"file_path": "…/release-owner.md"}
    }]
  },
  {
    "role": "user",
    "content": [{
      "type": "tool_result", "tool_use_id": "toolu_1",
      "content": "…The on-call handoff code is DETAIL_QUARTZ. …"
    }]
  }
]
```

查看磁盘上的 `release-owner.md` 还能发现，输入给 `Write` 的 YAML 只带名字、描述和类型，落盘后自动补上了 `modified` 时间戳——它能回答最后何时写过，但不能保证值班安排今天仍然有效。[自动记忆如何读写](https://code.claude.com/docs/en/memory#how-it-works)

## 自动记忆的超限与后台路径：Write 成功，为何另报 Error

本地终端默认开启自动记忆，存放在 `~/.claude/projects/<project>/memory/`。默认按仓库归属，**同一台机器上同一仓库的多个 worktree 共享自动记忆**；会话历史到期清理时记忆文件单独保留，可用 `/memory` 查看、编辑或关闭。[写入范围与存放位置](https://code.claude.com/docs/en/memory#auto-memory)

### 202 行实测：三处检查给出三种状态

我让真实 CLI 先 `Read` 索引，再用 `Write` 把 `MEMORY.md` 替换成 202 行（最后三行标记为 `EDGE_200`、`EDGE_201`、`EDGE_202`，文件很小，先撞 200 行上限）。对同一次写入检查三个位置：

| 检查位置 | 2.1.327 的实际结果 |
|---|---|
| 磁盘上的 `MEMORY.md` | 202 行全部落盘，包括第 202 行的 `EDGE_202` |
| 回给助手的 `user.tool_result` | 报告更新成功，**没有** `is_error` |
| 后续请求里的独立 `system` 消息 | 标明 `PostToolUse:Write`，提示超出读取上限，要求压缩索引并把细节移入主题文件 |

三者并不矛盾：`Write` 完成的是文件写入，而 `PostToolUse` 盯的是**下次启动能不能完整读入**（上限为前 200 行或前 25 KB，先到为准，与 `CLAUDE.md` 预算分开）。只看成功位会漏掉压缩提醒；见到 “Error” 就原样重试，只会再写一遍超限文件。[索引的写入与加载限制](https://code.claude.com/docs/en/memory#how-it-works)

重启后的首份请求里还有个更隐蔽的检索陷阱：

<FigClaudeMemory />

启动截断告警会摘引第一个被省略的行，所以全文搜 `EDGE_201` 依然命中——但它**只出现在告警引文里**，真正进了索引正文的只有到 `EDGE_200` 为止，`EDGE_202` 则彻底消失。核对关键条目是否生效时，必须检查索引正文段落，不能只数全文命中。

### 前台写入、后台提取与 Dream 的边界

除了前台对话直接读写，客户端还有独立的后台提取路径：官方发布记录披露过 v2.1.77 修复提取写入与主会话记录的竞态、v2.1.273 修复开启 `permissions.blockReadsOutsideWorkingDirectories` 时仓库自定义记忆目录对提取流程的权限收紧——这意味着磁盘上 `MEMORY.md` 变了，不能单凭结果断定是前台还是后台写的。[恢复会话竞态修复](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L8904) · [记忆提取与目录权限](https://github.com/anthropics/claude-code/blob/9fa26078be418ec4b217334812e2a04cc63336ae/CHANGELOG.md#L4404)

本地可用 `autoMemoryEnabled: false` 或 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` 关闭自动记忆（后台会话或由另一 Claude Code 启动的会话里 `/memory` 只能关不能重开）。帮助中心速查表列出了 `/dream`，但公开命令参考并未承诺本地定时整理的固定周期，以当前交互会话 `/help` 为准。Anthropic 对 **Managed Agents 的 Dreams API** 则给出了明确双库协议：异步读取旧记忆库与 1–100 份会话，结果写入新库供审核后再采用；不过托管服务的协议不能直接拿来推定本机终端的触发间隔或覆盖策略。[自动记忆开关](https://code.claude.com/docs/en/memory#enable-or-disable-auto-memory) · [CLI 帮助中心](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) · [Dreams API](https://platform.claude.com/docs/en/managed-agents/dreams)

## 一个空目录，为什么能切断 linked worktree 的 Skill 继承

我在主 checkout 写入未提交的 `release-card` Skill（在创建 worktree 之后才写入），然后在 `git worktree add` 建出的 linked worktree 里连续起三个新进程——提示词和 CLI 配置完全不变，只改变这个 worktree 根部的 `.claude/skills/`：

<FigClaudeScope />

我还用同一份 CLI 配置启动了一个完全无关的 Git 仓库作对照：它的首份请求里既没有 `INDEX_AFTER`，也没有两份 Skill 的简介——排除了「共用配置目录导致串号」的干扰。

结论非常干脆：自动记忆按仓库归属，所有 worktree 共享同一本机记忆目录；而项目级 Skill 从 v2.1.277 起先查当前 worktree 根部是否存在 `.claude/skills/`，**缺席才回退到主 checkout，只要本地目录存在——哪怕里面一个文件都没有——回退立刻关闭**。团队在一条分支上刚建了第一个本地 Skill，就可能让主仓原先可见的发布流程瞬间消失，而记忆索引却照常出现。排查时先分清丢的是索引事实还是 Skill 流程。[worktree 共享范围](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout) · [项目技能发现规则](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)

## Skill 的简介、正文与授权：三者各自何时过期

Claude Code 用三级按需披露控制 Skill 体积：平时只进简介清单，正文调用时加载，附件脚本用到再读。当 Skill 很多时，清单受**模型上下文窗口 1%** 的预算限制——超预算时保留名字，但会从低频条目开始略去描述。[Anthropic 工程文章](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [目录预算](https://code.claude.com/docs/en/skills#skill-descriptions-are-cut-short)

| Skill 配置 | 普通会话起步清单 | 谁能直接调用 |
|---|---|---|
| 默认 | 列出简介，正文按需加载 | 用户和模型 |
| `disable-model-invocation: true` | **连简介也不列给模型** | 仅用户输入 `/name` 显式调用 |
| `user-invocable: false` | 列出简介 | 仅模型触发；用户不能 `/name` 运行 |

调用时的生命周期拆成三条彼此独立的时钟：[谁能调用](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill) · [正文生命周期](https://code.claude.com/docs/en/skills#skill-content-lifecycle) · [工具预授权](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill)

1. **同轮重复调用自动去重，手改磁盘热发现但旧消息不变**：实测里接收端连续两次调用 `Skill({"skill":"release-card"})`，两次工具结果都说正在启动，但请求里完整正文只出现**一次**，第二次紧跟一条「已加载且说明未变化」的短提示。把入参换成手动专用的 `release-manual` 时，`Skill` 工具直接返回 `is_error: true` 且无正文；改为用户输入 `/release-manual`，正文立刻进入首份请求——说明**知道名字也不等于模型有调用权**。
2. **`allowed-tools` 免审批只管这一轮**：Skill 注入的正文会留在后续对话里，但预授权在**下次用户发消息时立刻失效**——**文字还在，不等于操作授权还在**。
3. **压缩与委派会改写可见性**：`/compact` 之后，根 `CLAUDE.md` 从磁盘重读，子目录规则恢复按需；已调用的 Skill 按最近优先重新附上，但**单个上限 5,000 token、总计 25,000 token**——把关键验收条件写在长 Skill 末尾，初读能看见，压缩后可能正好被截掉。普通子 Agent 不继承主对话自动记忆（fork 才继承），专职子 Agent 可配置独立 `memory: project`（`.claude/agent-memory/<name>/`）或 `local`（`.claude/agent-memory-local/<name>/`）；预加载给子 Agent 的 Skill 则在启动时直接注入正文。[压缩后说明](https://code.claude.com/docs/en/memory#instructions-seem-lost-after-/compact) · [子 Agent 持久记忆](https://code.claude.com/docs/en/sub-agents#enable-persistent-memory) · [预加载 Skill](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)

## skill-creator 到底测了什么，以及踩坑清单

哪怕 `release-card` 的触发评测拿了满分，生成的发布说明仍可能漏掉不兼容变更。翻开 Anthropic 公开的 `skill-creator` 脚本就能看清原因：它生成唯一名字，把**待测简介和占位正文**写进临时命令文件，再交给 `claude -p` 观察工具流是否命中 `Skill` 或 `Read`。[固定版本源码 · L51–75](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/scripts/run_eval.py#L51-L75) · [触发判定](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/scripts/run_eval.py#L132-L168)

```python title="run_eval.py · L51–54"
unique_id = uuid.uuid4().hex[:8]
clean_name = f"{skill_name}-skill-{unique_id}"
project_commands_dir = Path(project_root) / ".claude" / "commands"
command_file = project_commands_dir / f"{clean_name}.md"
```

它验证的是**简介能不能准确触发、会不会误触发**，根本不跑团队真正的发布步骤。要证明正文确实提升了产出质量，必须用已知变更集对照无技能基线或旧版本做输出断言。[输出评估与基线](https://github.com/anthropics/skills/blob/e4bb5d960d87126ff3b3a8af1a104b7db67560ba/skills/skill-creator/SKILL.md#L145-L201)

### 四条实战避坑清单

1. **查记忆是否生效，别只搜全文、要看消息槽位**：同一回合里的 `Edit` 会让新旧标记同时出现；200 行截断后的告警也会摘引第 201 行，唯有核对启动附件正文才靠谱。
2. **重要约定写进 `CLAUDE.md` 并配 CI，别只靠自动记忆**：自动记忆存在本机、不随换机器同步、还会撞 200 行/25 KB 上限；而 `CLAUDE.md` 的文本先后顺序也不能替代 CI 强制门禁。
3. **长 Skill 把硬性约束往前放**：压缩重附每个 Skill 只留前 5,000 token，放在末尾的检查项最容易在长任务中途消失。
4. **linked worktree 要么别建本地 `.claude/skills/`，要么完整维护**：哪怕一个空目录也会切断主 checkout 回退，排查时先确认缺的是记忆索引还是 Skill 清单。

## 回看开篇的四个问题

**1. 刚用 `Write` 和 `Edit` 改完记忆索引且全部报成功，为什么紧接着发出的请求里启动说明还是旧索引？**
启动时附上的 `MEMORY.md` 是一份定格快照，会话中途去改磁盘，Claude Code 不会回头改写这份启动说明（以免弄乱前面的缓存）；当前这一轮只能靠刚刚的 `Edit` 工具记录知道改了什么。只有关掉重启一个新进程，启动说明才会换上新索引；而详细内容所在的主题文件，还得等模型真的用 `Read` 打开后才会进入对话。

**2. `MEMORY.md` 写到 202 行时，为什么磁盘落盘、`tool_result` 报成功、请求里却同时冒出一条 `Error` 告警？**
这两件事各管各的：`Write` 工具只负责把 202 行完整写进磁盘，写成了就报成功；但写完之后另一道检查会盯着「下次启动最多只能读 200 行或 25 KB」，超标就另发一条系统告警，催模型把细节拆去主题文件。等重启截断时，告警里还会顺带引用被切掉的第 201 行，所以光靠全文搜索很容易看走眼。

**3. 为什么新建一个 Git linked worktree 能自动继承仓库的记忆索引，却可能因为多了一个空目录突然看不到主仓的 Skill？**
因为两者的查找规则不一样：自动记忆按仓库归属，同一台机器上同一个仓库的所有 worktree 共用同一份记忆；但项目 Skill 会先看当前 worktree 根目录有没有 `.claude/skills/`，**没有才去借用主仓的，只要本地建了这个目录——哪怕里面空无一物——借用立刻断掉**。

**4. 为什么 Skill 的正文在后续轮次还在对话里，它附带的 `allowed-tools` 免审批授权却已经过期了？**
因为「说明文字」和「工具授权」的寿命是分开算的：调出来的 Skill 正文会一直留在聊天记录里，甚至压缩后还会尽量重新附上前面一部分；但 `allowed-tools` 给的免确认特权只管调用它的这一轮，只要你发出下一条新消息，授权立刻收回。
