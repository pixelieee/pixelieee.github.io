**一句话结论：** Hermes 把经验拆进「每轮注入的极小记忆文件、按需检索的会话历史库、按需加载的 Skill」三类存储，靠前台自主写入、回合后后台复盘和 curator 定期归档来持续更新与清理，而整套设计最核心的约束只有一条：**不要弄脏 system prompt 的前缀缓存。**

读完这篇，你应该能回答六个问题：

1. 一条事实写进记忆之后，**什么时候**、**被谁**看到？
2. 后台复盘**什么时候**触发，为什么记忆和 Skill 的触发时机不一样？
3. 后台 Agent **能改什么、不能改什么**，改不了的去了哪里？
4. Skill 怎样从创建走到归档，**restore 之后为什么可能马上又被归档**？
5. 同一台机器上的 profile、项目和子 Agent 之间，**谁和谁共享**这些存储？
6. 前台会话**什么时候自己总结记忆和 Skill**，驱动它的原版 prompt 是什么、是常驻还是动态注入？

## 全景

<FigArch />

三类存储的差异决定了后面所有机制的形状：

| | 记忆文件 | 会话历史 | Skill |
|---|---|---|---|
| 位置 | `memories/MEMORY.md`、`USER.md` | `state.db` 的 `messages` 表 | `skills/<name>/SKILL.md` |
| 存什么 | 跨任务都成立的稳定事实 | 每一条消息，含工具调用与结果 | 某类任务的可复用做法 |
| 怎样进入模型 | 加载时全量取快照（仅去重与安全遮盖），注入 system prompt | 恢复会话时读取历史，模型可用 `session_search` 主动检索 | 清单进 system prompt，中途增删会在下一轮用户消息末尾通知，正文按需读 |
| 容量 | 默认 2200 / 1375 字符，可配置 | 不受记忆文件的字符预算限制 | 正文按需加载，由 curator 定期维护受管 Skill |
| 谁来写 | 前台模型、后台复盘 | 运行时自动写入 | 前台模型、后台复盘、curator |

这张表里最重要的一行是「怎样进入模型」。`MEMORY.md` 和 `USER.md` 会在每轮对话全量发给模型，所以体积必须很小；往期会话历史存在 `state.db` 里，开新对话时不会自动塞进上下文，只有模型主动调用 `session_search` 检索（或你手动恢复某条旧会话）时才去读，所以可以放心全量留存；Skill 介于两者之间，平时只有名字和一句描述常驻在 system prompt 里，正文内容由 Agent 按需读取。后面关于「什么该存在哪里」的规则，都从这一点推出来。

## 一条约束：不要弄脏前缀缓存

Hermes 把 system prompt 分成三档，按「重建时变化的可能性」从低到高排列：stable（身份、指引）、context（项目上下文）、volatile（Skill 目录、记忆、时间戳）。记忆被放在最后一档：

<CodeTr>

```python title="agent/system_prompt.py · 782–785"

# Skills are runtime-mutable, so the index leads the volatile band: on a longest-prefix
# backend an unchanged index stays inside the reused prefix; a changed one re-prefills from here.
volatile_parts: list[str] = [skills_prompt, *_memory_parts(agent)]
```

# 目录没变就仍落在复用的前缀里；目录变了，就从这里开始重新预填充。

## 记忆文件：小、冻结、可审计

### 格式、容量与安全扫描

`MEMORY.md` 和 `USER.md` 都是纯文本文件，里面按顺序存着一条条**记忆条目（entry）**，条目之间用**独占一行的 `§`**（源码分隔常量为 `"\n§\n"`）隔开。因为分隔符要求 `§` 必须单独占一整行，所以单条记忆可以自由跨多行，写在句子里的 `§`（比如「见 §3.2」）也只当普通文字，不会被误拆成两条：<Src p="tools/memory_tool_store.py" l="25" /> <Src p="tools/memory_tool_store.py" l="665-667" />

```text title="MEMORY.md 在磁盘上的实际格式（两条记忆条目示例）"
这个仓库使用 pnpm，不要运行 npm install。
§
发布前需值班人确认（详见规范 §3.2）。
单条记忆允许换行写多行。
```

`MEMORY.md` 记环境与约定，上限 2200 字符（官方配置注释约 800 token）；`USER.md` 记用户资料，上限 1375 字符（约 500 token）。<Src p="tools/memory_tool_store.py" l="186" /> <Src p="agent/agent_init.py" l="1336-1337" /> <Src p="cli-config.yaml.example" l="1034-1035" /> 之所以把两份文件合计压在约 1300 token 这么小的上限里，工具描述里的直接理由是记忆**每轮都会全量注入 system prompt**，必须保持高信噪比。<Src p="tools/memory_tool.py" l="376-377" /> <Infer />更深一层，用硬预算把记忆卡小，也是在结构上倒逼模型把长步骤和任务级经验分流进按需加载的 Skill、把细节留在会话历史里，避免 `MEMORY.md` 越滚越大。

两条保护措施体现了同一种态度：**出了问题要让人看得见，而不是悄悄处理掉。**

- 文件被手工改到超限时，加载**不截断**，只告警，并禁止继续添加，直到回到上限以内。<Src p="tools/memory_tool_store.py" l="246-252" />
- 每条 `entry` 在**写入时**和**加载时**都会过一遍本地威胁扫描（`tools/threat_patterns.py`，`scope="strict"`，不调模型，靠正则与不可见 Unicode 规则拦截提示词注入、凭据/上下文外泄、SSH 后门、篡改 `AGENTS.md`/配置及硬编码密钥）。写入时命中直接拒绝；如果是手工改盘或外部写入带进来的可疑条目，加载时在 system prompt 快照里会替换成 `[BLOCKED: …]`，**磁盘原文件不动**。注释的理由是：记忆会进入 system prompt，一条被投毒的条目会跨会话持续生效；静默丢弃则会把攻击藏起来，用户无从发现和删除。<Src p="tools/threat_patterns.py" l="1-94" /> <Src p="tools/memory_tool_store.py" l="28-31" /> <Src p="tools/memory_tool_store.py" l="221-253" />

### `memory` 工具：三种操作与原子批次

`memory` 工具通过 `target` 指定目标文件（`memory` 对应 `MEMORY.md`，`user` 对应 `USER.md`），只支持三种操作（`action`）：<Src p="tools/memory_tool.py" l="399-436" />

| 操作 | 必填参数 | 行为 |
|---|---|---|
| `add` | `content` | 追加一条新条目 |
| `patch` | `old_text`、`content` | 定位到包含 `old_text` 的条目，**只把命中的那一段**替换成 `content`，条目其余内容保留 |
| `remove` | `old_text` | 删除包含 `old_text` 的整条条目 |

（旧版整条覆盖式的 `replace` 已被显式拒绝。<Src p="tools/memory_tool.py" l="261-262" />）

只改一处时直接传上面的字段即可；如果要对同一文件做多项改动（尤其是文件写满后要先删旧、再加新），工具要求把它们放进一次调用的 `operations` 数组，原子执行，且**字符上限只检查整批执行完的最终结果**。单次 `add` 超限会返回现有条目，便于模型在下一轮打包合并；如果合并批次仍超限，整批不写入，错误只报告用量和原因。 <Src p="tools/memory_tool_store.py" l="322-336" /> <Src p="tools/memory_tool_store.py" l="578-598" />

```json title="批量 operations：一次调用先删旧再加新，只按最终结果检查字符上限"
{
  "target": "memory",
  "operations": [
    { "action": "remove", "old_text": "这个仓库用 npm" },
    { "action": "add", "content": "这个仓库用 pnpm，测试命令为 pnpm test。" }
  ]
}
```

只有一处改动时可以用单次写法：

```json title="单次 add"
{
  "target": "memory",
  "action": "add",
  "content": "这个仓库用 pnpm。"
}
```

```json title="单次 patch：只替换命中的那一段"
{
  "target": "memory",
  "action": "patch",
  "old_text": "这个仓库用 npm",
  "content": "这个仓库用 pnpm"
}
```

几条边界：

- `add` 去掉首尾空白后与已有条目完全相同就跳过；措辞不同则算新条目。<Src p="tools/memory_tool_store.py" l="369-388" />
- `patch` 和 `remove` 用 `old_text` 定位。命中多个**不同**条目返回 `ambiguous`；完全相同的重复条目不算歧义。`replace` 被明确拒绝。<Src p="tools/memory_tool_store.py" l="419-461" /> <Src p="tools/memory_tool.py" l="261-262" />
- 写入流程是加锁、重读文件、校验、写临时文件、原子替换。因为每次都先重读，两个同时运行的会话不会互相覆盖对方的写入。<Src p="tools/memory_tool_store.py" l="338-367" /> <Src p="tools/memory_tool_store.py" l="675-683" />
- 写入成功的返回值**故意不附上现有条目列表**。注释说把全部条目返回回去会诱导模型「再找点东西改」，重复发出同样的操作。<Src p="tools/memory_tool_store.py" l="623-636" />

### 什么该进记忆，什么该进 Skill

这是整套设计里最重要的一条分流规则，Hermes 在三处提示词里反复强调了三遍：`memory` 工具描述、system prompt 里的常驻指引、后台复盘提示词。<Src p="tools/memory_tool.py" l="375-398" /> <Src p="agent/prompt_builder.py" l="192-230" /> <Src p="agent/background_review.py" l="370-388" /> 下面这张表，归纳的就是这三处提示词**写给模型看的分流标准、典型内容与写法要求**：

| | 进记忆（`MEMORY.md` / `USER.md`） | 进 Skill（`SKILL.md`） | 都不进（跳过） |
|---|---|---|---|
| 判断标准 | 不管做什么任务、每次会话都成立 | 只在做某类任务时才有用 | 很快会过时，或随时能重新查到 |
| 提示词列出的典型内容 | 用户是谁、稳定的环境事实、不归属具体任务的长期约定 | 具体操作步骤、踩过的坑、用户对**这类任务**的偏好与纠正 | 任务进度、完成记录、临时待办 |
| 写法 / 处理方式 | 用陈述句（源码示例：「用户偏好简短回答」✓），不用祈使句（「永远简短回答」✗），免得日后覆盖用户当下的要求 | 按顺序写成可执行的步骤与避坑规则 | 不写入任何长期文件，留在会话历史里，需要时用 `session_search` 找 |

理由写在工具描述里：记忆**每一轮都会注入**，所以必须小；Skill 只在相关时才加载。这也解释了一个初看反直觉的选择：「用户对 TypeScript 任务的纠正」进的是 Skill，而不是 `USER.md`。同一事实也不该两处都写，注释说那样会让两个文件都更快顶到上限。

## 会话历史与 `session_search`

`state.db` 保存会话消息。模型需要主动找回旧对话时，可以用 `session_search`，其中关键词查询使用 SQLite FTS5，**不调用 LLM**。返回内容取自库里的消息，单条长消息会按模式截短（检索头尾预览 1,200 字符、`read` 模式 2,000 字符、`scroll` 展开 4,000 字符；注释 `#114344` 记过未限长前一次 `read` 吐出 74K 字符、一步把请求从 ~50K 推到 ~89K token 的事故）。除了给模型检索，你在终端执行 `hermes --resume` 或 `/resume` 恢复历史对话时，CLI 也是从这个数据库把旧会话消息完整加载回来。 <Src p="tools/session_search_tool.py" l="2-8" /> <Src p="tools/session_search_tool.py" l="34-40" /> <Src p="tools/session_search_tool.py" l="447-462" /> <Src p="hermes_cli/cli_agent_setup_mixin.py" l="620-630" />

Hermes 的整套内置会话存储与检索层（根目录下的 `hermes_state*.py` 模块，含 `hermes_state_fts.py`、`hermes_state_search.py` 与 `tools/session_search_tool.py`）里，**没有任何向量索引或 embedding 检索代码**——也就是说，内置的 `session_search` 纯粹是本地 SQLite 词法检索，零模型调用、离线可用，但也不做语义向量匹配（如需语义/向量记忆，需额外接入 `memory.provider` 外部记忆插件）。<Infer />源码没有注释解释内置搜索为何不用向量；这个工具要找回的是用户原话、文件名和命令输出，精确词法匹配往往比语义相似更直接，也省掉了维护 embedding 模型和额外调用的开销。

几处细节：

- 默认只搜 `user` 和 `assistant`，显式传 `role_filter="tool"` 才搜工具结果。<Src p="tools/session_search_tool.py" l="330-385" /> 中文这类不靠空格分词的文本另有一张 trigram 索引，但工具消息被排除在外：注释估计 trigram 索引约为原文体积的 2.6 倍，而工具输出占消息字节的约 90%。<Src p="hermes_state_common.py" l="1025-1039" />
- `scroll` 按数据库中的消息顺序读取锚点和前后各 `window` 行，默认 5，可设为 1 到 20，结果可以包含工具输出。同一会话谱系中，仍在当前上下文里的锚点会被拒绝；压缩移出上下文的旧消息、因压缩结束的父会话和 `/new` 前的会话仍可读取。 <Src p="tools/session_search_tool.py" l="521-548" /> <Src p="tools/session_search_tool.py" l="763-770" />
- `read` 模式只传 `session_id`，超过 30 条消息时返回最早 20 条和最近 10 条，单条内容也有长度上限。<Src p="tools/session_search_tool.py" l="447-462" />

注意 `window` 数的是**行**，不是对话轮次。你只说一句「找出 pnpm 版本」，库里就可能有四行：用户提问、助手发出工具调用、工具返回、助手作答。一条助手消息发出两个工具调用时，助手只占一行，两个工具返回各占一行。<Src p="hermes_state_common.py" l="531-538" />

## Skill：按需加载的做法

### 发现与读取

一个 Skill 以 `SKILL.md` 为入口，文件头有 `name` 和 `description`。system prompt 里只放一份目录：每个 Skill 的 `load_name`（就是传给 `skill_view` 的 `name`）和一句描述，标成 `[names only]` 的类别连描述也省去。<Src p="agent/prompt_builder.py" l="1309-1372" /> 正文由模型用 `skill_view` 按需打开，传 `file_path` 可读附带文件。<Src p="tools/skills_tool.py" l="592-694" />

这就是 Skill 能比记忆「大」的原因：它的常驻成本只有目录里的一行。

### 前台什么时候写（以及常驻的原始 prompt）

前台会话**没有定时器，也不会在对话中途往用户消息里动态塞提醒**（后文会看到，早期动态插提醒污染了 43% 的用户消息，才在提交 `45058b4105` 里被拆掉改成后台复盘）。前台模型全靠**会话启动时一次性写进 system prompt 与工具声明（`tools[]`）里的常驻指引**，在对话过程中自己判断时机直接调用 `memory` 或 `skill_manage`（用户也可以随时用 `/learn` 或直接要求保存）。

具体落在 system prompt 的三处常驻区块（加上 `memory` 与 `skill_manage` 工具自身的 schema 描述）：

- **`stable` 档 · 记忆与分流指引**（<Src p="agent/prompt_builder.py" l="192-230" />，排在最前、每轮不变以保前缀缓存）；

### curator：只归档，不删除

`curator` 是 Skill 库的维护任务，模块开头写着它的底线：**never delete, only archive (recoverable)**。<Src p="agent/curator.py" l="1-7" />

### 整合：默认关闭

`curator.consolidate` 默认关闭。开启并且有候选时，curator 另起一个只带 `skills` 工具集的 Agent，关掉记忆、跳过项目上下文文件。<Src p="agent/curator.py" l="1105-1140" /> 它拿到的是候选列表和使用统计，再按需读正文，**不读用户的对话历史**。提示词要求按**内容**判断重叠而不是按使用次数，倾向于合并成一个类级别的「伞形」Skill，并把归档称为它能做的最具破坏性的操作。<Src p="agent/curator.py" l="296-337" />

对受管 Skill，一次使用或修补会刷新活动时间，推迟 `stale` 或归档。启用整合后，内容重叠的 Skill 还可能被合并；已归档的 Skill 可以用 `restore` 放回活动目录。

## Background Review：把三者串起来

前台模型可能忘了存。Background Review 是兜底：回合结束后另起一个临时 Agent，回看这一段对话，决定往记忆或 Skill 里写什么。

### 什么时候触发

两种存储用两套计数，单位不同，**判断时机也不同**：

| | 记忆复盘 | Skill 复盘 |
|---|---|---|
| 计什么 | 用户轮 | 模型请求（内部步骤） |
| 默认阈值 | 10（`memory.nudge_interval`） | 10（`skills.creation_nudge_interval`） |
| 何时累加 | 每来一条用户消息 | 每准备一次模型请求 |
| **何时决定要不要复盘** | **回合开头** | **回合结尾** |
| 跨回合 | 累计，不按回合清零 | 累计，不按回合清零 |

### fork：为缓存而生的临时 Agent

`build_cache_parity_fork()` 新建的临时 `AIAgent` 有几个刻意的设计：<Src p="agent/background_review.py" l="965-1005" />

- **与父会话共用 `session_id`。** 使用同一模型时，fork 还继承父会话的缓存提示词和工具列表，以便复用前缀；换用其他模型时会构建自己的提示词。 <Src p="agent/background_review.py" l="1003-1018" />
- **与父会话共用同一个 `MemoryStore` 对象**，所以它写入的记忆和前台写入的是同一份状态。<Src p="agent/background_review.py" l="992" />
- **持久化完全断开**，不写 `state.db`。注释记录了不这样做的后果：共用 `session_id` 的 fork 会把自己的「复盘指令」写进真实会话，下一轮用户对话会把它当成常驻指令读回来。
- **记忆和 Skill 的复盘间隔都设为零**，关闭这两种自动触发；复盘最多跑 16 轮。 <Src p="agent/background_review.py" l="173" /> <Src p="agent/background_review.py" l="992-995" />
- 使用 Hermes 托管的本地 `llama-server` 时，任务进入**空闲队列**，等本机没有进行中的聊天回合、本地模型空闲时才取出，最长等 30 分钟。理由是复盘会占住 GPU，而下一轮用户请求一到又会把它取消，解码成本白付。<Src p="agent/review_idle_queue.py" l="1-42" /> <Src p="agent/review_idle_queue.py" l="126-142" />

### 审批：暂存而不是拒绝

后台复盘的提示词原本只要求模型做 `add`（新增），但 `memory` 工具描述里自带「写满时立即整理（consolidate now）」的指引；为了防止自动运行的 fork 顺着这条指引在无人审阅的情况下删改旧条目（源码注释关联 `#105921`），Hermes 在工具派发白名单之外又加了第二道闸门：自动复盘提交 `patch` 或 `remove` 时不直接改盘，而是返回 `staged: true` 和 `pending_id`，等用户用 `/memory pending` 查看、`/memory approve <id>` 由 CLI 本地命令重放落盘。为什么选择暂存而不是直接拒绝，docstring 讲得最清楚：

### 提示词的倾向

两份复盘提示词的语气有意不对称。记忆那份是中性的，按「一个事实只存一处」的规则引导选文件：`USER.md` 写 who the user is，`MEMORY.md` 写 facts about the ENVIRONMENT you operate in。<Src p="agent/background_review.py" l="370-388" /> Skill 那份明显更积极：要求从对话里提炼可复用的技巧和纠正，并特别注明 `Nothing to save.` **不应该是默认答案**。<Src p="agent/background_review.py" l="448-518" /> 结合上面的工具限制，后台的整体倾向很清楚：**Skill 尽量多写，记忆只增不删。**

## 作用域：profile、项目与委派

### profile 是存储的边界

记忆按 profile 保存，位置由 `HERMES_HOME` 决定：默认 profile 是 `~/.hermes`，具名 profile 是 `~/.hermes/profiles/<名字>`。<Src p="tools/memory_tool.py" l="38-40" /> <Src p="website/docs/user-guide/profiles.md" l="401-433" /> 同一 profile 的所有会话共享同一对文件，**不按项目、工作目录、用户 ID 或角色分文件**。换工作目录只改变工作位置，换 profile 才换文件。

一个例外：`profile create --clone` 会把 `MEMORY.md` 和 `USER.md` 复制进新 profile，文档的理由是记忆被当作 Agent 身份的一部分，和 `SOUL.md` 一样。<Src p="website/docs/user-guide/profiles.md" l="83" />

历史库也按 profile 划分。`session_search` 默认只查当前 profile 的 `state.db`；显式传 `profile` 时，以**只读**方式打开另一个 profile 的库。<Src p="tools/session_search_tool.py" l="434-444" /> profile 只是存储的边界，**不是沙箱**，文件权限和工具授权另算。

### Skill 的四层查找，与不对称的写入

查找顺序是：受信任的项目目录 → 当前 profile 的 `$HERMES_HOME/skills` → `skills.create_dir` → `skills.external_dirs`，同名时前者覆盖后者。<Src p="agent/skill_utils.py" l="398-420" />

项目层有一道信任门：只有项目根在 `skills.trusted_project_dirs` 里，才会扫描最近 Git 根下的 `.hermes/skills/` 和 `.agents/skills/`。注释的理由很直接：项目里的 Skill 是提示注入的入口，不能因为克隆了一个仓库就自动加载；用户主目录本身也不会被当作项目根，以免点文件仓库被误认。<Src p="agent/skill_utils.py" l="507-596" />

写入却是**不对称**的：

- **新建**写当前 profile；配置了 `skills.create_dir` 时写那个目录。<Src p="tools/skill_manager_tool.py" l="200-208" />
- **修改**查找目标时排除项目层，所以项目 Skill **从不被改写**。<Src p="agent/skill_utils.py" l="423-426" />

后果是：模型读的是项目版，再用同名 `name` 提交修改，命中的可能是 profile 里的同名副本，而我没有找到任何给模型的提示。

### 委派不会创造新的记忆层

`delegate_task` 起的子 Agent 有自己的会话，和父会话存在同一个数据库里，用 `parent_session_id` 关联。<Src p="tools/delegate_tool.py" l="124-152" /> 它的记忆被**硬编码**关掉（`skip_memory=True`），委派工具表里也屏蔽了 `memory`，注释写的是 “no writes to shared MEMORY.md”。<Src p="tools/delegate_tool.py" l="289-308" /> <Src p="tools/delegate_tool_toolsets.py" l="14-22" />

想让不同角色各有长期记忆，就要为它们分别建 profile、分别运行。开启 `profile_routes` 的委派可以让子 Agent 使用另一个 profile 的环境、凭据和 Skill，但它仍然是子 Agent，记忆限制不变。<Src p="tools/delegate_tool_routes.py" l="111-153" />

## 设计评价

### 做得好的地方

1. **复用缓存时也有办法传递变化。** 记忆快照和 Skill 目录可以随同一段提示词反复发送，新增 Skill 则在下一轮消息末尾告知模型。同模型的复盘沿用父会话前缀，工具权限在派发时检查。
2. **默认可逆。** 记忆超限不截断，可疑条目只遮盖不删除，Skill 只归档不删除，后台的删除意图暂存而不是丢弃。出了问题，用户总能看见、总能撤回。
3. **分工有明确判据。** 「每轮都要注入，所以必须小」这一条，同时决定了记忆和 Skill 的边界、两份提示词的语气，以及后台工具的范围，而不是交给模型凭感觉。
4. **失败时收紧而不是放开。** 暂存失败就退化为拒绝；由 Skill 计数触发的复盘拿不到 `memory`；项目 Skill 必须显式信任。

### 值得警惕的地方

以下是我的判断，不是源码事实。

1. **记忆会饱和，而后台无力清理。** 后台复盘只能 `add`；文件写满后，`add` 被拒绝，腾空间所需的 `remove` 和 `patch` 又要人批准。清理只能等前台模型下一次主动添加时被拒、顺手合并，或者用户去处理 `/memory pending`。如果大部分记忆都由后台写入，它很可能长期停在第一次写满时的样子。
2. **触发时机难以预测。** 两套计数单位不同、决定时机不同，前台写入还会清零计数，很难事先说清一次具体对话会不会触发复盘。这对用户无所谓，对调试和评测却是个麻烦。
3. **并发会话可能使用不同的记忆快照。** 同一 profile 共享磁盘文件。一方写入记忆后，另一方仍可能按旧 system prompt 回答，直到自己的提示词重建。
4. **restore 不重置时钟**，见上面的实验。
5. **同名 Skill 的修改会悄悄落到 profile 副本上。** 项目层和 profile 层同名时，`skill_manage` 改的是 profile 版，模型和用户都可能以为改的是项目版。
6. **字符上限是一个粗粒度的约束。** 它守住了 prompt 的大小，但不区分条目的价值：一条关键约定和一条可有可无的偏好，占用同样的预算。

## 回看开篇的六个问题

**1. 一条事实写进记忆之后，什么时候、被谁看到？**
刚写完时，当前会话里的模型只能从这次 `memory` 工具的返回结果里知道写成功了；system prompt 在启动时已经锁死（为了复用前缀缓存），不会跟着更新，要等到触发上下文压缩、切换或恢复会话，或者新开一个对话时，才会从磁盘重读新内容。后台复盘和当前会话共用同一份内存里的 `MemoryStore`，能立刻看到；同时开着的另一个会话窗口也一样，除非它自己发生压缩或切换会话，否则会一直沿用启动时的旧快照。

**2. 后台复盘什么时候触发，为什么记忆和 Skill 的触发时机不一样？**
两者都要等模型正常回复完用户、没被打断后才在后台启动（定时任务 `cron` 这类非交互式执行会直接跳过后台复盘——源码注释称一次复盘大约消耗 3 万 token，而无真人互动的场景收益很低 <Src p="agent/turn_finalizer.py" l="778-786" />）。区别在于计数单位和「决定要不要跑」的时间点：
- **记忆复盘（默认每 10 条用户消息）**：你每发一条消息，计数就加 1（不管模型后面调多少次工具，一条用户消息只算 1 次）。所以刚收到第 10 条用户消息时，系统就已经确定「这一轮答完后要跑记忆复盘」——就算接下来模型在回复过程中自己调用了 `memory` 工具，也不会取消这次复盘。
- **Skill 复盘（默认每 10 次模型请求）**：一条用户消息里，模型可能来回调多次工具，每次发给模型的请求都算 1 次。刚收到消息时还不知道这轮一共会调几次，只能等整轮回复结束前再检查总数够不够 10；如果中途模型自己调用了 `skill_manage`，计数会当场清零、从 0 重新数。

**3. 后台 Agent 能改什么、不能改什么，改不了的去了哪里？**
发给模型的 `tools[]` 工具声明列表保持与父会话逐字节一致（为了保住前缀缓存），真正的限制发生在**工具派发阶段的白名单拦截**：
- **对 Skill**：派发白名单默认只放行只读文件工具（`read_file`、`search_files`）和 Skill 工具（`skills_list`、`skill_view`、`skill_manage`）。如果要修改已有的 Skill，后台复盘必须先在本次运行里用 `skill_view` 或 `read_file` 把对应文件实际读一遍，否则直接拒绝（防止只凭聊天记录里的印象盲改）。
- **对记忆**：后台复盘的提示词原本只要求它做 `add`（新增），但 `memory` 工具描述里自带「写满时立即整理（consolidate now）」的提示；为了防止自动运行的后台 fork 顺着这条提示删掉没人审阅过的旧条目（源码注释关联 `#105921` <Src p="agent/background_review.py" l="1094-1098" />），Hermes 设了两道闸门：第一，仅由 Skill 计数触发的复盘，派发白名单直接不含 `memory`，只有开启了记忆且触发了记忆复盘（单触发、双触发或用户手动执行 `/refine`）才放行 `memory`；第二，即便放行了 `memory`，自动触发的后台复盘（区别于手动 `/refine`）也**只能直接执行 `add`**，提交的 `patch` 和 `remove` 会被拦截并暂存到 `/memory pending`——之所以「暂存」而不是「直接拒绝」，是因为后台 fork 的总结不会返回给主对话，直接拒绝会让这次整理请求彻底丢失、用户无从得知 <Src p="tools/memory_tool.py" l="179-186" />。等你执行 `/memory approve <id>` 后，由 **CLI 本地命令直接重放写入磁盘**（不再调用前台或后台模型；如果不执行命令，待批记录就一直留在磁盘上不会生效）。

**4. Skill 怎样从创建走到归档，restore 之后为什么可能马上又被归档？**
后台复盘创建的 Skill（以及你手动托管给 curator 的 Skill）会按 `.usage.json` 记录最近一次活动时间：14 天无活动标成陈旧（`stale`，此时仍在目录里可用），30 天无活动转为归档（`archived`）并移入 `skills/.archive/`，默认不真删。问题在于 `restore` 恢复时只把目录移回原位、把状态改回 `active`，**没有重置最近活动时间**；如果你恢复后没通过 `skill_view` 读取或修补它，下一次定时或手动 curator 检查看到它还是 30 天前的旧时间，就会立刻再次归档。

**5. 同一台机器上的 profile、项目和子 Agent 之间，谁和谁共享这些存储？**
- **记忆与会话历史按 profile 共享、不分项目**：同一 profile 下切到别的工作目录干活，依然共用同一份 `MEMORY.md` / `USER.md` 和 `state.db`；只有切换 profile 才会换存储。
- **Skill 按层叠加读取，但 `skill_manage` 永不改动项目目录**：读取时会叠加受信任的项目目录（最近 Git 根下的 `.hermes/skills/`、`.agents/skills/`）和当前 profile 目录（`$HERMES_HOME/skills/`，项目优先）；但通过 `skill_manage` 新建或修改 Skill 时永远跳过项目层（新建只写 `$HERMES_HOME/skills/` 或配置的 `skills.create_dir`，同名修改会落到 profile 副本；前台若按用户要求用普通文件工具直接改仓库里的 `SKILL.md`，则不受 `skill_manage` 限制）。
- **子 Agent 彻底不能用记忆功能**：所有通过 `delegate_task` 派出的子 Agent 虽然会把对话写进同一个 `state.db`，但记忆子系统被硬编码关闭——**既不注入记忆，也不能调用 `memory` 工具**（哪怕跨 profile 委派，也只带上目标的 `SOUL.md` 身份和 Skill，依然不带记忆）。

**6. 前台会话什么时候自己总结记忆和 Skill，驱动它的原版 prompt 是什么、是常驻还是动态注入？**
前台**没有定时器，也不在对话中途往用户消息里动态插提醒**（早期插提醒的写法污染了 43% 的用户消息，已在提交 `45058b4105` 中改为回合后后台复盘）。前台全靠模型自己随时决定并调用 `memory` / `skill_manage`（或由用户主动用 `/learn` / 口头要求保存），驱动它的指引在会话启动时一次性写进 **system prompt**（`stable` 档的 `build_memory_guidance` 与 `SKILLS_GUIDANCE`，加上 `volatile` 档 `## Skills` 清单段上方）以及 `tools[]` 工具描述里，**全程常驻、每轮不变**，既能让前台随时记录，又不破坏前缀缓存（三段原文见上文「前台什么时候写」）。 <Src p="agent/prompt_builder.py" l="192-230" /> <Src p="agent/prompt_builder.py" l="257-264" /> <Src p="agent/prompt_builder.py" l="1362-1375" />
