**一句话结论：** Hermes 把「学到的东西」分进三类存储：两个很小、每轮都注入的 Markdown 文件，一个全量但只按需检索的历史库，一组按需加载的 Skill。往里写的路径也有三条：前台模型自己写、回合结束后的后台复盘、每周一次的 Skill 库维护。这套设计里大部分看似别扭的地方，都能用同一条约束解释：**不要弄脏 system prompt 的前缀缓存。**

读完这篇，你应该能回答五个问题：

1. 一条事实写进记忆之后，**什么时候**、**被谁**看到？
2. 后台复盘**什么时候**触发，为什么记忆和 Skill 的触发时机不一样？
3. 后台 Agent **能改什么、不能改什么**，改不了的去了哪里？
4. Skill 怎样从创建走到归档，**restore 之后为什么可能马上又被归档**？
5. 同一台机器上的 profile、项目和子 Agent 之间，**谁和谁共享**这些存储？

## 全景

<FigArch />

三类存储的差异决定了后面所有机制的形状：

| | 记忆文件 | 会话历史 | Skill |
|---|---|---|---|
| 位置 | `memories/MEMORY.md`、`USER.md` | `state.db` 的 `messages` 表 | `skills/<name>/SKILL.md` |
| 存什么 | 跨任务都成立的稳定事实 | 每一条消息，含工具调用与结果 | 某类任务的可复用做法 |
| 怎样进入模型 | 会话开始时整体注入 system prompt | 从不自动注入，靠 `session_search` 查 | 目录进 prompt，正文靠 `skill_view` 按需读 |
| 容量 | 2200 / 1375 字符硬上限 | 不限 | 不限，由 curator 定期维护 |
| 谁来写 | 前台模型、后台复盘 | 运行时自动写入 | 前台模型、后台复盘、curator |

这张表里最重要的一行是「怎样进入模型」。记忆每轮都在，所以必须小；历史从不自动出现，所以可以全量；Skill 介于两者之间，平时只露出名字和一句描述。后面关于「什么该存在哪里」的规则，都从这一点推出来。

## 一条约束：不要弄脏前缀缓存

Hermes 把 system prompt 分成三档，按「重建时变化的可能性」从低到高排列：stable（身份、指引）、context（项目上下文）、volatile（Skill 目录、记忆、时间戳）。记忆被放在最后一档：

<CodeTr>

```python title="agent/system_prompt.py · 782–785"

# Skills are runtime-mutable, so the index leads the volatile band: on a longest-prefix
# backend an unchanged index stays inside the reused prefix; a changed one re-prefills from here.
volatile_parts: list[str] = [skills_prompt, *_memory_parts(agent)]
```

同一个目标在代码里至少出现了五次，每次都有注释写明理由：

- **记忆冻结**：会话中途写入不改 prompt，上面已经看到。
- **记忆排在最后**：让前面的 stable 部分成为可复用的最长前缀。
- **后台复盘复制父会话的 `tools[]`**，沿用同一个 `session_id`。注释称之为 “warm prompt-cache parity”，估计能省约 26% 成本。<Src p="agent/background_review.py" l="965-1008" />
- **后台只在派发时限制工具**，发给模型的工具列表保持字节一致。<Src p="agent/background_review.py" l="1088-1092" />
- **刷新只发生在本来就要重建 prompt 的时刻**：上下文压缩之后、会话切换或恢复时。<Src p="agent/system_prompt.py" l="814-832" />

读源码时可以用这条线预测行为：**任何会改变已发送前缀的动作，都会被推迟到压缩或新会话这类本来就要重建 prompt 的时刻。**

## 记忆文件：小、冻结、可审计

### 格式、容量与安全扫描

两个文件各是一串 `entry`，用独占一行的 `§` 分隔。常量是 `"\n§\n"`，所以不在行首行尾的 `§` 只是普通文字；一个 `entry` 可以跨多行。<Src p="tools/memory_tool_store.py" l="25" /> <Src p="tools/memory_tool_store.py" l="665-667" />

`MEMORY.md` 记环境与约定，上限 2200 字符；`USER.md` 记用户资料，上限 1375 字符。<Src p="tools/memory_tool_store.py" l="186" /> <Src p="agent/agent_init.py" l="1336-1337" /> <Infer />限制用字符数而不是 token 数，源码没有解释；字符数与分词器无关、计数便宜，是合理的理由。

两条保护措施体现了同一种态度：**出了问题要让人看得见，而不是悄悄处理掉。**

- 文件被手工改到超限时，加载**不截断**，只告警，并禁止继续添加，直到回到上限以内。<Src p="tools/memory_tool_store.py" l="246-252" />
- 每条 `entry` 加载时都会过一遍威胁扫描。命中的条目在 prompt 里显示为 `[BLOCKED: …]`，**文件原文不动**。注释的理由是：记忆会进入 system prompt，一条被投毒的条目会跨会话持续生效；静默丢弃则会把攻击藏起来，用户无从发现和删除。<Src p="tools/memory_tool_store.py" l="221-253" />

### `memory` 工具：一次调用，一个原子批次

工具描述本身就是一份设计说明。它要求把对同一文件的所有改动放进一次调用的 `operations` 数组，原子执行，**字符上限只检查最终结果**。这样一次调用就能「删掉旧条目腾出空间，再加新条目」，不会因为中间状态超限而失败。添加被拒绝时，工具会把现有条目全部返回，提示模型重发一个合并批次。<Src p="tools/memory_tool.py" l="375-445" />

只有一处改动时可以用单次写法：

```json title="单次 add"
{
  "target": "memory",
  "action": "add",
  "content": "这个仓库用 pnpm。"
}
```

```json title="单次 patch：只替换命中的那一段"
{
  "target": "memory",
  "action": "patch",
  "old_text": "这个仓库用 npm",
  "content": "这个仓库用 pnpm"
}
```

几条边界：

- `add` 去掉首尾空白后与已有条目完全相同就跳过；措辞不同则算新条目。<Src p="tools/memory_tool_store.py" l="369-388" />
- `patch` 和 `remove` 用 `old_text` 定位。命中多个**不同**条目返回 `ambiguous`；完全相同的重复条目不算歧义。`replace` 被明确拒绝。<Src p="tools/memory_tool_store.py" l="419-461" /> <Src p="tools/memory_tool.py" l="261-262" />
- 写入流程是加锁、重读文件、校验、写临时文件、原子替换。因为每次都先重读，两个同时运行的会话不会互相覆盖对方的写入。<Src p="tools/memory_tool_store.py" l="338-367" /> <Src p="tools/memory_tool_store.py" l="675-683" />
- 成功返回**故意不回显条目列表**。注释说回显会诱导模型「再找点东西改」，重复发出同样的操作。<Src p="tools/memory_tool_store.py" l="623-636" />

### 什么该进记忆，什么该进 Skill

这是整套设计里最重要的一条规则，它在三个地方各说了一遍：工具描述、system prompt 里的指引、后台复盘的提示词。<Src p="tools/memory_tool.py" l="375-398" /> <Src p="agent/prompt_builder.py" l="192-230" /> <Src p="agent/background_review.py" l="370-388" />

| | 进记忆 | 进 Skill | 都不进 |
|---|---|---|---|
| 判据 | 不管做什么任务都成立 | 只在做某类任务时有用 | 很快会过时，或随时能重新查到 |
| 例子 | 用户是谁、稳定的环境事实、长期约定 | 具体步骤、踩过的坑、用户对**这类任务**的偏好与纠正 | 任务进度、完成记录、临时待办 |
| 写法 | 陈述句：「用户偏好简短回答」 | 可执行的步骤 | 留在会话历史，用 `session_search` 找 |

理由写在工具描述里：记忆**每一轮都会注入**，所以必须小；Skill 只在相关时才加载。这也解释了一个初看反直觉的选择：「用户对 TypeScript 任务的纠正」进的是 Skill，而不是 `USER.md`。同一事实也不该两处都写，注释说那样会让两个文件都更快顶到上限。

## 会话历史与 `session_search`

记忆只放得下几十条最精炼的事实，其余的一切都在 `state.db` 里。`session_search` 是取回它们的唯一入口：用 SQLite FTS5 检索 `messages` 表，**不调用任何 LLM**，返回的全是数据库里的原始消息。<Src p="tools/session_search_tool.py" l="2-8" />

我在 `hermes_state*` 里没有找到任何向量或 embedding 相关的代码，所以「为什么不用向量检索」没有注释可引。<Infer />这个工具要找回的是用户原话和命令输出，精确匹配比语义相似更重要，也省掉一次模型调用。

几处细节：

- 默认只搜 `user` 和 `assistant`，显式传 `role_filter="tool"` 才搜工具结果。<Src p="tools/session_search_tool.py" l="330-385" /> 中文这类不靠空格分词的文本另有一张 trigram 索引，但工具消息被排除在外：注释估计 trigram 索引约为原文体积的 2.6 倍，而工具输出占消息字节的约 90%。<Src p="hermes_state_common.py" l="1025-1039" />
- `scroll` 模式围绕命中行读取：`window` 默认 5，**限制在 1 到 20 之间**，返回中心行加前后各最多 5 行，按数据库行顺序，可以带回工具结果。<Src p="tools/session_search_tool.py" l="763-770" /> <Src p="hermes_state_messages.py" l="1407-1424" /> 锚点在**当前会话谱系**内的请求会被拒绝，那部分本来就在上下文里。<Src p="tools/session_search_tool.py" l="542-543" />
- `read` 模式只传 `session_id`，超过 30 条消息时返回最早 20 条和最近 10 条，单条内容也有长度上限。<Src p="tools/session_search_tool.py" l="447-462" />

注意 `window` 数的是**行**，不是对话轮次。你只说一句「找出 pnpm 版本」，库里就可能有四行：用户提问、助手发出工具调用、工具返回、助手作答。一条助手消息发出两个工具调用时，助手只占一行，两个工具返回各占一行。<Src p="hermes_state_common.py" l="531-538" />

## Skill：按需加载的做法

### 发现与读取

一个 Skill 以 `SKILL.md` 为入口，文件头有 `name` 和 `description`。system prompt 里只放一份目录：每个 Skill 的 `load_name`（就是传给 `skill_view` 的 `name`）和一句描述，标成 `[names only]` 的类别连描述也省去。<Src p="agent/prompt_builder.py" l="1309-1372" /> 正文由模型用 `skill_view` 按需打开，传 `file_path` 可读附带文件。<Src p="tools/skills_tool.py" l="592-694" />

这就是 Skill 能比记忆「大」的原因：它的常驻成本只有目录里的一行。

### 前台什么时候写

- **创建**：`skill_manage` 可用时，prompt 里有一句指引，要求模型在摸索出非平凡的流程后用 `skill_manage` 记下来；困难或反复试错的任务结束时，还会提示模型主动提议保存。<Src p="agent/prompt_builder.py" l="257-264" /> <Src p="agent/prompt_builder.py" l="1362-1375" />
- **修补**：加载的 Skill 漏了步骤或命令有误时，指引要求模型**在结束前**用 `skill_manage(action='patch')` 修订，不等用户开口。

这些写入默认直接生效；开启 `skills.write_approval` 后改为暂存待批，前台和后台都一样。<Src p="tools/write_approval.py" l="1-10" /> 由 `skill_manage` 创建的 Skill 会被打上 `created_by: agent`，这是它进入 curator 管理范围的唯一途径，从不按目录位置推断。<Src p="tools/skill_usage.py" l="1-6" />

### curator：只归档，不删除

`curator` 是 Skill 库的维护任务，模块开头写着它的底线：**never delete, only archive (recoverable)**。<Src p="agent/curator.py" l="1-7" />

它的运行规则比想象中保守：

- **首次调用不执行。** 没有 `last_run_at` 时，第一次调用只把它记成当前时间就返回，所以刚装好要等满一个间隔才会真正运行。<Src p="agent/curator.py" l="169-176" />
- **间隔默认 168 小时**；调用方传入空闲时长时，还要求至少空闲 2 小时。<Src p="agent/curator.py" l="31-35" /> <Src p="agent/curator.py" l="1198-1207" />
- **只管 Agent 创建的 Skill。** 用户自己写的不碰；内置 Skill 只有开启 `curator.prune_builtins` 才可能被归档；置顶（pinned）和被 cron 引用的 Skill 跳过。<Src p="tools/skill_usage.py" l="618-628" /> <Src p="agent/curator.py" l="216-230" />
- **按活动时间判断。** 活动时间取 `last_used_at`、`last_viewed_at`、`last_patched_at` 中最新的一个，存在旁路文件 `.usage.json` 里，没有记录时退回 `created_at`。遥测放在旁路文件，是为了不污染用户手写的 `SKILL.md`。<Src p="tools/skill_usage.py" l="121-127" />

三点值得注意：`active` 超过 30 天可以**直接**归档，不必先经过 `stale`；`stale` 在代码里没有被排除出目录，所以仍然可用；归档条件只看「时间够久、当前不是 archived」，**不看它是不是刚被 restore 回来**。最后这一点会在后面的实验里出问题。

### 整合：默认关闭

`curator.consolidate` 默认关闭。开启并且有候选时，curator 另起一个只带 `skills` 工具集的 Agent，关掉记忆、跳过项目上下文文件。<Src p="agent/curator.py" l="1105-1140" /> 它拿到的是候选列表和使用统计，再按需读正文，**不读用户的对话历史**。提示词要求按**内容**判断重叠而不是按使用次数，倾向于合并成一个类级别的「伞形」Skill，并把归档称为它能做的最具破坏性的操作。<Src p="agent/curator.py" l="296-337" />

把这些串起来，一个 Skill 的一生是：**创建 → 使用中被修补**（修补会刷新活动时间，推迟变成 `stale`）**→ 积累后被整合 → 长期无人问津被归档 → 必要时 restore。**

## Background Review：把三者串起来

前台模型可能忘了存。Background Review 是兜底：回合结束后另起一个临时 Agent，回看这一段对话，决定往记忆或 Skill 里写什么。

<FigReview />

### 什么时候触发

两种存储用两套计数，单位不同，**判断时机也不同**：

| | 记忆复盘 | Skill 复盘 |
|---|---|---|
| 计什么 | 用户轮 | 模型请求（内部步骤） |
| 默认阈值 | 10（`memory.nudge_interval`） | 10（`skills.creation_nudge_interval`） |
| 何时累加 | 每来一条用户消息 | 每准备一次模型请求 |
| **何时决定要不要复盘** | **回合开头** | **回合结尾** |
| 跨回合 | 累计，不按回合清零 | 累计，不按回合清零 |

出处：<Src p="agent/turn_context.py" l="758-767" /> <Src p="agent/turn_iteration_prep.py" l="165-167" /> <Src p="agent/agent_init.py" l="1386-1390" /> <Src p="agent/turn_context.py" l="600-602" />

用一个例子区分两种单位。你只说了一句「修好测试」：模型先读两个文件（第 1 步），拿到内容后决定跑测试（第 2 步），看到结果后直接作答（第 3 步，没有工具调用也算）。这是 **1 个用户轮、3 个内部步骤**。<Infer />按用户轮数记忆、按步骤数记 Skill，大概是因为值得记的事实通常出现在用户的话里，而值得沉淀的做法通常伴随大量工具操作；代码里没有注释说明这一点。

### fork：为缓存而生的临时 Agent

`build_cache_parity_fork()` 新建的临时 `AIAgent` 有几个刻意的设计：<Src p="agent/background_review.py" l="965-1005" />

- **复制父会话的 system prompt 和 `tools[]`，沿用同一个 `session_id`**，让请求命中父会话已经预热的前缀缓存。
- **与父会话共用同一个 `MemoryStore` 对象**，所以它写入的记忆和前台写入的是同一份状态。<Src p="agent/background_review.py" l="992" />
- **持久化完全断开**，不写 `state.db`。注释记录了不这样做的后果：共用 `session_id` 的 fork 会把自己的「复盘指令」写进真实会话，下一轮用户对话会把它当成常驻指令读回来。
- **自身的计数器置零**，不会递归触发复盘；最多跑 16 轮。<Src p="agent/background_review.py" l="173" /> <Src p="agent/background_review.py" l="995" />
- 使用 Hermes 托管的本地 `llama-server` 时，任务进入**空闲队列**，等本机没有进行中的聊天回合、本地模型空闲时才取出，最长等 30 分钟。理由是复盘会占住 GPU，而下一轮用户请求一到又会把它取消，解码成本白付。<Src p="agent/review_idle_queue.py" l="1-42" /> <Src p="agent/review_idle_queue.py" l="126-142" />

### 提示词的倾向

两份复盘提示词的语气有意不对称。记忆那份是中性的，按「一个事实只存一处」的规则引导选文件：`USER.md` 写 who the user is，`MEMORY.md` 写 facts about the ENVIRONMENT you operate in。<Src p="agent/background_review.py" l="370-388" /> Skill 那份明显更积极：要求从对话里提炼可复用的技巧和纠正，并特别注明 `Nothing to save.` **不应该是默认答案**。<Src p="agent/background_review.py" l="448-518" /> 结合上面的工具限制，后台的整体倾向很清楚：**Skill 尽量多写，记忆只增不删。**

把前面所有机制放到一条时间线上，跟踪一条事实和一个 Skill：

归纳成一张表：

| 读者 | 记忆文件 | Skill |
|---|---|---|
| 发起写入的那次调用 | 工具返回值立刻反映实时状态 | `skill_view` 读到的就是最新文件 |
| 同一会话的 system prompt | 压缩后、会话切换或恢复时才重读 | 目录在重建时更新，正文本来就不在 prompt 里 |
| 同一 profile 的新会话 | 启动时读入 | 启动时出现在目录里，正文按需读 |
| 同时运行的另一个会话 | 磁盘上不会丢，但它的 prompt 要等它自己重建 | 同左 |
| 后台复盘的 fork | 与父会话共用同一个存储对象 | 读写同一个目录 |

触发重读的地方比官方文档写的多：压缩之后会调用 `invalidate_system_prompt()`，CLI、ACP、TUI 的会话切换与恢复路径也会调用。<Src p="agent/system_prompt.py" l="814-832" /> <Src p="agent/conversation_compression.py" l="3096" />

表里真正可能出问题的是第四行。同一会话里写入的事实本来就来自这个会话的对话，模型的上下文里已经有它，所以 prompt 晚一点更新基本无害。但**两个同时运行、共用一个 profile 的会话**之间，一方写入的记忆，另一方在重建之前完全看不到。

## 作用域：profile、项目与委派

### profile 是存储的边界

记忆按 profile 保存，位置由 `HERMES_HOME` 决定：默认 profile 是 `~/.hermes`，具名 profile 是 `~/.hermes/profiles/<名字>`。<Src p="tools/memory_tool.py" l="38-40" /> <Src p="website/docs/user-guide/profiles.md" l="401-433" /> 同一 profile 的所有会话共享同一对文件，**不按项目、工作目录、用户 ID 或角色分文件**。换工作目录只改变工作位置，换 profile 才换文件。

一个例外：`profile create --clone` 会把 `MEMORY.md` 和 `USER.md` 复制进新 profile，文档的理由是记忆被当作 Agent 身份的一部分，和 `SOUL.md` 一样。<Src p="website/docs/user-guide/profiles.md" l="83" />

历史库也按 profile 划分。`session_search` 默认只查当前 profile 的 `state.db`；显式传 `profile` 时，以**只读**方式打开另一个 profile 的库。<Src p="tools/session_search_tool.py" l="434-444" /> profile 只是存储的边界，**不是沙箱**，文件权限和工具授权另算。

### Skill 的四层查找，与不对称的写入

查找顺序是：受信任的项目目录 → 当前 profile 的 `$HERMES_HOME/skills` → `skills.create_dir` → `skills.external_dirs`，同名时前者覆盖后者。<Src p="agent/skill_utils.py" l="398-420" />

项目层有一道信任门：只有项目根在 `skills.trusted_project_dirs` 里，才会扫描最近 Git 根下的 `.hermes/skills/` 和 `.agents/skills/`。注释的理由很直接：项目里的 Skill 是提示注入的入口，不能因为克隆了一个仓库就自动加载；用户主目录本身也不会被当作项目根，以免点文件仓库被误认。<Src p="agent/skill_utils.py" l="507-596" />

写入却是**不对称**的：

- **新建**写当前 profile；配置了 `skills.create_dir` 时写那个目录。<Src p="tools/skill_manager_tool.py" l="200-208" />
- **修改**查找目标时排除项目层，所以项目 Skill **从不被改写**。<Src p="agent/skill_utils.py" l="423-426" />

后果是：模型读的是项目版，再用同名 `name` 提交修改，命中的可能是 profile 里的同名副本，而我没有找到任何给模型的提示。

### 委派不会创造新的记忆层

`delegate_task` 起的子 Agent 有自己的会话，和父会话存在同一个数据库里，用 `parent_session_id` 关联。<Src p="tools/delegate_tool.py" l="124-152" /> 它的记忆被**硬编码**关掉（`skip_memory=True`），委派工具表里也屏蔽了 `memory`，注释写的是 “no writes to shared MEMORY.md”。<Src p="tools/delegate_tool.py" l="289-308" /> <Src p="tools/delegate_tool_toolsets.py" l="14-22" />

想让不同角色各有长期记忆，就要为它们分别建 profile、分别运行。开启 `profile_routes` 的委派可以让子 Agent 使用另一个 profile 的环境、凭据和 Skill，但它仍然是子 Agent，记忆限制不变。<Src p="tools/delegate_tool_routes.py" l="111-153" />

## 一个实验：restore 之后会被立刻重新归档

读 curator 的代码时我注意到，`restore_skill()` 最后只调用了 `set_state(ACTIVE)`，不刷新任何时间戳；而归档条件只看「时间够久、当前不是 archived」。<Src p="tools/skill_usage.py" l="586-614" /> 这意味着一个被 restore 的旧 Skill，下一次 curator 运行时应该会被**立刻再次归档**。

光读代码不够，我在固定提交上用一个临时的 `HERMES_HOME` 跑了一遍：建一个由 Agent 创建、45 天没有活动的 Skill，跑一次自动转换，restore，再跑一次。[完整脚本](/files/restore_rearchive.py)可以直接下载复现，需要 Python 3.11 以上。

```python title="restore_rearchive.py（节选）"
u.mark_agent_created("demo")
rec.update(use_count=3, last_used_at=old, last_viewed_at=old, created_at=old)  # 45 天前

print("pass 1:", c.apply_automatic_transitions(), state())
print("restore:", u.restore_skill("demo"), state())
print("pass 2:", c.apply_automatic_transitions(), state())
```

```text title="输出（state, 目录在 skills/ 下, 目录在 .archive/ 下）"
pass 1:  {'archived': 1, ...} -> ('archived', False, True)
restore: (True, 'restored to …/skills/demo') -> ('active', True, False)
pass 2:  {'archived': 1, ...} -> ('archived', False, True)
```

结论确认：**restore 之后，如果在下一次 curator 运行之前没有读取、使用或修改这个 Skill，它会被原样再次归档。** 实际影响有限：curator 默认一周才跑一次，而 restore 通常是为了马上用它，一次 `skill_view` 就会刷新活动时间。但如果你 restore 只是想「先放回来以后再说」，它会在一周后悄悄回到归档里。

## 设计评价

### 做得好的地方

1. **一条约束贯彻到底。** 冻结快照、volatile 档排序、fork 复用工具列表、派发侧白名单、复盘推迟到答复之后，全都服务于前缀缓存，而且每一处都有注释写明理由。在这么大的代码库里，这种一致性并不常见。
2. **默认可逆。** 记忆超限不截断，可疑条目只遮盖不删除，Skill 只归档不删除，后台的删除意图暂存而不是丢弃。出了问题，用户总能看见、总能撤回。
3. **分工有明确判据。** 「每轮都要注入，所以必须小」这一条，同时决定了记忆和 Skill 的边界、两份提示词的语气，以及后台工具的范围，而不是交给模型凭感觉。
4. **失败时收紧而不是放开。** 暂存失败就退化为拒绝；由 Skill 计数触发的复盘拿不到 `memory`；项目 Skill 必须显式信任。

### 值得警惕的地方

以下是我的判断，不是源码事实。

1. **记忆会饱和，而后台无力清理。** 后台复盘只能 `add`；文件写满后，`add` 被拒绝，腾空间所需的 `remove` 和 `patch` 又要人批准。清理只能等前台模型下一次主动添加时被拒、顺手合并，或者用户去处理 `/memory pending`。如果大部分记忆都由后台写入，它很可能长期停在第一次写满时的样子。
2. **触发时机难以预测。** 两套计数单位不同、决定时机不同，前台写入还会清零计数，很难事先说清一次具体对话会不会触发复盘。这对用户无所谓，对调试和评测却是个麻烦。
3. **并发会话之间看不到彼此。** 同一 profile 下同时开着两个会话，一方写入的记忆另一方要等自己重建 prompt 才看得到。磁盘层面不会丢数据，但两个会话可能各自基于不同版本的「事实」工作。
4. **restore 不重置时钟**，见上面的实验。
5. **同名 Skill 的修改会悄悄落到 profile 副本上。** 项目层和 profile 层同名时，`skill_manage` 改的是 profile 版，模型和用户都可能以为改的是项目版。
6. **字符上限是一个粗粒度的约束。** 它守住了 prompt 的大小，但不区分条目的价值：一条关键约定和一条可有可无的偏好，占用同样的预算。
