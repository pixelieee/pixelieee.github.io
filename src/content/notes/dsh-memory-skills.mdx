## 换仓库后，为什么还能搜到上次发布的记录？

我先在临时项目 A 启动官方示例指定的 Reference Memory 服务，写入一条事实：`release` 有一条观察 `refresh atlas`，和另一个实体 `manifest` 之间有一条 `requires` 关系。退出进程，切到项目 B，用同一个图谱文件重新启动。查 `ATLAS` 仍返回 `release`。接着保持项目 B 和检索程序不动，只换一个空图谱文件，结果就变成空集。

把相同的问题问 DSH 自带的实验性会话查询工具，作用域却换了。读取其他会话时，它用目标会话 ID **和调用方的工作目录**一起筛选，再核对目标的会话头。两个独立目录即使属于同一个 Git 仓库，也不因此共享这条查询路径；上面外部服务的共享条件则是两个进程打开同一份图谱。读一段“跨项目记忆”的演示，最先值得看的是成功返回数据的**工具名**。<Src {...source} p="packages/experimental/tool-session-query/src/workspace-access.ts" l="74-112" /> <Src {...source} p="apps/cli/config/examples/mcp-memory/mcp-reference-memory.cordis.yml" l="1-13" />

下文沿三次具体的变化追踪谁在读取旧材料：会话生成检查点、Skill 文件被修改、记忆服务换进程。前两条查固定提交，第三条使用官方示例锁定的独立服务。没有模型参与写入图谱。

## 一条经验的四种去向

| 载体 | 持有者和范围 | 进入下一次推理的条件 |
|---|---|---|
| 原始会话和检查点 | Session 追加事件，持久化提供方写入日志 | 延续或恢复该会话后，由当前有效的消息序列决定 |
| 用户和项目指令 | `agent-instructions` 从用户根、项目路径读取文件 | 第一次请求注入基线，此后按工作目录或相关文件变化协调更新 |
| Skill | `ctx.skills` 汇集提供方；文件型由目录和文件持有 | 模型先收到可调用目录，再加载正文；用户显式点名另走一条路径 |
| 外部长时记忆 | 所选 MCP 服务拥有数据库、检索和写入语义 | 安装并启用服务、暴露相应工具，再由调用者实际读写 |

这里有两个常被混用的“查询”。`ctx.sessionQuery` 是应用层的会话历史服务。官方的第三方记忆 MCP 配置则允许检索另外维护的数据集。一条事实能被前者搜到，并不能说明后者有这条记录。<Src {...source} p="packages/session-query/session-query/README.md" l="28-49" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="5-21" />

## 会话压缩只替换模型眼前的那一段

日志和模型当前可见的消息序列在 DSH 里有各自的读法。JSONL 后端按会话追加逻辑事件，默认可以用带校验的 Zstandard 帧存储；还有可选的 SQLite 持久化后端。`readSession` 返回可回放的原始事件，`readSurface` 返回当前消息序列。读历史时优先读取运行中的会话，否则可以冷读持久副本。<Src {...source} p="docs/subsystems/persistence.md" l="341-346" /> <Src {...source} p="packages/session-query/session-query/README.md" l="9-13" /> <Src {...source} p="packages/session-query/session-query/README.md" l="36-49" />

基本压缩后端在步骤边界检查上下文压力，也有路由报告溢出后的恢复入口。选区要保住合适的近期消息，不能把工具调用与结果拆开。总结写成 `compaction/summary` 事件，并记录被遮盖的具体事件，随后再追加一条带替换操作的消息。可以从这条消息沿来源序号追到摘要及原始材料。<Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="155-182" /> <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="228-251" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="115-156" />

```ts title="compaction-basic/src/region.ts · 507–510"
  session.append('user/message', checkpointMessage, {
    surfaceOp: { op: 'replace', startSeq: start, endSeq: end },
    sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
  })
```

`startSeq` 和 `endSeq` 本身都是事件序号。后端先在当前消息序列中找到这两项，再按它们的**位置**截取闭区间。之前已经替换过一段时，简单选取两个数字之间的所有日志行会抓错材料。事务先留下开始标记，成功写摘要与替换消息之后才结束；如果带封装的摘要并没有比被替换内容更小，后端会报告失败。这样，恢复时能区别「尝试过压缩」和「已经用摘要接替了原文」。<Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="200-250" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="411-426" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="492-510" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="337-358" />

### 摘要生成期间又来了一条消息

正常入口有队列。上游把一次手工压缩停在等待摘要的时刻，经 `agent.followup` 提交第二个问题，观察到压缩结束并完成刷新之后才开始下一回合。模型先收到检查点，再收到那个问题。下面的稳定性检查负责另一层问题，即运行时的可见消息序列如果真的变了，正在生成的摘要还能不能用。<Src {...source} p="packages/compaction/compaction-basic/tests/manual-compaction.spec.ts" l="266-308" />

摘要要等一次模型调用。此时如果后面又追加一条用户消息，能否提交刚写好的摘要？答案取决于**调用者选了哪种稳定性检查**。自动压缩在本回合内运行，提交前要求整条可见消息序列与测量时一致。手动选区只要求那段消息仍然连续、两端合法、事件及其计量结果一致。新消息只要追加在选区之外，后一种检查就允许它和旧选区的摘要同时保留。两种模式共用替换函数。<Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="398-415" /> <Src {...source} p="packages/compaction/compaction-basic/src/index.ts" l="428-454" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="431-469" />

另一个边界是**写到哪一步失败**。封装后的摘要至少和原片段一样大，会在替换发生前失败；若检验通过，代码先追加摘要、替换消息与结束事件，之后才调用可选的持久化刷新。后者失败时，上层收到的是 `persistence` 错误。此时内存中可能已经有了新检查点，所以“命令报错”也不能直接翻译成“旧消息仍然可见”。区分两种情况要看当前序列、结束事件上的错误，以及重启后能否冷读到它。<Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="228-270" /> <Src {...source} p="packages/compaction/compaction-basic/src/region.ts" l="411-425" />

## 工作区规则：写在文件里，还要进得了预算

默认基础组合启用 `agent-instructions`。首次请求先读用户根（`$DSH_HOME` 及共享 agents 根），再从项目根到工作目录读取项目指令。`AGENTS.md`、`CLAUDE.md` 和各自的 `.local.md` 可以作出贡献，同一候选组去除首尾空白后内容相同的文件只呈现一次。每条链的预算分别为 65,536 **字节**；它不是两条链共享的字符数，也没有承诺一定能把每份文件完整贴进去。<Src {...source} p="packages/context/agent-instructions/README.md" l="27-44" /> <Src {...source} p="packages/context/agent-instructions/src/files.ts" l="430-450" />

当前会话同样有刷新边界。成功的相关文件操作可能让下一次请求得到更深目录的新规则、已有规则的替换或移除通知；恢复会话会重新核对基线。外部编辑器保存文件本身不等于当前聊天立刻多出一条消息。执行一次工具操作时，插件检查成功与否，等待待处理的投影，并在实际继续的步骤中组合指令。<Src {...source} p="packages/context/agent-instructions/README.md" l="9-13" /> <Src {...source} p="packages/context/agent-instructions/src/index.ts" l="330-369" />

## Skill 有三道选择：作用域、目录、正文

`ctx.skills` 先在每个作用域层内挑同名赢家，再把层合并。靠近目标 agent 的层可以覆盖较远层，候选的数值排名只在**同一层**里比较。文件提供方的默认排名是项目 `.dsh/skills` 100、项目 `.agents/skills` 200、自定义目录 300、用户 DSH 400、用户 agents 500、随包目录 600。把这张表当成全进程的唯一优先级，就会误判预设单独挂载的同名 Skill。<Src {...source} p="packages/skill/skill/src/index.ts" l="553-586" /> <Src {...source} p="packages/skill/skill/src/index.ts" l="810-815" /> <Src {...source} p="packages/skill/skill-filesystem/README.md" l="44-58" />

在下一步开始前，工具插件用当前 agent 作用域和工作目录取得快照，筛出允许模型调用的条目，将**名称、描述**发布为有来源标记的消息。模型用 `skill` 工具读取时，加载前后都要核对调用策略；文件提供方会重读当前正文。用户输入 `/<name>` 则从真正的用户消息识别手势，检查 `userInvocable`，把正文作为指令附在该步。禁用模型主动调用、保留用户显式调用，是两个独立开关组合出来的行为。<Src {...source} p="packages/skill/tool-skill/src/index.ts" l="133-159" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="166-207" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="packages/skill/skill-filesystem/src/index.ts" l="212-234" />

为什么改了正文，目录却可能安静？进入目录摘要的字段只有名称、描述和本次发现是否完整。只改步骤，下一次加载可以取得新正文，而模型端没有新的目录要接收；改描述、删除条目或从部分发现恢复，才可能出现替换目录。**空目录也有两种含义**：完整发现后没有可用项，或有提供方失败、这次只能确认零项。后者不会作为权威结果缓存，模型也不能把旧目录里残留的名字当成当前可用。<Src {...source} p="packages/skill/tool-skill/src/index.ts" l="290-329" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="344-356" /> <Src {...source} p="docs/subsystems/skills.md" l="11-17" /> <Src {...source} p="docs/subsystems/skills.md" l="77-83" />

### 文件未动，目录为什么又发了一次？

目录有两份可比的状态。一份来自这一步刚完成的发现：条目按名称和已呈现的描述计算摘要，发现不完整还要额外记一位。另一份来自**模型当前可见**的最后一条目录消息：插件逆向读会话事件，在事件上找可解析的目录数据，再检查其序号是否还在 `surface.nodes` 中。只比较文件时间戳，解释不了压缩之后的行为。<Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="344-355" /> <Src {...source} p="packages/skill/tool-skill/src/index.ts" l="380-399" />

这里能用两个相反的用例检查解释是否成立。只改正文时，官方测试读到了第二版正文，目录消息总数仍为 1。用检查点覆盖刚发过的目录时，文件没有变化，下一步却留下第 2 条目录。前者检验提供方怎样读文件，后者检验消费端是否记得**模型还能看到什么**。恢复旧会话时，插件也从有来源标记的可见事件恢复这个判断；它无需猜测摘要模型有没有在一段自由文字里准确复述 Skill 清单。<Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="585-614" /> <Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="689-744" />

### 发现过程中，提供方掉线或发生更新

若较高优先级的来源暂时不可读，较低层的同名条目可能当选。插件告诉模型只能使用本次确认的项，并标出发现不完整。即使两次确认的名称碰巧相同，恢复完整的那一步也会改变摘要并撤下旧告警。这解决的是“当前目录有多可信”，和“文件最后是谁改的”无关。<Src {...source} p="packages/skill/tool-skill/src/index.ts" l="290-329" /> <Src {...source} p="packages/skill/tool-skill/tests/tool-skill.spec.ts" l="363-402" />

还有一个更短的竞争窗口：列目录刚开始，提供方就通知注册表内容已变。注册表把工作目录、作用域链和修订号都放入缓存键。扫描前后的修订号不同会重查一次；又遇到变化，就交出这次看到的条目并标记不可缓存。正文加载还有独立的身份核对：读取路径后，如果正文返回的名称已经和获胜候选不同，本次调用返回空并让对应缓存失效。这样一个正在改名的文件不会以旧名交付一份新身份的指令。<Src {...source} p="packages/skill/skill/src/index.ts" l="24-28" /> <Src {...source} p="packages/skill/skill/src/index.ts" l="502-550" /> <Src {...source} p="packages/skill/skill/tests/skill.spec.ts" l="796-864" />

## 外接记忆：谁拥有“记住”这次写入？

官方给出 Memorix、MCP Reference Memory、Engram 三种默认关闭的参考配置。DSH 负责启动已安装的 stdio 服务或连接现有 HTTP 服务，发现并暴露工具。索引、项目标识、数据迁移、冲突处理和遗忘策略要去相应服务核实。即便启用了工具，每条普通用户消息会不会触发写入，仍取决于调用路径。<Src {...source} p="docs/user/guide/mcp-memory.md" l="5-33" />

以 Reference Memory 为例，示例通过 `MEMORY_FILE_PATH` 指向本地知识图谱的 JSONL，支持实体、关系和观察。这里的搜索是对名称、类型和观察值做不区分大小写的子串匹配。把两段语义相近的文本送进去、检索却没有命中，不足以说明 DSH 丢了记忆；应先核对工具是否真的调用、两个进程是否指向同一文件、字面检索词是否出现在已写入字段。<Src {...source} p="apps/cli/config/examples/mcp-memory/mcp-reference-memory.cordis.yml" l="1-13" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="48-59" />

### 图谱里的边能找到邻居，能顺便读到它的属性吗？

首节实验具体调用了 `create_entities`、`create_relations`、`search_nodes` 和 `open_nodes`。向已存在的 `release` 再调用一次 `create_entities`，并带上一条新观察 `SECOND_NOTE`，服务成功返回空的新增列表。随后搜索那个标记也是空集。这个操作按名字去重；要给已有实体补事实，接口是 `add_observations`。仅统计“成功的写工具调用次数”，在这里就会多算一次实际记住的事实。[固定版本的服务器实现](https://unpkg.com/@modelcontextprotocol/server-memory@2026.7.4/dist/index.js)

| 在新进程里的查询 | 命中实体 | 可回答的问题 |
|---|---|---|
| 同图谱，搜 `ATLAS` | `release` | 观察值匹配，也带回指向 `manifest` 的边 |
| 同图谱，搜 `map` | 无 | 本次输入里概念接近的词没有字面命中 |
| 同图谱，打开 `manifest` | `manifest` | 现在才读到邻居的观察值 `owner: ci` |
| 同目录，另一个空图谱，读全图 | 无 | 恢复了哪个服务进程与打开哪个文件是两件事 |

`ATLAS` 返回的结果里有邻居的名字和关系，却没有邻居的观察值。要回答“这个依赖由谁维护”，还需要再调用一次工具。这个差别比“用了知识图谱”更能说明一次回答究竟得到了什么证据。此实验直接对示例指定的 stdio 服务发送 MCP 请求，覆盖写入、停止进程、重开与读取；DSH 宿主的工具选择和模型是否会主动走第二跳仍是另一个问题。[下载可复现实验](/experiments/dsh-memory-graph.py)

在空目录运行 `npm install @modelcontextprotocol/server-memory@2026.7.4`，然后执行 `python dsh-memory-graph.py node_modules/@modelcontextprotocol/server-memory/dist/index.js`。脚本只在临时目录写两份图谱。

## 实验：600 字节的限制，为什么能得到 879 字节？

[下载规则预算实验](/experiments/dsh-instruction-budget.mjs)，保存到 DSH 固定提交的仓库根目录，用 Node 22.23.1 执行 `node dsh-instruction-budget.mjs`。脚本把一个工作区依赖指向同一提交的源码，然后把 240 字节的用户规则、800 字节的项目根规则和 240 字节的子目录规则交给真实渲染器。测量的是上游收到的完整文本，包含文件名和省略说明。

| 输入与每链预算 | 输出字节 | 被完全省略 | 被截断 |
|---|---:|---|---|

## 进化发生在哪一层

固定版本里可以验证三种不同的变化：会话历史能生成检查点；Skill 提供方能热更新；维护者能根据真实失败修改并重新发布 Skill。第三种有一个具体例子：官方的 Cordis 插件开发 Skill 曾因正文过长，被标准预设的工具结果裁剪器截去中段。维护者把分支配方移入 `references/`，把模板移入 `templates/`，为入口长度和引用完整性增加测试。这里有明确的失败样本、改动和回归条件，承担写入的是维护者。<Src {...source} p=".agents/notes/archived/architecture/2026-09-21-creator-skills-progressive-disclosure.md" l="8-26" />

实验性的 `ralph` 工具提供了另一种迭代。用户明确要求分轮使用新 Agent 后，每一轮拿到固定目标、共享工作区，以及上一轮有限长度的交接报告。父对话和更早子会话不会作为种子带入。子 Agent 自报完成即可结束循环，工具没有独立验证成果。这里跨轮传递的是工作成果和交接信息，不能由此推断某个 Skill 得到了改进。 <Src {...source} p="packages/experimental/tool-ralph/README.md" l="28-38" />

在这次查到的基础组合、Skill 注册表和消费工具中，没有找到一个会在普通会话结束后自行提炼经验、改写 Skill 并按使用量归档的后台维护器。由用户指示的文件编辑、私有插件或外接记忆服务可以改变具体部署的答案。<Infer /> DSH 的长处是能区分“哪次调用、哪个作用域、哪份材料”造成了变化；代价是，仅凭客户端里出现过一段文字，几乎无法反推它会不会进入另一个会话。要验证跨会话复用，最有辨识度的观察是新会话里**实际到达模型的消息或实际返回的工具结果**。<Src {...source} p="packages/skill/tool-skill/src/index.ts" l="222-255" /> <Src {...source} p="docs/user/guide/mcp-memory.md" l="65-72" />

Hermes 有从历史材料到后台复盘、再到文件写入的内建路径。DSH 的热更新证明读取端能看见一次修改；要断言系统从历史中提炼了新做法，还需要找到那次写入的来源。 [对照 Hermes 的实现](/notes/hermes-memory-skills/#background-review把三者串起来)
