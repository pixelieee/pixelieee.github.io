**一句话结论：** Hermes、Claude Code 和 Codex 都内置了「跨会话记忆」——专门的记忆文件，加上自动写入工具或后台提炼任务。Pi 走了相反的极简路线：**它完整实现了 Skill，却故意不做内置记忆库**——没有 `MEMORY.md`，没有 `memory` 工具，也没有回合结束后的后台复盘，和它默认不内置子 Agent、计划模式是同一个取舍。<Src {...source} p="packages/coding-agent/README.md" l="15-19" /> 默认情况下，能跨会话留存下来的只有两样东西：**磁盘上直接维护的 Markdown 文件**（`AGENTS.md` 与 `SKILL.md`），以及**会话本身——一棵像 Git 提交一样只追加、可分叉的 JSONL 树**。连 system prompt 的更新、上下文压缩、乃至隐藏一条失败消息，Pi 都不改旧记录，只在文件末尾**再追加一行**；每次发请求前，再从当前节点顺着父指针倒推回根，把这一条路上的记录拼成模型看到的上下文。这套设计里几乎所有看似反直觉的现象，都能用这四个字解释：**只追加，不改写。**

读完这篇，你应该能回答五个问题：

1. 没有内置记忆库，日常用 Pi 时**长期约定、操作流程、排错进展**分别该放进哪里？
2. 会话开着没关，你在磁盘上同时改了 `AGENTS.md` 和 `SKILL.md`：为什么不执行 `/reload` 直接调用时，发给模型的同一个请求里**既带着改之前的旧 `AGENTS.md`，又带着改之后的新 `SKILL.md` 正文**？
3. JSONL 日志里明明写着的消息，**为什么**模型可能一次都看不到？切回旧分支时，另一条分支的压缩摘要**还在不在**？
4. 上下文压缩**保留什么、丢掉什么**？摘要末尾的「已修改文件」清单为什么会记下**根本没改成功**的文件？
5. 如果想在 Pi 上自己搭一套自动记忆或复盘机制，可以从**哪几个扩展接口**接入？

## 全景：没有记忆库，知识往哪放

先把全局装进脑子里。Pi 里一切能影响模型上下文的输入，只走下面三条通道：

|---|---|---|---|
| 位置 | `~/.pi/agent/sessions/--<cwd>--/<时间>_<id>.jsonl` | 个人全局目录 `~/.pi/agent/`，加上从 `cwd` 一路到文件系统根的每层目录 | `~/.pi/agent/skills`、`~/.agents/skills`、项目 `.pi/skills`、到 Git 根为止的 `.agents/skills`、Pi 包 |

| 谁来写 | 运行时自动追加 | 手动编写，或让模型用 `write` / `edit` 修改文件 | 手动编写、安装 Pi 包，或让模型用 `write` / `edit` 修改文件 |

看懂这张表，关键在两行：

- **「怎样进入模型」决定了什么内容该放哪里。** `AGENTS.md` 每次请求都会整份塞进提示词、一直占用上下文窗口，适合放简短、做任何任务都要遵守的硬约束（构建命令、目录边界、代码风格）；Skill 平时只占一行简介，适合放几百行的发布流程、排障手册和脚本；临时试错留在会话树里，走不通就用 `/tree` 退回分叉点重走，不必担心污染后面的上下文。
- **「何时读磁盘」决定了修改何时生效。** 会话树在每次请求前都会重新拼装，所以切分支和压缩当场生效；`AGENTS.md` 和 Skill 索引表只在启动或 `/reload` 时读进内存，所以你在编辑器里改了它们，正在跑的会话并不会察觉；唯独 Skill 的**正文**不走内存缓存，每次调用都直接去磁盘读文件。所以只要在会话中途同时改了 `AGENTS.md` 和 `SKILL.md`、没跑 `/reload` 就再次调用这个 Skill，发出去的同一个请求里就会同时装进「旧版 `AGENTS.md` + 上一轮留下的旧版 `SKILL.md` 正文 + 本轮刚读出的新版 `SKILL.md` 正文」。

## 一条底层规则：只追加，不改写

普通聊天客户端把会话存成一个数组：压缩了就把旧元素删掉换成摘要，改了 system prompt 就把第 0 项覆盖掉。一旦这样做，会话就只能往前走——没法像代码一样回退到半小时前的某个分叉点去试另一条路，事后也没法从日志还原「第 5 轮回答出错时，模型看到的提示词到底长什么样」。

Pi 的做法是把整份会话存成一棵**只追加的树**。文件里的每一行都是一个带 `id` 和 `parentId` 的节点，当前位置叫 `leaf`（叶指针）：

- 正常聊天时，新节点挂在当前 `leaf` 下面，`leaf` 跟着往前移；
- 用 `/tree` 回退到较早的一轮时，Pi **不删任何旧行**，只是把 `leaf` 挪回那个旧节点；接下来新说的话会自动长成另一条分支。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1591-1602" />

真正体现功力的地方在于：**Pi 把原本不属于「聊天消息」的变化，也全都设计成了树上的追加节点**。就连 system prompt 和可用工具列表也不例外——会话开头的第 1 条 `system` 消息写下初始提示词（按 `<tools>`、`<rules>`、`<project_context>`、`<skills>` 等带名字的 XML 段落分块保存）和初始工具集；中途执行 `/reload` 改了规则或增减了工具，Pi 不会回头去改开头那条消息，而是**对比新旧内容，只把发生变化的段落打包成一条新的 `system` 消息**，追加到当前分支末尾。<Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="187-192" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="216-228" />

顺着源码数一遍，整套系统里有六种操作都在遵守同一条「只追加」纪律：

1. **普通对话（`message`）**：挂在当前 `leaf` 下；如果写磁盘失败，连刚放进内存的条目和 `leaf` 指针也当场回滚，绝不留下指向空父节点的脏状态。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1199-1232" />
2. **提示词与工具变更（追加 `system` 消息）**：对比当前分支已生效的各个段落与新内容，只把有变化的段落作为一条新 `system` 消息追加进去。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1826-1848" />
3. **隐藏或替换旧消息（`context_edit`）**：追加一条指向旧条目 `targetId` 的编辑记录，`replacement: null` 代表对模型隐藏它，原消息在 JSONL 里纹丝不动。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="174-180" />
4. **上下文压缩（`compaction`）**：追加一条摘要记录，用 `firstKeptEntryId` 指明从哪条近期消息开始保留原文，同时把那一刻合并后的完整 `system` 状态存成快照。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1278-1305" />
5. **跨分支带走经验（`branch_summary`）**：`/tree` 切走时如果选择总结旧分支，摘要会作为新节点追加到**切入的目标位置**，离开的那条旧分支本身不被改动。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="4280-4292" />
6. **上下文超限恢复**：某次回答因超限报错时，先追加 `context_edit` 把这次失败回答隐藏掉，再追加 `compaction` 压缩并自动重试。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3211-3216" />

这样做除了让分叉回退零成本，还有一个实打实的性能收益：**保住服务端的前缀缓存（prefix cache）**。不同模型接口对 `system` 消息的规矩不同——有的允许对话中间再插 `system` 消息，有的只认请求最开头那一条。对前者，Pi 直接把这条新 `system` 消息留在对话末尾，前面几万 token 的历史前缀一个字没变，照常命中缓存；对后者，Pi 在发请求前把所有 `system` 消息合并成一条新开头，每次改规则也只丢一次缓存。<Src {...source} p="packages/ai/src/utils/transcript.ts" l="104-120" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="657" /> 就连请求模型生成压缩摘要时，Pi 都特意传了 `cacheRetention: "none"`，因为这种一次性提示词下轮不会再用，没必要花钱写缓存。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="626-632" />

把它和 Hermes 对照最能看出门道：两边都在尽力保住前缀缓存，Hermes 选的是**在会话中途冻结 system prompt 里的记忆快照**，写入只落磁盘、下轮不改提示词；Pi 选的是**允许提示词中途更新，但只往末尾追加变化的部分**。[对照 Hermes 的冻结快照](/notes/hermes-memory-skills/#一条约束不要弄脏前缀缓存)

## 会话树：一份文件怎样算出不同上下文

### 落盘规则

会话文件默认按启动时的工作目录分组，存在 `~/.pi/agent/sessions/--<工作目录路径（斜杠换成 -）>--/` 下，文件名是 `<时间戳>_<会话ID>.jsonl`。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="586-595" /> 可以用 `--session-dir`、`PI_CODING_AGENT_SESSION_DIR` 或 `sessionDir` 改存储目录，也可以传 `--no-session` 纯内存运行。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="64-68" />

有两处工程细节很考究：

- **光打开不说话，不留空文件。** 启动时生成的模型信息、思考档位和初始 `system` 消息先放在内存里；直到出现第一条 `user` 或 `assistant` 消息，才连同文件头信息一次性建文件写盘。代码注释专门解释了为什么在 `user` 消息一发出就立刻写盘，而不等 `assistant` 回复：万一第一轮请求中途断了，用户敲进去的长提示词也不会丢。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1168-1197" />
- **损坏行自动跳过。** 读取会话文件时，遇到损坏或手动改坏的 JSON 行会直接忽略，不会因为一行脏数据废掉整份会话。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="617-625" />

### 每次请求前的三步组装

用户在同一个会话里可以用 `/tree` 切换分支，也可以用 `/fork` 从某条历史消息拆出独立的新会话文件，或用 `/clone` 把当前分支拷成新会话。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-48" /> 正因为一份 JSONL 文件里可能并存着好几条分叉，**用编辑器从上往下读到的行顺序，并不是模型看到的顺序**。

每次发请求前，`SessionManager` 按下面三步从树里算出当前上下文（源码叫 `buildSessionProjection`）：

1. **顺着父指针找祖先链。** 从当前 `leaf` 一路沿 `parentId` 走回根节点，再倒过来排成一条从旧到新的消息链。凡是不在这条链上的旁支节点，不管时间戳有多新，一律忽略。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="390-416" />
2. **截断到最近一次压缩。** 只在上面这条消息链里找**最后一条** `compaction` 记录。如果找到了，这条记录之前的早期消息就不再逐条发送，换成「压缩记录本身 + 从 `firstKeptEntryId` 开始保留的近期条目 + 压缩之后新追加的条目」：

```ts title="packages/coding-agent/src/core/session-manager.ts · 499–511"
const contextEntries: SessionEntry[] = [compaction];
let foundFirstKept = false;
for (let i = 0; i < compactionIdx; i++) {
	const entry = path[i];
	if (entry.id === compaction.firstKeptEntryId) {
		foundFirstKept = true;
	}
	if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
		contextEntries.push(entry);
	}
}
contextEntries.push(...path.slice(compactionIdx + 1));
return contextEntries;
```
<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="468-512" />

注意上面第 8 行特意跳过了保留区间里的 `system` 消息：因为在生成 `compaction` 记录的那一刻，Pi 已经把当时生效的所有 `system` 消息合并成一份完整快照，存进了 `compaction.systemMessage` 字段里；组装上下文时，Pi 会先放上这份 `system` 快照、再放上摘要正文，如果保留区间里中途追加过的旧 `system` 消息不跳过，就会被重复应用一遍。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="461-464" /> <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1286-1302" />

3. **应用消息编辑（`context_edit`）。** 对留下的每个条目，检查这条链上有没有指向它的 `context_edit`（有多条时取最后一条）：`replacement` 为 `null` 就把该条目从本次上下文里彻底隐去；否则只替换消息正文，保留角色和元数据。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="519-574" />

把这三步画出来，就能一眼看明白为什么同一份 JSONL 会算出完全不同的上下文：

<FigPiBranch />

**压缩摘要和消息编辑都严格属于它们所在的那条分支。** 在分支 B 上做了压缩，摘要节点挂在 B 末端；一旦用 `/tree` 切回分支 A，从 A 倒推回根的路上根本没有那个压缩节点，模型看到的立刻变回 A 的原始历史。同理，在 A 上用 `context_edit` 隐去了一条消息，切去 B 时也互不相干。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1377-1416" />

### 超限恢复为什么先写 `context_edit` 再压缩

`context_edit` 最重要的内置用处，是处理模型上下文超限（context overflow）或输出被提前截断。

设想一次请求刚发出去，服务商返回了上下文超限错误，或者回答卡在半截停住了。此时这条失败的 `assistant` 记录已经写进了会话树（保留下来供计费统计和问题排查）。如果直接在这上面跑压缩，压缩器要么把半截废话总结进去，要么连压缩本身也超限。

Pi 的恢复顺序是：先把这次失败回答及它带出的工具结果逐一追加 `context_edit(targetId, null)` 从模型视野里摘掉，然后跑一次自动压缩，再重新发起请求；**整个恢复最多只试一次**，再超限就直接报错停下，防止死循环烧钱。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3180-3216" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1334-1340" /> 这里还有一个很稳健的细节：万一紧接着的压缩请求因为网络故障或用户按取消而没跑成，前面写下的那几条「隐藏失败请求」的 `context_edit` **依然保留在分支上**——分支上虽然没有新摘要，但下次发请求时，那次失败记录已经不会再混进上下文了。<Src {...source} p="packages/coding-agent/docs/compaction.md" l="85-98" />

### 多次压缩怎样接力，超长单轮怎样切分

用一组具体数字看懂连续压缩：假设第 1 次压缩把前 160K 历史压成了摘要 S1，留下了最近 20K 原文（起点记为 `firstKeptEntryId`）。继续聊到又触发第 2 次压缩时，Pi 从上次留下的那 20K 原文起点开始往后取需要总结的范围，把「**上次幸存的旧原文 + 这期间新增的早期对话**」连同 `<previous-summary>` 里的 **S1** 一起交给摘要模型，用一份「增量更新」提示词合成新摘要 S2。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="714-727" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="872-894" /> 这意味着：**每次再次压缩都会损耗一层细节**——第 1 次没写进 S1 的内容，第 2 次不可能再找回来。

选切分点还有两条硬规矩：

- **绝不把工具调用和工具结果劈成两半。** 切点只能落在 `user`、`assistant`、bash 执行或自定义消息上，不能落在 `toolResult` 上，否则保留段的开头会出现一条找不到对应调用的孤立结果，直接被模型接口拒收。<Src {...source} p="packages/coding-agent/docs/compaction.md" l="128-136" />

### 「已修改文件」清单为什么会记下失败的编辑

为了防止压缩后模型忘了自己动过哪些文件，默认压缩器会在摘要末尾自动附上一份 `<read-files>` 和 `<modified-files>` 清单，同时写进结构化的 `details` 字段。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="1042-1056" /> 但看一眼提取代码就会发现一个必须留心的坑——**它只看工具调用的参数，完全不看执行结果**：

```ts title="packages/coding-agent/src/core/compaction/utils.ts · 48–62"
function addFileOp(toolName: string, args: Record<string, unknown> | undefined, fileOps: FileOperations): void {
	const path = typeof args?.path === "string" ? args.path : undefined;
	if (!path) return;
	switch (toolName) {
		case "read":
			fileOps.read.add(path);
			break;
		case "write":
			fileOps.written.add(path);
			break;
		case "edit":
			fileOps.edited.add(path);
			break;
	}
}
```
<Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="27-73" />

代码遍历待摘要区间里 `assistant` 发出的 `read`、`write`、`edit` 调用，以及 codemode（让模型写脚本批量调工具的模式）记在工具结果里的嵌套调用：凡是传给 `edit` 或 `write` 的路径一律归进 `modifiedFiles`（如果同一路径还传给过 `read`，会从 `readFiles` 里剔除，只留「只读未改」的文件）。**哪怕那次 `edit` 因为匹配不到旧文本当场报错、磁盘文件一个字节没变，路径照样进 `modifiedFiles`**；而且下一次压缩还会把上一次压缩记下的文件集合直接并进来。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="57-88" /> <Infer />源码没有说明为什么不核对成败；从结构上看，`extractFileOpsFromMessage` 每次只单独看一条消息，不去把前一条 `assistant` 的工具调用与下一条 `toolResult.isError` 配对核对（就连工具结果里自带 `status` 字段的嵌套调用记录，也直接走同一个只看参数的 `addFileOp`），实现最简单。<Src {...source} p="packages/ai/src/types.ts" l="627-639" /> 代价很明确：这份清单只能当作「模型试图碰过哪些路径」的线索，不能当作「文件已经改好」的证据。后面的实验二专门验证了这一点。

**Pi 在内存里只缓存「名字 → 简介 + 文件路径」这张索引表，从不缓存 Skill 正文。** 由此直接推出三条日常必定会遇到的现象：

## 作用域与扩展：想加长期记忆，从哪接入

先把跨项目、跨会话的隔离边界理清：

- **会话目录只管归档查找，不同会话互不共享历史。** `--continue` 会打开当前工作目录最近的一份会话；但只要你是新开会话（直接启动或 `/new`），哪怕在同一个目录里，上次聊过什么也绝不会自动混进来。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="5-22" />
- **全局与项目分层。** `~/.pi/agent/` 下的上下文文件和 `~/.pi/agent/skills`、`~/.agents/skills` 对本机所有项目生效；项目内的文件只覆盖对应目录树。

如果你希望在 Pi 上做出类似 Hermes 的「后台复盘写记忆」或结构化状态管理，Pi 在扩展层提供了四种分工明确的接入方式：

1. **`pi.appendEntry(customType, data)`**：往当前分支追加自定义状态记录，重启或切换分支后可以顺着分支历史重新读出恢复，但**完全不发给模型**，不占半个 token。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="118-132" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1683-1690" />
2. **`custom_message`（`sendMessage`）**：同样记在分支上，但**会转成消息进入模型上下文**，还能控制是否在终端界面显示。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="147-165" />
3. **`before_agent_start`**：每轮运行前可动态增改 `systemPromptOptions.sections`（例如从外部记忆库检索相关条目塞进自定义段落，Pi 会自动对比段落变化并追加更新）。<Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-657" />
4. **`session_before_compact` 与 `agent_end`**：前者可以完全接管压缩摘要怎么写，后者可以在回合结束后异步提炼经验写回磁盘。<Src {...source} p="packages/coding-agent/docs/extensions.md" l="534-552" />

仓库自带的两个扩展示例把这套机制用得很漂亮：`todo.ts` 把待办快照塞在每次工具结果的 `details` 里，收到 `session_start` 或 `session_tree` 事件就顺着**当前分支**从头读一遍历史结果来恢复状态——于是你用 `/tree` 退回较早的分支时，连待办列表也会跟着「时光倒流」回当时的状态。<Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="106-133" /> `handoff.ts` 则提供 `/handoff` 命令，把当前分支的排错上下文浓缩成一份交接草稿放进新会话的输入框，由人审阅修改后再发出，用人工确认的交接草稿代替全自动的后台记忆。<Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="160-190" />

## 实验验证

下面三个实验都直接运行固定提交的 TypeScript 源码，用官方自带的内存模拟服务商 `fauxProvider` 在进程内截获准备发给模型的请求消息，不经过外部网络和真实大模型，因此能把「Pi 到底给模型组装出了什么消息」测得一清二楚。

### 实验一：会话中途改磁盘文件，同一次请求里新旧版本并存

按前面的源码分析，`system` 段落定格在资源加载时，`/skill:name` 每次直接读磁盘文件，而旧消息一直留在分支上。把这三件事串进同一个会话，应该能在单次请求里同时抓到新旧两代内容。

脚本在临时目录里放好 `AGENTS.md`（写 `RULE_A`）和 `release` Skill（简介 `DESC_A`、正文 `BODY_A`）。第 1 轮调用 `/skill:release` 后，直接改写磁盘文件把三处标记全换成 `B`，顺手新建一个 `late` Skill，接着在不重载、重载、重开会话三种状态下发请求：

```js title="pi-skill-lifecycle.mjs（节选）"
await turn("initial", session, "/skill:release");
await putSkill("release", "DESC_B", "BODY_B");
await putSkill("late", "NEW_SKILL", "New instructions.");
await writeFile(join(project, "AGENTS.md"), "RULE_B");
await turn("edit on disk", session, "/skill:release");
await turn("unknown name", session, "/skill:late");
await session.reload();
await turn("reload", session, "/skill:release");
```

点选下面面板里的五个阶段，可以直接核对每次请求里携带的标记：

<FigPiSkillRequests />

**改完磁盘后的那次请求里，生效的 `system` 仍是 `RULE_A · DESC_A`，第 1 条用户消息里留着旧的 `BODY_A`，而第 2 条用户消息已经展开成了最新的 `BODY_B`；下一轮敲 `/skill:late` 则没被展开，直接当成普通文字 `/skill:late` 发给了模型。** 每一项都与源码路径严丝合缝。

`/reload` 那一轮还验证了一个排查问题时极易误判的现象：如果直接拿字符串去搜底层原始请求，`RULE_A` **依然搜得到**——因为开头的第 1 条 `system` 消息从来没被改写；脚本同时检查了原始 `system` 列表（2 条：开头的 `A` 与追加的更新 `B`）和调用 `getCurrentSystemMessage()` 合并后的结果（只有 `RULE_B · DESC_B · NEW_SKILL`）。排查问题时如果只做全文搜索，就会把已经生效的热重载误判成失败。

### 实验二：失败的 `edit` 照样写进压缩清单

为了验证前面发现的「只看参数、不看执行结果」，脚本在磁盘写入内容为 `unchanged` 的 `release.md`，让 `fauxProvider` 调用真实的内置 `edit` 工具去替换一段根本不存在的文字，确认工具返回 `isError: true` 且磁盘文件未变后，把会话交给 `prepareCompaction`（设 `keepRecentTokens: 1` 迫使该轮进入待摘要区）：

```json title="同一次失败编辑的三处实测结果"
{
  "toolError": true,
  "onDisk": "unchanged",
  "readFiles": [],
  "modifiedFiles": ["release.md"]
}
```

**工具明确报错、磁盘分毫未动，`release.md` 依然被列进了 `prepareCompaction` 算出的 `modifiedFiles`。** 后续模型如果只凭压缩摘要里的 `<modified-files>` 判断之前做过什么，就会误以为该文件已经改过。本实验测到 `prepareCompaction` 与 `computeFileLists` 为止；摘要文本拼接与跨次合并由源码直接确认。

### 实验三：切回分支 A，分支 B 的压缩摘要与编辑会串过来吗

第三个实验用内存模式的真实 `SessionManager` 构造最小分叉树，直接传入固定摘要文字，单独验证会话树的三步组装逻辑：

```js title="probe.mjs"
import {SessionManager} from './packages/coding-agent/src/core/session-manager.ts';
const log = SessionManager.inMemory();
const say = text => log.appendMessage({role:'user', content:text, timestamp:0});
const root=say('base'); const left=say('attempt A');
log.branch(root); const right=say('attempt B');
console.log('raw messages',log.getEntries().filter(e=>e.type==='message').map(e=>e.message.content));
console.log('active leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendCompaction('checkpoint', right, 1200);
console.log('compacted',log.buildSessionContext().messages.map(m=>m.summary ?? m.content));
log.branch(left);
console.log('other leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendContextEdit(left, null);
console.log('edited A', log.buildSessionContext().messages.map(m=>m.content));
```

| 观察点 | `buildSessionContext()` 实测输出 |
|---|---|
| 遍历 JSONL 里的全部原始消息 | `base`、`attempt A`、`attempt B` |
| 叶节点在 B | `base`、`attempt B` |
| 在 B 后面追加压缩记录 `checkpoint`（从 `attempt B` 起保留） | `checkpoint`、`attempt B` |
| 把叶节点切回 A | `base`、`attempt A` |
| 在 A 上追加一条隐藏消息的 `context_edit(left, null)` | `base` |

**切回 A 的瞬间，B 上的 `checkpoint` 彻底退出模型视野；再对 A 追加隐藏编辑后，`attempt A` 仍躺在原始日志里，模型收到的上下文却只剩 `base`。** 这也和上游 `build-context.test.ts` 的分支与压缩回归测试完全吻合。<Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="126-147" /> <Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="211-246" />

## 设计评价

### 做得好的地方

1. **「只追加树」同时解决了回退试错、状态审计与前缀缓存三件事。** 不管是对话、规则更新、压缩还是隐藏失败消息，全都只是树上的新节点：分支切换零拷贝，支持中途 `system` 消息的模型不丢缓存，出了怪回答随时能顺着父指针还原当时的完整输入。
2. **Skill 不造专用工具，复用率极高。** `<skills>` 清单只给路径，正文走普通 `read` 工具和现用现读的 `/skill:name`，既省掉了一套工具封装和正文缓存同步代码，又让作者改完 `SKILL.md` 正文就能立刻实测。
3. **异常路径考虑周全。** 首次发言前不建空文件，写盘失败当场回滚内存节点和 `leaf` 指针，超限恢复先隐藏失败请求且最多重试一次——每处都在防止脏状态传染后续轮次。
4. **内核克制，扩展接口分工清楚。** 不强塞一套黑盒自动记忆，而是把「存状态但不发给模型」（`appendEntry`）、「存消息发给模型」（`custom_message`）和「按段落更新提示词」（`before_agent_start`）拆成互不干扰的三件事。

### 值得警惕的地方

以下是我基于源码机制做的工程判断。

1. **改了磁盘规则却没有任何未刷新提示。** 会话运行中改了 `AGENTS.md` 或 Skill 简介，界面不会提醒「磁盘已变，需 `/reload`」，用户极易对着旧规则排查半天。
2. **同一上下文里可能并存新旧几版 Skill 正文。** `/skill:name` 每次展开都把整段正文写成永久留存的 `user` 消息；同一个会话里反复改 `SKILL.md` 反复调，新旧几版正文会同时留在历史里，只能靠模型自己分辨哪条最新。
3. **`modifiedFiles` 把「试图改」记成了「已改过」。** 编辑报错也进清单、跨次压缩还一路累加，长会话多次压缩后容易误导模型跳过本该重做的修改。
4. **连续压缩每次都会再丢一层细节。** 新摘要是在旧摘要文本上做增量改写，早期没写进摘要的约束或排错结论，后面不会再从原始日志补回来。
5. **经验沉淀完全靠自觉。** 没有后台自动复盘，意味着一次排了半小时才踩明白的坑，只要人没开口让模型写进 `AGENTS.md` 或 `SKILL.md`，关掉会话就形同没发生过。
6. **`AGENTS.md` 无需信任确认，且会一路向上扫到系统根目录。** 刚克隆的陌生仓库只要带 `AGENTS.md` 就会直接注入 system prompt；另外如果你在家目录 `~/` 放过一份全局 `AGENTS.md`，在 `~/tmp/` 下做任何隔离测试都会顺带把它扫进去。

## 仍未弄清的问题

1. **`/tree` 切回旧分支后的首轮 `system` 更新。** 从源码调用链看，切回旧分支后下一轮请求会自动追加一条把旧分支同步到最新已加载资源的 `system` 消息；这一点我只核对了代码路径，没有单独跑交互实验验证。
2. **各服务商适配器的中途 `system` 消息支持表。** 每次 `/reload` 究竟是「留在原位置保缓存」还是「合并到开头丢一次缓存」，取决于对应模型适配器的 `supportsMidConvoSystemMessages` 标记，本文没有逐家统计。
3. **真实摘要模型的信息保留率。** 本文实验均用固定文本代替摘要模型输出，测清的是「哪些内容被送进了压缩器」，没有评测真实模型在连续多次压缩后的细节遗漏率。
