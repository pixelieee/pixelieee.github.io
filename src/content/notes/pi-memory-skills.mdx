**一句话结论：** Pi 完整支持 Skill，但故意不做内置记忆库；对话、规则更新、压缩与隐藏旧消息都只往 JSONL 树末尾追加一行，发请求时再从当前节点倒推回根拼出上下文。<Src {...source} p="packages/coding-agent/README.md" l="15-19" />

读完这篇，你能搞清四件事：

1. 没有内置记忆库时，**长期规则、操作步骤、临时试错**在 Pi 里分别怎么存？
2. 为什么在 JSONL 文件里写着的消息，模型可能一次都看不到？切回旧分支时，另一条分支的压缩摘要去哪了？
3. 会话中途同时改了 `AGENTS.md` 和 `SKILL.md`、没跑 `/reload` 就调用：为什么同一次请求里会同时带着**旧 `AGENTS.md`、旧正文和新正文**？
4. 想自己给 Pi 加上长期记忆，该从哪几个扩展接口切入？

## 一张图看懂：没有记忆库，知识放哪

Hermes、Claude Code 和 Codex 都自带跨会话记忆文件和自动提炼任务。Pi 走了相反的极简路线——没有 `MEMORY.md`，没有 `memory` 工具，也没有后台复盘。

一切能进入模型上下文的信息，只走下面三条路：

<FigPiArch />

| 通道 | 怎么进模型 | 何时读磁盘 | 适合放什么 |
|---|---|---|---|
| **会话树**（`*.jsonl`） | 每次请求前，从当前叶节点 `leaf` 倒推回根拼装 | 打开会话时读一次，之后边追加边写盘 | 当前任务的聊天与试错（走不通就 `/tree` 退回分叉） |
| **上下文文件**（`AGENTS.md`） | 整份塞进 system prompt，每轮都占窗口 | 只在启动和 `/reload` 时读进内存 | 简短、所有任务都要遵守的硬规则（命令、边界、风格） |
| **Skill**（`SKILL.md`） | 平时只在 `<skills>` 清单里占一行简介和路径；需要时再读正文 | 索引表在启动/`/reload` 时扫；**正文每次调用现读磁盘** | 几百行的发布流程、排障手册和脚本 |

抓住最后一列和「何时读磁盘」这两栏，整套系统的分工就立住了：**规则常驻、Skill 按需、试错留在分支树里**。

## 唯一底层规则：只追加，不改写

普通聊天客户端把会话存成数组：压缩就删掉旧元素换摘要，改 system prompt 就覆写第 0 项。一旦覆盖，就没法退回半小时前另试一条路，事后也还原不出当时模型到底看到了什么提示词。

Pi 把整个会话存成一棵**只追加的 JSONL 树**。每行自带 `id` 和 `parentId`，指针 `leaf` 标记你此刻停在哪里——用 `/tree` 回到旧节点时一行不删，只是把 `leaf` 挪回去，新发言自动长出一条新分支。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="984-995" /> <Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1591-1602" />

最精巧的地方在于：**连非聊天状态的变化，也全都作为节点追加到树尾**：

- **规则或工具变更（新 `system` 消息）**：Pi 按 `<tools>`、`<rules>`、`<project_context>`、`<skills>` 等带名字的 XML 段落组织初始提示词；`/reload` 改了规则后，不回头改第 1 条消息，只把**有变化的段落**打包成一条新 `system` 消息追加到当前分支末尾。<Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="187-192" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1826-1848" />
- **上下文压缩（`compaction`）**：追加一条摘要节点，记录「从哪条近期消息开始保留原文」（`firstKeptEntryId`），同时把那一刻合并后的完整 `system` 状态存成快照。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="1278-1305" />
- **隐藏或替换旧消息（`context_edit`）**：追加一条指向旧条目 `targetId` 的记录，`replacement: null` 代表对模型隐藏它，原消息在 JSONL 里纹丝不动。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="174-180" />
- **跨分支带走结论（`branch_summary`）**：`/tree` 切走时若选择总结旧分支，摘要追加到**目标分支**，旧分支保持原样。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="4280-4292" />

这样做不仅让分叉回退零成本，还能**保住服务端前缀缓存（prefix cache）**：对允许对话中途出现 `system` 消息的模型接口，新更新直接留在末尾，前面几万 token 的历史前缀一字未动；对只认开头一条 `system` 的接口，才在发送前合并成新开头。<Src {...source} p="packages/ai/src/utils/transcript.ts" l="104-120" /> 就连请求模型生成压缩摘要这种一次性调用，Pi 都特意传了 `cacheRetention: "none"`，不花冤枉钱写缓存。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="626-632" /> 对比 [Hermes 的冻结快照](/notes/hermes-memory-skills/#一条约束不要弄脏前缀缓存)：Hermes 靠「会话中途不改 system prompt」保缓存，Pi 靠「允许更新但只往末尾追加差异」保缓存。

## 会话树与压缩：一份文件怎样算出不同上下文

同一份会话里，`/tree` 在原文件内切分支，`/fork` 把某条历史消息拆成独立新文件，`/clone` 把当前分支拷成新会话。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-48" /> 正因为一份 JSONL 里可能并存好几条分叉，**文件的行顺序不是模型看到的顺序**。每次发请求前，`SessionManager` 按三步组装上下文：

1. **找祖先链**：从当前 `leaf` 顺着 `parentId` 走回根，倒序排成一条消息链；所有旁支无论多新一律忽略。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="390-416" />
2. **截断到最近一次压缩**：取这条链上**最后一条** `compaction`，把更早的消息换成「压缩记录（先放合并好的 `system` 快照，再放摘要）+ `firstKeptEntryId` 起的近期原文 + 压缩后的新消息」。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="468-512" />
3. **应用 `context_edit`**：对留下的条目应用链上最后一条指向它的编辑——`null` 就隐藏，否则替换正文。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="519-574" />

同一份 JSONL 在分支 A 和分支 B 上会算出两套完全不同的上下文：

<FigPiBranch />

因为每步只沿当前祖先链计算，**压缩摘要和 `context_edit` 都严格属于它们所在的那条分支**。切回分支 A，分支 B 末端的 `checkpoint` 立刻退出视野，A 的原始消息完好回归。

```ts title="packages/coding-agent/src/core/session-manager.ts · 499–511（为什么跳过保留区里的 system）"
const contextEntries: SessionEntry[] = [compaction];
let foundFirstKept = false;
for (let i = 0; i < compactionIdx; i++) {
	const entry = path[i];
	if (entry.id === compaction.firstKeptEntryId) {
		foundFirstKept = true;
	}
	if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
		contextEntries.push(entry);
	}
}
contextEntries.push(...path.slice(compactionIdx + 1));
return contextEntries;
```

### 超限恢复、两个预算参数与「假修改」陷阱

- **超限恢复为什么先写 `context_edit` 再压缩**：请求因超限报错或中途截断时，失败回答已记在树里（留着计费排查）。Pi 先追加 `context_edit(targetId, null)` 隐藏这次失败记录，再压缩并重试——**最多试一次**防止死循环烧钱；哪怕压缩本身中途失败，隐藏记录仍留在分支上，下次发请求不会再带进坏记录。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3180-3216" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="85-98" />
- **两个最容易搞混的预算**：`reserveTokens`（默认 **16,384**）决定**什么时候触发**（`contextTokens > contextWindow - reserveTokens`，随时也能敲 `/compact [补充要求]` 手动压缩）；`keepRecentTokens`（默认 **20,000**）决定**压的时候留多少近期原文**。连续压缩会在旧摘要上增量改写，每次都会再丢一层细节；切点绝不劈开工具调用与 `toolResult`，单轮超长时则把本轮前半程单独压成第二份摘要拼接。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="267-270" /> <Src {...source} p="packages/coding-agent/docs/compaction.md" l="27-41" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="872-894" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="976-1040" />
- **「已修改文件」清单的陷阱**：摘要末尾自动附带 `<read-files>` 和 `<modified-files>`，但统计代码 `addFileOp` **只看工具调用的参数，完全不核对执行结果**（包括 codemode 批量脚本记在工具结果里的嵌套调用）——凡是调用过 `edit` 或 `write` 的路径一律归进 `modifiedFiles`（同时从 `readFiles` 剔除），跨次压缩还会一路累加。<Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="27-73" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="57-88" /> <Src {...source} p="packages/ai/src/types.ts" l="627-639" />

## AGENTS.md 与 Skill：为什么一次请求会新旧并存

会话树管的是「单次会话怎么分叉和压缩」；能跨会话留下来的，是另外两条通道——磁盘上的 `AGENTS.md` 和 `SKILL.md`。把它们各自的读盘时机摆在一起，开头那个「新旧并存」的悬念立刻就通了。

**上下文文件（`AGENTS.md`）按目录叠加、同目录覆盖，且没有文件监听。** Pi 先读 `~/.pi/agent/`，再从 `cwd` 一路向上扫到**文件系统根目录 `/`**（不停在 Git 根），同目录只取第一个命中的文件：`AGENTS.override.md > AGENTS.md > AGENTS.MD > CLAUDE.md > CLAUDE.MD`。<Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="214-233" /> <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="262-304" /> 它在启动时读进内存后就不再重读——会话中途改了 `AGENTS.md`，必须敲 `/reload`，新内容才会作为一条新 `system` 更新追加进来。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="1798-1824" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3831-3873" />

**Skill 则完全相反：Pi 没有专门的 `skill` 工具，内存只存索引、正文现用现读。** Pi 只在 system prompt 的 `<skills>` 段落里放一张 `<available_skills>` 清单（名字 + 简介 + 磁盘绝对路径），直接让模型用 `read` 去读文件（如果连 `read` 和 `bash` 都被禁了，整段 `<skills>` 直接省掉）。<Src {...source} p="packages/coding-agent/src/core/skills.ts" l="347-388" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="173-181" /> 而用户手敲 `/skill:name` 时，同样只查索引拿路径，然后当场 `readFileSync`：

这直接推出三条结果：

1. **只改已有 Skill 的正文** → 不用 `/reload`，下次 `read` 或 `/skill:name` 立刻拿到新正文；但之前轮次展开过的旧正文作为普通 `user` 消息仍留在历史里。
2. **改了 `description` 或 `disable-model-invocation`** → 必须 `/reload`，因为 `<skills>` 清单缓存在内存里。<Src {...source} p="packages/coding-agent/src/core/skills.ts" l="352-360" />
3. **新建或改名了 Skill** → 必须 `/reload`，否则索引里找不到，手敲 `/skill:新名字` 会原封不动当普通聊天发给模型。

下面是直接跑源码截获的五次真实请求——启动时放 `RULE_A`（`AGENTS.md`）和 `release`（`DESC_A` / `BODY_A`），第 1 轮调用后把磁盘全改成 `B` 并新建 `late`。在「改磁盘文件后」那一轮，**同一次请求里同时装着 `RULE_A · DESC_A`、旧 `BODY_A` 和新 `BODY_B`**：

<FigPiSkillRequests />

有个排查问题时极易误判的细节：`/reload` 后如果直接拿字符串全文搜底层请求，`RULE_A` **依然搜得到**——因为开头的第 1 条 `system` 消息没被改写，新内容是在末尾追加的第二条 `system` 更新；只有按顺序合并后（`getCurrentSystemMessage()`），生效的才是 `RULE_B · DESC_B · NEW_SKILL`。

汇总成一张 4 行速查表：

| 场景 | 改了 `AGENTS.md` | 改了已有 Skill 正文 | 新建 Skill 或改简介 |
|---|---|---|---|
| **同一会话下一轮** | 看不到（仍是旧规则） | 立刻拿到新正文；旧正文仍留在前面消息里 | 索引没变；`/skill:新名字` 当普通字发走 |
| **执行 `/reload` 后** | 追加新 `system` 更新，生效 | 同上 | `<skills>` 索引更新，命令可正常展开 |
| **同目录 `/new` 新会话** | 读到新文件 | 读到新文件 | 出现在初始 `<skills>` 清单（**不继承旧聊天**） |
| **`/tree` 切回旧分支** | 下一轮前自动对比并补一条 `system` 更新同步最新规则[^tree] | 只保留该分支自己当年展开过的正文 | 同左 |

## 想自己加长期记忆，从哪接入

默认不同会话互不共享历史（只有 `--continue` 或 `/resume` 才续接旧文件）。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="5-22" /> 如果你想自己搭类似 Hermes 的后台复盘或结构化记忆，Pi 提供了四个互不打架的扩展接口：

1. **`pi.appendEntry(customType, data)`**：往当前分支存自定义状态，重启或切分支可恢复，**完全不发给模型**、不占 token。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="118-132" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1683-1690" />
2. **`custom_message`（`sendMessage`）**：同样挂在分支上，但**会转成消息进上下文**。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="147-165" />
3. **`before_agent_start`**：每轮前动态修改 `systemPromptOptions.sections`（比如从外部库检索记忆塞进自定义段落，Pi 自动对比变化并追加更新）。<Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-657" />
4. **`session_before_compact` 与 `agent_end`**：前者接管压缩摘要怎么写，后者在回合结束后异步提炼经验落盘。<Src {...source} p="packages/coding-agent/docs/extensions.md" l="534-552" />

## 踩坑清单与文档差异

### 实战中最容易踩的 4 个坑

以下是我基于源码机制做的工程判断：

1. **改了规则没任何刷新提示**：会话运行中改了 `AGENTS.md` 或 Skill 简介，界面不会提醒「需 `/reload`」，很容易对着旧规则白查半天。
2. **反复改 Skill 反复调，新旧正文会同框**：每次 `/skill:name` 都把正文写成永久 `user` 消息，同一会话里多版正文并存，只能靠模型自己分哪条最新。
3. **`modifiedFiles` 把「试图改」记成「已改过」**：`edit` 报错照样进清单、跨压缩一路累加，长会话多次压缩后可能误导模型跳过本该重做的修改。
4. **`AGENTS.md` 免信任且一路扫到 `/`** ：刚克隆的陌生仓库带 `AGENTS.md` 就会直接进 system prompt；家目录 `~/` 放了全局 `AGENTS.md`，在 `~/tmp/` 做测试也会顺带扫进去。

## 回看开篇的四个问题

1. **没有内置记忆库时，长期规则、操作步骤、临时试错怎么存？** 长期规则写进 `AGENTS.md` / `CLAUDE.md` 启动拼进系统提示，可复用步骤写成 `SKILL.md` 启动只列索引、用时 `read` 正文，临时试错留在 JSONL 会话树里随压缩折成摘要。
2. **为什么 JSONL 里写着的消息模型可能一次都看不到？切回旧分支时，另一条分支的压缩摘要去哪了？** Pi 发请求前从当前节点沿 `parentId` 倒推回根，遇到该分支上最新的压缩点就跳到 `firstKeptEntryId`；被跳过的旧消息、非当前路径的分支，以及另一条分支上生成的压缩摘要虽然仍留在文件里，都不会出现在本次请求中。
3. **中途同改 `AGENTS.md` 和 `SKILL.md` 且未 `/reload`，为何同一次请求会同时带着旧规则、旧正文和新正文？** 因为 `AGENTS.md` 与 Skill 索引在会话启动时已缓存，改盘不重读；而 `/skill:name` 和 `read` 每次都直接现读磁盘，旧消息留在对话历史里，新展开又带进新正文，三者便同框出现在同一请求。
4. **想给 Pi 加上长期记忆，该从哪几个扩展接口切入？** `before_agent_start` 负责动态注入系统提示或记忆消息，`context` 负责发请求前裁剪/重写消息列表，`session_before_compact` / `session_before_tree` 负责接管压缩与切分支摘要，`appendEntry` 负责往 JSONL 里写不进模型的扩展状态。
