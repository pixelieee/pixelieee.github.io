## 同一次调用，可以同时看到旧规则和新步骤

我给一个 `release` Skill 放了两处容易辨认的文字：目录描述是 `DESC_A`，正文是 `BODY_A`。项目的 `AGENTS.md` 另写 `RULE_A`。第一次调用之后，把三个 A 都换成 B，再创建一个叫 `late` 的 Skill。保持会话开启，再次发出同一句 `/skill:release`。

在 Pi 真正交给测试 provider 的请求里，当前有效的系统规则还是 **A**，这次调用展开的步骤已经是 **B**；更早的用户消息里还保留着上一份 **A**。表面上矛盾的三个答案各自都对。规则和目录来自上次加载资源时构造的系统提示词，命令执行时按路径读正文，旧消息则沿当前分支继续发送。切换下图，可以看见到底是哪一行先变。

## 同一条经验，三条读取路径

假设一次排错发现「发布前要先生成索引」。把它留在不同地方，之后看见它的人就不同。

| 放在哪里 | 谁写入、谁读取 | 下一次何时可见 |
|---|---|---|
| 会话消息、压缩或分支摘要 | 运行时追加记录，SessionManager 重建当前路径 | 恢复或沿用相应分支时。开一个独立会话没有这条路径 |
| 项目或用户指令 | 人或有文件写权限的工具改 Markdown，资源加载器读取 | 在适用目录新开会话，或在当前会话重新加载资源 |
| `skills/release/SKILL.md` | 作者维护步骤，资源加载器登记元数据 | 名称、描述及路径可进入提示词，正文由模型按需读，或由人显式调用 |

项目文件可以通过版本控制分享，用户目录也可以由同一用户的多个项目共用。会话文件按工作目录归组只影响寻找和恢复会话，并不会把同目录最近的聊天拼进每个新请求。`--continue`、`/resume` 和 `/new` 是不同的入口。<Src {...source} p="packages/coding-agent/docs/sessions.md" l="7-27" /> <Src {...source} p="packages/coding-agent/docs/sessions.md" l="61-72" />

## 磁盘保留两条路，请求只走一条

持久会话默认保存在 `~/.pi/agent/sessions/`。一条消息所在的记录带有 `id` 和 `parentId`；追加时，新记录成为当前叶节点的孩子。`/tree` 在同一份会话里换位置，`/fork` 从较早的用户消息另建会话，`/clone` 则复制当前分支。用文本编辑器打开 JSONL 看到的是追加次序，不能据此推断模型接收的消息次序。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="983-995" /> <Src {...source} p="packages/coding-agent/docs/sessions.md" l="36-49" />

## 压缩到底从哪儿取得“修改过的文件”？

再回到发布任务。这次我让测试 provider 调用 Pi 自带的 `edit`，把 `release.md` 中一段根本不存在的旧文字换掉。工具返回错误，磁盘上的文件仍是 `unchanged`。等新一轮开始，我把真实会话交给 Pi 的压缩准备函数，给近期原文留 1 token，以便将这次调用纳入待总结区。文件列表里出现了 `release.md`。

```json title="同一次失败操作的三处观察"
{
  "toolError": true,
  "onDisk": "unchanged",
  "readFiles": [],
  "modifiedFiles": ["release.md"]
}
```

这个列表的来源可以精确到三步。先在**可见消息**里找 assistant 发出的 `read`、`write`、`edit` 工具调用；对于通过 codemode 间接发出的调用，还会读工具结果里的嵌套调用记录。再按参数里的 `path` 归类、去重。如果同一路径既读过又尝试编辑，只列入修改一栏。最后把清单附到摘要末尾，也放入结构化的 `details`。这条路径没有逐项检验直接编辑是否成功，也没有读 Git 差异。<Src {...source} p="packages/coding-agent/src/core/compaction/utils.ts" l="29-74" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="899-919" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="1037-1056" />

这还会影响第二次压缩。默认压缩器会把上一次非扩展检查点中记录的文件集合并入新集合；旧摘要本身也会作为更新摘要的输入。因此，只凭较晚的 `modifiedFiles` 能找到一个**值得重新检查的路径**，要回答“发布清单究竟更新了没有”，仍需回到工具结果或产物。上面的实验实测到压缩准备层，摘要文本的生成与后续合并是沿源码核对的。<Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="51-83" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="713-733" />

### 一个很长的工具回合会被从哪儿切开

如果预算边界落在一轮排错的中间，Pi 不会随意从一个工具返回值开始保留。它在当前分支的有效消息上选合法切点，把材料分成三段：这一轮以前的历史、这一轮已完成的前半段、继续保留原文的尾部。前两段都有材料时，分别生成历史摘要与回合前缀摘要，再用 `Turn Context (split turn)` 接起来。已经有旧摘要而没有新增的早期历史时，旧摘要可以直接承担第一段。这样最新的工具交换还能接上它所回答的问题。代价是连续压缩依赖先前概括过的内容，早先漏掉的选择理由未必会在下一次重新出现。<Src {...source} p="packages/coding-agent/docs/compaction.md" l="87-98" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="863-919" /> <Src {...source} p="packages/coding-agent/src/core/compaction/compaction.ts" l="980-1020" />

## 项目指令怎样进入下一轮

资源加载器先检查 agent 目录，再收集工作目录的祖先，按由远到近的顺序排列。**同一目录只取一个候选文件**，依次尝试 `AGENTS.override.md`、`AGENTS.md`、`AGENTS.MD`、`CLAUDE.md`、`CLAUDE.MD`。所以在 `repo/sub` 加 override 不会抹掉 `repo` 的规则，它改变的是 `sub` 自己贡献哪一份文件。嵌套的 Git worktree 还要处理一个特例，避免同一仓库位置在父树和工作树里重复贡献指令。<Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="214-260" /> <Src {...source} p="packages/coding-agent/src/core/resource-loader.ts" l="262-304" />

文件正文随后进入 system prompt 的项目上下文。官方配置文档明确写出，发现这些上下文文件无需项目授权；它们与项目 `.pi` 的配置是两条路径。拿一个仓库的 AGENTS.md 来解释会话行为时，启动目录和 agent 目录都应一并记录，否则另一个人即使打开同一个仓库，也可能读到不同的祖先指令。<Src {...source} p="packages/coding-agent/docs/configuration.md" l="39-47" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="79-91" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="170-181" />

## Skill 的描述和正文有不同的更新时间

启动时，资源加载器解析 Skill 的 frontmatter，保存名称、描述、文件路径、基础目录和调用策略。缺少有效描述会跳过；若只是某些名称规范不合，代码可以给诊断后继续登记。默认的自动选择目录为模型提供名称、描述和位置。`disable-model-invocation: true` 会把该项排除，提示词构造器还会检查所选工具是否提供读取路径。宿主读取过文件来解析 frontmatter，不等于文件全文已经发送给模型。<Src {...source} p="packages/coding-agent/src/core/skills.ts" l="277-344" /> <Src {...source} p="packages/coding-agent/src/core/skills.ts" l="352-390" /> <Src {...source} p="packages/coding-agent/src/core/system-prompt.ts" l="171-181" />

显式输入 `/skill:release v2` 走另一条路。Pi 在当前登记表里按名称找 Skill，**当场重新读磁盘文件**，去掉 frontmatter，将正文、相对路径基准和用户追加的 `v2` 组织成输入。由此可以预测一个容易误判的结果：只改已有 Skill 的正文，再显式调用，可能马上得到新步骤；新建或改名则需要让当前登记表重新发现它，`/reload` 会重载资源并重建运行时。此前已经进入聊天的旧正文依然属于之前那条消息。<Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="2310-2338" /> <Src {...source} p="packages/coding-agent/src/core/agent-session.ts" l="3849-3877" />

## 实验：切回 A，B 的摘要会跟过来吗？

在固定提交的仓库根目录执行 `npm ci --ignore-scripts`，把下面保存为 `probe.mjs`。执行 `node --import ./packages/coding-agent/src/experimental/source-resolver.ts probe.mjs`。这里用了真实 SessionManager 的内存模式，刻意只检验分支和上下文重建；压缩摘要由实验直接提供，没有向模型请求摘要。

```js title="probe.mjs"
import {SessionManager} from './packages/coding-agent/src/core/session-manager.ts';
const log = SessionManager.inMemory();
const say = text => log.appendMessage({role:'user', content:text, timestamp:0});
const root=say('base'); const left=say('attempt A');
log.branch(root); const right=say('attempt B');
console.log('raw messages',log.getEntries().filter(e=>e.type==='message').map(e=>e.message.content));
console.log('active leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendCompaction('checkpoint', right, 1200);
console.log('compacted',log.buildSessionContext().messages.map(m=>m.summary ?? m.content));
log.branch(left);
console.log('other leaf',log.buildSessionContext().messages.map(m=>m.content));
log.appendContextEdit(left, null);
console.log('edited A', log.buildSessionContext().messages.map(m=>m.content));
```

| 观察点 | 实测输出（按顺序） |
|---|---|
| 遍历原始消息 | `base`、`attempt A`、`attempt B` |
| B 是当前叶 | `base`、`attempt B` |
| 在 B 后追加 checkpoint | `checkpoint`、`attempt B` |
| 再切回 A | `base`、`attempt A` |
| 在 A 追加一条省略编辑 | `base` |

本实验前四行只改变了分支或压缩边界。第五行在 A 的原始消息仍然存在时，单独通过一条编辑把它移出请求。本次另运行了官方的 Skill 解析、同名优先级和会话上下文重建测试。对照整个调用链，这些观察能解释历史如何被筛选，无法衡量模型自己撰写摘要时遗漏事实的比例。<Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="126-147" /> <Src {...source} p="packages/coding-agent/test/session-manager/build-context.test.ts" l="211-246" />

## 哪些变化能跨会话积累

这版默认 coding agent 里，可追到的持久写入是会话条目、对用户或项目文件的编辑，以及扩展明确实现的写入。默认压缩和切分支能改变后续上下文；在上述路径里，没有找到从成功会话自动提炼 Skill、按使用次数改写它、再归档旧版本的维护器。要让发布经验在**新项目会话**里重复生效，可以有意识地更新相应指令或 Skill，并用一次全新会话检查可见范围。若要跨仓库共享，位置和分发方式也要相应改变。<Src {...source} p="packages/coding-agent/docs/skills.md" l="58-67" /> <Src {...source} p="packages/coding-agent/docs/skills.md" l="87-93" />

Pi 给扩展留了不同层次的接口。`pi.appendEntry()` 能让扩展状态随会话保存，但该条目本身不进入模型上下文；自定义消息可以进入。`session_before_compact` 可以替换摘要策略，`before_agent_start` 可以改本轮的输入。这些接口足以构建带复盘的应用。评估某个具体 Pi 部署时，还需找出实际安装的扩展、谁触发写入、写到哪里，以及新会话谁来读。<Infer /> 把复用交给可编辑文件使改动容易审阅，同时也意味着，一条只在对话中获得、从未写回的经验，可能在原会话之外完全不可见。<Src {...source} p="packages/coding-agent/src/core/session-manager.ts" l="122-134" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="532-552" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="615-635" /> <Src {...source} p="packages/coding-agent/docs/extensions.md" l="1625-1633" />

### 两个官方扩展示例，把“进化”落实到是谁写、谁读

看 `todo` 示例，工具每次返回时在结构化的 `details` 里放整份待办快照和下一个 ID。扩展收到 `session_start` 或 `session_tree`，先清掉内存变量，再沿当前分支回放属于 `todo` 的工具结果。切回较早叶节点，扩展便能恢复那个分支的任务状态。这里有持久化，也有恢复，范围由这份会话与所选分支划定。<Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="106-138" /> <Src {...source} p="packages/coding-agent/examples/extensions/todo.ts" l="147-177" />

要把一次排错明确交给**另一个会话**，官方还给了一个 `/handoff` 示例。它从旧分支收集材料，结合用户提供的下一步目标生成交接草稿。用户可编辑、可取消。新会话保存父会话引用并将草稿放进编辑器，由用户决定是否发送。这条链的产物是一条面向下一次任务的提示词；安装这个扩展、触发命令和确认交接是三个可定位的决定。两个示例都没有把这次经验发布成所有项目都能发现的 `SKILL.md`。<Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="85-116" /> <Src {...source} p="packages/coding-agent/examples/extensions/handoff.ts" l="161-190" />

我的判断是，Pi 在排错时最有价值的特性，是能从一个意外答案追溯到**哪一条分支、哪次资源加载、哪次显式调用**。代价同样具体：用户修正过的步骤可能同时存在于旧消息和新文件中，压缩清单也可能只记录了尝试修改的路径。要证明一条经验已经变成可迁移的做法，最直接的检查是从一个全新会话调用目标 Skill，观察实际展开的步骤。

Pi 沿当前叶节点重建消息，Hermes 另提供主动检索会话历史的工具。判断一次回答怎样用到了旧材料，前者可以查分支，后者还可以查历史工具调用。 [对照 Hermes 的实现](/notes/hermes-memory-skills/#会话历史与-session_search)
