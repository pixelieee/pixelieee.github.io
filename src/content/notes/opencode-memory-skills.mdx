**一句话结论：** OpenCode 没有统一的内置记忆库，但它的刷新节奏和 Pi 刚好相反——`AGENTS.md` 每轮重读磁盘，`SKILL.md` 正文却缓存在进程内存里直到重启，SQLite 保留原始工具记录，而压缩器只拿工具输出的前 2,000 个 UTF-16 字符写摘要。<Src {...source} p="packages/opencode/src/session/prompt.ts" l="1255-1285" /> <Src {...source} p="packages/opencode/src/session/compaction.ts" l="50-79" />

读完这篇，你能搞清四件事：

1. 同一个会话中途同时改了 `AGENTS.md` 和 `SKILL.md`：为什么下一轮立刻看到**新版规则**，调用 `skill` 却还返回**旧版正文**？
2. 一次完整的 Skill 读取经过压缩和进程重启后，为什么尾部步骤消失了，SQLite 数据库里却还能查到原文？
3. 为什么两个目录里放了同名 Skill，8 次冷启动会随机命中不同文件，甚至让重启后的同一次请求混进两个来源？
4. 一个 Skill 明明存在磁盘上却用不了，到底卡在**发现、清单展示、还是权限审批**哪一道门？

本文固定 **v1.18.33**（提交 `51ef4be`），所有实验均由正式版 `opencode run` / `opencode serve` 搭配本地回环 HTTP 服务实测完成。

## 一张图看懂：和 Pi 刚好相反的设计

| 通道 | 存在哪里 | 何时读磁盘 | 修改后何时生效 |
|---|---|---|---|
| **项目规则**（`AGENTS.md`） | 全局配置目录、仓库祖先目录、`read` 触发的子目录 | **每次普通请求重读** | 改完保存，下一轮立刻生效 |
| **Skill**（`SKILL.md`） | 进程内存的实例注册表（含正文 `content`） | **进程启动时一次性扫描解析** | 必须重启进程/服务才能读到新版 |
| **会话历史**（SQLite） | `session` / `message` / `part` 三张表 | 按 `session_id` 查询并套用过滤规则 | 原文一直在库里；模型只看到最新摘要与保留尾段 |

## 项目规则：每轮重读，读文件还会顺路补子目录

OpenCode 找规则分全局和项目两层，行为藏着两个容易看错的细节：

- **遇到首个命中的文件名就跳出文件名循环，但同一文件名会一路向上收集。** 全局先找配置目录的 `AGENTS.md`（兼容 `~/.claude/CLAUDE.md`）；项目层按顺序试 `AGENTS.md` → `CLAUDE.md` → 旧式 `CONTEXT.md`。一旦在工作目录到仓库根之间找到任意 `AGENTS.md`，就会把这条路径上**所有的 `AGENTS.md` 都收进来**，同时跳过后面的 `CLAUDE.md` 查找。<Src {...source} p="packages/opencode/src/session/instruction.ts" l="60-68" /> <Src {...source} p="packages/opencode/src/session/instruction.ts" l="110-150" /> <Src {...source} p="packages/core/src/fs-util.ts" l="154-166" />
- **用 `read` 打开子目录文件时，会动态补加载附近规则。** 从仓库根启动会话时，深层子包的 `AGENTS.md` 最初并不在 `system` 里；直到模型调用 `read` 读了那个子包里的代码，工具会顺着文件路径向上找尚未加载的规则并附在结果里（跳过已在 `system`、历史或本条消息里认领过的）。配置里的 `instructions` 还能直接指定额外文件、glob 或 URL。<Src {...source} p="packages/opencode/src/tool/read.ts" l="294-314" /> <Src {...source} p="packages/opencode/src/session/instruction.ts" l="179-220" /> <Src {...source} p="packages/web/src/content/docs/rules.mdx" l="109-131" />

因为规则加载器在每轮构造请求前都会重新读盘，在同一会话里改完 `AGENTS.md` 和 `SKILL.md` 再调用，实测立刻呈现出「规则变新、Skill 仍是旧版」：

## SQLite 与压缩：库里留原文，但摘要前硬切 2,000 字符

OpenCode 把会话拆成 `session`、`message`、`part` 三张 SQLite 表，事件投影器负责落库；新开会话不共享旧消息，只有传 `--session` 或续接最近顶层会话时才按同一个 `session_id` 加载历史。<Src {...source} p="packages/core/src/session/sql.ts" l="22-36" /> <Src {...source} p="packages/core/src/session/sql.ts" l="68-98" /> <Src {...source} p="packages/opencode/src/cli/cmd/run.ts" l="452-528" />

上下文变长时，OpenCode 有两套截然不同的瘦身机制，**都不会擦除 SQLite 里的原始字符串**：

1. **工具输出清理（`prune`）——保护 `skill`，只打时间戳。** 从新往旧扫描已完成的工具输出，保留最近约 **40,000** token 的保护区且跳过 `skill` 工具；当更早的可清理输出超过 **20,000** token 时，给对应 part 写上 `state.time.compacted`。之后发给模型时，转换器看到这个时间戳就输出 `[Old tool result content cleared]`，数据库里的原文本身一字未删。<Src {...source} p="packages/opencode/src/session/compaction.ts" l="28-33" /> <Src {...source} p="packages/opencode/src/session/compaction.ts" l="271-315" /> <Src {...source} p="packages/opencode/src/session/message-v2.ts" l="290-302" />
2. **会话压缩（`compaction`）——不保护 `skill`，进摘要前直接按 2,000 字符硬切。** 自动阈值超限或手动调用 `/session/{id}/summarize` 时，OpenCode 把旧历史序列化后交给 compaction agent 写摘要，并把保留近期原文的起点记在 `tail_start_id`。但序列化工具输出时，**所有工具一律按前 2,000 个 UTF-16 代码单元硬截断**：

```ts title="packages/opencode/src/session/compaction.ts · 51–52, 76–79"
const truncate = (value: string) =>
  value.length <= TOOL_OUTPUT_MAX_CHARS ? value : `${value.slice(0, TOOL_OUTPUT_MAX_CHARS)}\n[truncated]`

const output = part.state.time.compacted
  ? "[Old tool result content cleared]"
  : truncate([part.state.output, ...attachments].join("\n"))
return [call, `[Tool result]: ${output}`]
```

- **摘要失败不会替换历史。** 只有已完成且无错的摘要才能在恢复时截断历史；若摘要调用本身超限报错，磁盘上虽有 `summary: true` 消息，下次恢复仍不会拿它当有效断点。<Src {...source} p="packages/opencode/src/session/compaction.ts" l="358-391" /> <Src {...source} p="packages/opencode/src/session/message-v2.ts" l="525-546" />

## Skill 三道门：发现、展示、审批，外加并发竞态

排查 OpenCode 里一个 Skill 为什么「找不到」或「读不出」，要分清三道互相独立的门：

1. **发现门（启动扫描 + 内存缓存正文）**：扫描用户与仓库的 `.claude/skills`、`.agents/skills`、配置目录的 `skill/` 或 `skills/`，以及 `skills.paths` / `skills.urls`；解析 frontmatter 后连同**正文 `content`** 一起写进实例注册表（先登记内置技能 `customize-opencode`，所以磁盘同名文件可覆盖它）。缺少 `description` 不会被解析器拒收，照样进注册表。<Src {...source} p="packages/opencode/src/skill/index.ts" l="105-139" /> <Src {...source} p="packages/opencode/src/skill/index.ts" l="258-285" />
2. **展示门（`<available_skills>` 在 `system` 里，不在工具描述里）**：生成清单时，`Skill.available(agent)` 过滤掉权限为 `deny` 的项并省略没写 `description` 的项（`ask` 仍展示）；清单实际插在 **`system` 消息**里，`skill` 工具说明只让模型去 `system` 里看名字（若整个 `skill` 工具被禁，整段清单省略）。<Src {...source} p="packages/opencode/src/skill/index.ts" l="310-337" /> <Src {...source} p="packages/opencode/src/session/system.ts" l="107-118" /> <Src {...source} p="packages/opencode/src/tool/skill.txt" l="1-5" />
3. **执行审批门（调用时才触发 `ctx.ask`）**：工具按名字查内存注册表，再跑权限判定（取最后一条同时匹配工具与模式的规则）。获准后返回 `info.content`、基目录和**最多 10 条**辅助文件路径（只列路径，不执行脚本也不读文件内容）。<Src {...source} p="packages/opencode/src/tool/skill.ts" l="21-65" /> <Src {...source} p="packages/opencode/src/permission/index.ts" l="67-101" />

用正式程序实测同一份 `release` 技能在三种权限下的表现：

| 策略 | `system` 清单里有没有 | 调用 `skill("release")` 实际结果 |
|---|---|---|
| `allow`（普通 agent） | 列出 `release` | 直接返回完整正文与辅助文件列表 |
| `deny`（`reviewer`） | 不列出 `release` | `skill` 工具仍在定义里，点名调用直接返回权限拒绝，无正文 |
| `ask`（`approver`） | 列出 `release` | 挂起待批请求；回复 `once` 只放行这一次，同会话再调会生成新的审批 ID |

## 哪些变化能跨会话留下来

OpenCode 没有回合结束后的自动复盘器，不会因为某个 Skill 跑成功了就自动改写 `SKILL.md`。能跨会话留存的路径只有三条：

1. **明确写回可发现的磁盘文件**：`/init` 命令模板引导模型阅读仓库并更新项目根 `AGENTS.md`，普通编辑工具也能按要求把流程写成 `SKILL.md`。<Src {...source} p="packages/opencode/src/command/template/initialize.txt" l="33-66" /> <Src {...source} p="packages/opencode/src/tool/registry.ts" l="211-246" />
2. **特定模型分支的提示词记忆（非全局默认）**：无自定义提示词且命中某些模型名时，OpenCode 会走 `PROMPT_BEAST` 模板，指示模型在用户要求记住某事时写 `.github/instructions/memory.instruction.md`——但默认规则加载器根本不扫这个路径，不能当成通用的跨会话记忆保证。<Src {...source} p="packages/opencode/src/session/llm/request.ts" l="53-67" /> <Src {...source} p="packages/opencode/src/session/prompt/beast.txt" l="114-134" />
3. **插件钩子**：`experimental.session.compacting` 允许插件在压缩时注入额外上下文或替换摘要提示词；但真正的长期记忆写入、去重和技能演进要由插件自己实现。<Src {...source} p="packages/plugin/src/index.ts" l="291-316" /> <Src {...source} p="packages/web/src/content/docs/plugins.mdx" l="350-389" />

## 踩坑清单与文档差异

### 实战中最容易踩的 4 个坑

<Infer /> 以下基于源码与实测结果做出的工程判断：

1. **改完 `SKILL.md` 看到新规则就以为 Skill 也刷新了**：`AGENTS.md` 每轮现读、Skill 正文缓存到重启，在运行中的服务里会稳定出现「规则 V2 + Skill V1」。
2. **长 Skill 经过压缩必丢尾段**：`prune` 保护了 `skill`，但真正压缩时 `truncate()` 按 2,000 个 UTF-16 字符一刀切（含 `<skill_content>` 封装），重要收尾检查放末尾极易在进摘要前就被切掉。
3. **同名 Skill 千万别指望「项目覆盖全局」**：无界并发解析导致后完成者覆写先完成者，跨目录重名会随机抖动，恢复会话时甚至前后不一致。
4. **手动压缩在上下文很宽裕时可能清空全部近期原文**：整段历史都装进 `preserve_recent_tokens` 时切点为 0，反而不会设 `tail_start_id` 保留尾段。

## 回看开篇的四个问题

1. **中途同改 `AGENTS.md` 和 `SKILL.md`，为何下一轮立刻见新规则，调 `skill` 却还返回旧正文？** OpenCode 每轮发请求前都会重新读取磁盘上的 `AGENTS.md`，但所有 Skill 的解析结果（含正文）都在进程首次扫描后缓存在内存里，直到重启进程才会重新读盘。
2. **完整读取的 Skill 经过压缩和重启后，为何尾部步骤消失，SQLite 里却还能查到原文？** 原始工具输出完整留在 SQLite 的 `part` 表里永不删改；但压缩前构造摘要输入时会把旧工具输出裁到前 2,000 个 UTF-16 字符，尾部的 `TAIL_CHECKPOINT_PROBE` 在写摘要前就被截掉了，新进程沿摘要续聊自然看不见。
3. **两个目录放同名 Skill，为何 8 次冷启动随机命中不同文件，重启后还会混进两个来源？** 扫描函数用 `Promise.all` 无界并发遍历多个目录，后完成的写入覆盖先完成的，赢家取决于 I/O 落盘顺序；重连旧会话时，历史消息保留着上次调用的旧路径正文，而新进程的 `system` 清单可能已经换成了另一个赢家。
4. **Skill 存在磁盘上却用不了，到底卡在哪一道门？** 顺着三道门查：先看有没有被发现（目录层级、默认禁用外置路径或 `description` 缺失导致不进清单），再看有没有进入 `system` 的 `<available_skills>`，最后看 `permission.skill` 是 `allow`、`ask` 还是 `deny`。

准备 Python 3.10+、Git 和 OpenCode `v1.18.33` 可执行文件，两套脚本都使用本地回环服务，无需模型密钥，运行后会打印临时目录供核对原始 `requests.json` 与 SQLite 数据库：

- **压缩截断 + 重启 + `allow`/`deny`/`ask` 权限实测**：[下载 opencode-checkpoint.py](/experiments/opencode-checkpoint.py)

```sh title="复现压缩与权限实验"
python opencode-checkpoint.py
```

绑定脚本打印的 `:session_id`，可直接核对 SQLite 里未删减的工具原文（本次返回 `head = 50`、`tail = 2575`）：

```sql title="SQLite · part.data"
SELECT instr(json_extract(data, '$.state.output'), 'HEAD_CHECKPOINT_PROBE') AS head,
       instr(json_extract(data, '$.state.output'), 'TAIL_CHECKPOINT_PROBE') AS tail
FROM part
WHERE session_id = :session_id
  AND json_extract(data, '$.tool') = 'skill';
```

```sh title="复现同名竞态实验"
python opencode-skill-roots.py
```
