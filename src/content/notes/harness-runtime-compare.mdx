**一句话结论：** 前沿 harness 在「会话能不能续上」上已经很像；真正分出阵营的，是**真相放哪、谁去动外界、Agent 之间怎么说话、别人怎样嵌进来**这四件事。DeepSeek Harness 把模型可见历史做成了日志上的唯一事实，但循环自己仍然去调模型和工具——这正是「日志是真相」和「循环是纯命令」之间还空着的那一格。

这篇不是产品评测，也不是记忆 / Skill 专题（那几篇已经单独写过）。它只服务一个目的：让你读完以后，对 Pure Agent 的终局取舍有自己的判断，而不是被某一家的叙事带走。

读完你应能回答：

1. 「只追加 JSONL」和「日志是唯一事实」是不是一回事？
2. 为什么 dsh 说一切皆插件，却仍然不能叫「纯内核」？
3. 前台跟人说话、后台干活，各家分别靠什么拼出来？
4. 进程内库、按需子进程、常驻 App Server，各自在解决谁的问题？
5. Pure Agent 若要占一个还没人站稳的位置，最站得住的切口在哪？

## 轴 1：真相在哪

先分清两个常被混为一谈的说法。

**说法 A：会话落成只追加的文件。** Claude Code 默认把会话写到本地 JSONL，恢复时读回（官方 Glossary / Sessions）。Codex 有 rollout JSONL，「so sessions can be replayed or inspected later」（`codex-rs/rollout/src/recorder.rs`）。pi 的会话是带 `id` / `parentId` 的 JSONL 树。这只说明「聊过的内容能回来」，不说明「循环此刻信的是这份文件」。

**说法 B：发给模型的历史只能从日志推导。** 七家里，公开源码把这话说死的是 DeepSeek Harness：

> The LLM message history is *derived* from the log, never stored separately; replay is re-derivation from the same events.

出处：`docs/subsystems/session.md`（提交 `2e39e70`）。循环组请求时走 `session.deriveMessages()`（`packages/core/agent-loop/src/agent.ts` 一带）。

对照一下其余几家在轴 1 上的落点：

| | 落盘形态 | 循环当下信什么 | 算不算「日志唯一事实」 |
|---|---|---|---|
| Claude Code | JSONL 转录 | 文档未写内部；子进程拥有转录文件 | 文档未主张 |
| Codex | 内存 history + rollout JSONL + state DB | `run_turn` 读内存 history | 否。rollout 写失败不阻断继续 |
| pi | JSONL 树 | 循环中是内存消息；已终结上下文以 SessionManager 为准 | 对已落盘树是；对 in-flight 不是 |
| OpenCode | SQLite 会话 / 消息 / durable event | runner 读已记录的 Session history | 接近「提交记录」，不是命令级 fold |
| Hermes | SQLite persistence | 仍拿消息列表去调模型 | 规范副本，不是 fold 执行本体 |
| Alma | Memory topic 等产品对象 | 文档未写事件日志 | 不适用 |
| dsh | 追加 SessionEvent；JSONL 等为后端 | `deriveMessages()` | **对模型可见历史：是** |

所以：只追加很常见；**把日志当成循环的唯一输入**并不常见。OpenCode / Hermes / Codex 都有很强的持久化，但「下一步做什么」仍然捏在命令式循环和内存结构手里。

<Infer /> 若只学「落成 JSONL」，Pure Agent 学到的是入场券，不是差异。差异要从说法 B 继续往下挖——挖到轴 2。

## 轴 2：谁执行副作用

真相在日志里，并不自动等于「循环不会去动外界」。

DeepSeek Harness 在同一份设计里把两件事叠在一起：历史从日志来；循环仍然 `llm.stream`、仍然 `tools.execute`（`packages/core/agent-loop/src/agent.ts`）。工具路径上，内存里会先 `append('tool/call')` 再 `dispatch`（`packages/core/tools/src/batch.ts`）；磁盘上的「请求前 / 工具副作用前必须 flush」则是**可卸插件** `dsh-session-checkpoint-policy`。架构文档写明：

> Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself…

出处：`docs/architecture.md`。于是「先写后做」在 dsh 里是默认组合的行为，不是不可替换的内核函数。进程崩溃后，物理上有效的日志前缀由存储交回，未闭合的一轮由 `interruptedTurnClosers` 补合成结果再 append（`packages/core/agent-loop/src/index.ts`、`packages/core/session/src/repair.ts`）。这很强，但执行者仍是那个可被 patch 掉的 `AgentLoop` 服务。

把镜头拉开：

| | 循环是否亲自执行 | 先写后做有多硬 |
|---|---|---|
| Codex | 是，`run_turn` 采样并执行 function call | rollout 非 fail-closed；无 dsh 那种统一语义闭合入口 |
| pi | 是，`agent-loop` 调 `tool.execute` | 助手消息经监听器 append 后再跑工具；无强制 fsync |
| OpenCode | 是 | 本地工具在相关事件发布后再启动；靠 SQLite claim 续跑 |
| Hermes | 是 | 工具前 flush 到 session DB，失败则不执行 |
| dsh | **是** | 内存层硬；磁盘层是插件；resume 补合成 closer |

这里出现一个容易被宣传带偏的点：**「事件驱动」也不等于「循环不执行」。** Pizza 用 `EventStore` 订阅替换对话级 `while`，但 LLM handler 里仍然直接 `await` 模型；OpenSuperAgent 外层甚至是 400ms 轮询泵，内层再把一整轮交给 Pizza。它们回答的是「谁被什么叫醒」，不是「副作用能不能进内核」。

若把 Pure Agent 的切口画在这里，句子会变成：

> 日志是唯一事实；`reduce` 只产出 effect；真正的模型调用和工具调用永远在 interpreter 里；重放时核对这些 effect，而不是再执行一遍。

这不是 dsh 已经做完的事。dsh 做完的是前半句里的「模型历史」；后半句仍空着。2026-09 笔记里出现过的运行时字符串 `log-reconstruction desync`，在 `2e39e70` 全库已不存在——它随着 v0.2.0-rc.2 移除运行时不变量插件一起离开了。谁若还想要「篡改日志必被检出」，那是自己要守的断言，不是现行 dsh 的抛错。

## 轴 3：Agent 怎么说话

「一个跟用户说话，其它在后台干活」听起来像产品功能，落到运行时只有几种拼法。

**拼法一：子代理是工具。** 主会话调用一个工具，工具内部再开一轮；结果作为 tool result 回来。Claude Code 的 subagent、Sema 的 `sub_agent`、许多「后台 true」开关，都是这条。主会话的上下文不被子步骤刷屏，但子代理通常不是一等公民会话。

**拼法二：独立会话 + 邮箱 / 队列。** Codex 有 mailbox，采样中途可以「为了邮件抢占」；pi 默认不做 sub-agent，但同一 agent 有 steer / followUp 队列；dsh 的子代理树里，`sendMessage` 会先做成 `kind: 'agent-message'` 的用户消息，再 `steer` 进同一套 inbox——入口统一，类型仍在。任务板在 dsh 里**不**叫醒 agent。

**拼法三：编排账在循环外。** OpenSuperAgent：Router / Worker 同进程多 facade，通信是 SQLite inbox + 定时泵，不是对等消息。dsh-superagent-prototype：main 与 `worker-<ticket>` 靠 effect 队列、`relay`（唤醒）和 `notice`（注入但不唤醒）分工。前台进度是投影；后台完成是之后某一次输入。

**拼法四：产品级团队。** Claude Code 的 Agent teams（实验）：lead、队友、共享任务，用户可直连队友；限制包括进程内队友不能随 `/resume` 恢复。Hermes 有 `delegate_task`。Alma 不谈子代理，谈的是 workflow 与人的审批。

对照「要不要统一成一种消息」：

| | 用户插话 / 对端消息 / 外部事件 |
|---|---|
| 多数产品 | **不**统一。工具结果、子代理通知、邮箱邮件、真人输入类型不同 |
| dsh | 都进 Session 日志，但 `user/message`、`agent-message`、`subagent-settled` 仍分开 |
| Pizza | 跨 agent 的 `_tell` 最终往往包成带约定前缀的 `USER_MESSAGE`——统一了入口，丢了类型 |

<Infer /> 统一入口有价值；把别人的话伪装成用户原文会欠账。更干净的形状是：同一种 `Input` 管道，字段上保留 `user` / `peer` / `external`。

## 轴 4：怎样被嵌入

这条轴决定「Pure Agent 对集成方意味着什么」。

| | 主嵌入方式 | 常驻服务？ |
|---|---|---|
| Claude Code | 每次 `query()` 一个子进程，stdio | 另有 Anthropic 托管 Managed Agents；本地不是 App Server |
| Codex | 公开 TS SDK = `codex exec` 子进程 + JSONL | 有 app-server（stdio / unix / ws），但 TS SDK 默认不走它 |
| pi | 进程内 `createAgentSession()` | `pi --mode rpc` 是长寿命子进程，默认不听端口 |
| OpenCode | SDK 内存路由 | 可开 HTTP，默认本机 + 口令 |
| Hermes | 进程内 Python | gateway 常驻是为了 IM，不是给嵌入方用的 JSON-RPC 内核 |
| Alma | 无本地 SDK | 托管 HTTP / MCP |
| dsh | 同进程 Cordis；公开 SDK 拉 `dsh` 子进程 | Web profile 才听 `127.0.0.1:3080`；sdk / acp / headless 不听 |

规律很稳：**要给别人 embed，默认答案几乎都是「进程内库」或「需要时拉起一个进程」。** 常驻服务器出现在已经有多客户端、IM、桌面远程这些产品理由之后。Codex 自己的公开 TS SDK 都没有把 app-server 当成默认入口。

这也解释了为什么「一切皆插件」不能从 dsh 原样搬进 Pure Agent：dsh 的不可拔掉的是 Cordis 框架和事件契约，循环实现可以换；Pure Agent 若把 `reduce` 也做成配置项，就回到「没有特权核心」——那正好取消「执行者永远在 core 外」这句还没人占稳的话。

## 空位：谁还没站稳

把四条轴叠在一张表上（只标与 Pure Agent 相关的格）：

| | 日志派生模型历史 | 循环不执行副作用 | 进程内可 import | 核心保证不可被插件拔掉 |
|---|---|---|---|---|
| pi | 弱 | 否 | **是** | 循环在核心，但能力常外置到扩展 |
| dsh | **强** | 否 | 是（亦有子进程 SDK） | 否——loop 也可替换 |
| Codex / Claude Code | 弱 / 未公开 | 否 | 公开 SDK 多为子进程 | 产品本体强，但不是 TS 进程内纯内核 |
| OpenCode / Hermes | 中 | 否 | 有限 | 否 |

还没人同时稳住的格子是：

1. TypeScript 进程内可 `import`；
2. 模型可见历史（以及 effect）以追加日志为唯一事实；
3. `reduce` 永不执行副作用，interpreter 先记后做；
4. 这些保证不是 profile 里可卸的插件。

Pizza / Restate / Temporal 从侧面证明：事件订阅、journal 重放、activation 边界都有生产级先例；它们要么 handler 仍执行 I/O，要么不在「终端编码 Agent 内核」这个产品点上。空位仍然空着。

## 决策清单（读完后填）

下面不是我替你做的决定，是你读完四条轴后应能自己勾的题。勾完再谈 Pure Agent 的规格书。

**A. 真相**

- [ ] 只要可恢复的 JSONL / SQLite（入场券）
- [ ] 模型历史必须从日志 derive（dsh 已经走到）
- [ ] 连 effect 命令也必须先入日志，重放可核对（空位）

**B. 执行**

- [ ] 循环可以调模型和工具（主流）
- [ ] 循环只产出 effect，interpreter 执行（空位）
- [ ] 磁盘先写后做做成可卸插件（dsh）
- [ ] 磁盘先写后做做成内核保证（更严）

**C. 通信**

- [ ] 子代理主要是工具
- [ ] 独立会话 + 邮箱 / steer
- [ ] 循环外的编排账（inbox / outbox）
- [ ] 统一 Input 管道，保留 peer 类型（推荐讨论的形状）

**D. 嵌入**

- [ ] 只做进程内库
- [ ] 库 + 按需子进程桥（主流嵌入折中）
- [ ] 默认常驻 App Server（多客户端产品）

**E. 扩展**

- [ ] 一切皆插件，含 loop（dsh）
- [ ] 小内核不可拔，外侧模块可卸载（与「薄肌 / 成本按需」一致）

**F. 对外用词**（替代口头「积木」）

- [ ] 原语 Primitive = 内核不可再拆的概念
- [ ] 模块 Module = 外侧可装卸的能力
- [ ] 能力 Capability = 对用户叙述时的功能块
